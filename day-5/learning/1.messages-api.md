# The Messages / Chat API

## 1. What it is
Every chat model is called the same way: I send a **list of messages** and get a new message back. The model is stateless (Day 4), so the list is the whole conversation, and **my code builds it, stores it and sends it again every turn**.

```json
{
  "model": "some-model",
  "messages": [
    {"role": "user", "content": "Hi, I am Asha."},
    {"role": "assistant", "content": "Hello Asha!"},
    {"role": "user", "content": "What is my name?"}
  ]
}
```

## 2. Roles
| Role | Who writes it | Used for |
|---|---|---|
| `system` | me, the developer | Rules, tone, format, the task; it comes before the chat |
| `user` | the person (or my code on their behalf) | Questions, documents, instructions |
| `assistant` | the model (or me, to replay past turns) | Earlier answers; also a way to pre-fill the start of a reply |
| `tool` | my code, later (Day 16) | The result of a function the model asked me to run |

- User and assistant messages normally **alternate**, and the last one is a `user` message.
- Where the system prompt goes depends on the provider (section 6).
- The model never sees "who is who" except through these roles, so putting user text into the `system` role by mistake gives it too much authority.

## 3. The message array, drawn (the diagram for the day)
What my code sends on turn 3, and what comes back:

```
 request                                                    response
 +---------------------------------------------+            +--------------------------+
 | model, max_tokens, temperature              |            | role: assistant          |
 | system:   "You answer in one sentence."     |            | content: [text block]    |
 | messages:                                   |  ------->  | stop_reason: end_turn    |
 |   1 user       "Hi, I am Asha."             |            | usage: input / output    |
 |   2 assistant  "Hello Asha!"                |            +--------------------------+
 |   3 user       "I like chai."               |                         |
 |   4 assistant  "Nice choice!"               |                         v
 |   5 user       "What is my name?"   <- new  |           my code appends it as message 6
 +---------------------------------------------+           and saves the whole list in the DB
```
- Input tokens on turn 3 = system + messages 1 to 5. Output tokens = only the new reply.
- The assistant reply is **appended by my code**, otherwise the next turn has no trace of it.
- With a database the list becomes two tables: `conversations` and `messages` (role, content, tokens, model, created_at), as in today's task.

## 4. Content blocks
`content` can be a plain string, or a **list of blocks** when a message holds more than text:

```json
{"role": "user", "content": [
  {"type": "text", "text": "What is in this picture?"},
  {"type": "image", "source": {"type": "url", "url": "https://example.com/cat.png"}}
]}
```
- Block types: `text`, `image`, `document` (for example a PDF), and later `tool_use` and `tool_result`.
- Each block has a `type` field that says which shape it has. That is a **discriminated union**, the same pattern as Day 3 in Pydantic: `Field(discriminator="type")` picks the right model by reading `type`.
- The model's **reply is also a list of blocks** (Anthropic style), even if there is only one text block.
- Not every model accepts every block type (a text-only model rejects images). The provider docs say which.

## 5. Stop reasons: why the model stopped
Every response says why it ended. Code must check it.

| Meaning | Anthropic `stop_reason` | OpenAI `finish_reason` | What I should do |
|---|---|---|---|
| Finished normally | `end_turn` | `stop` | Use the answer |
| Ran out of `max_tokens` | `max_tokens` | `length` | The answer is **cut off**; raise the limit or continue; never trust truncated JSON |
| Hit one of my stop sequences | `stop_sequence` | `stop` | Fine; I asked for it |
| Wants to call a tool | `tool_use` | `tool_calls` | Run the tool, send the result back (Day 16) |
| Declined or filtered | `refusal` | `content_filter` | Show a safe message; do not parse the text as data |

- Gemini through the OpenAI-compatible endpoint uses the OpenAI names (Day 4: `finish_reason` was in the last chunk).

## 6. Provider differences (the same idea, different shapes)
| Point | Anthropic (Messages API) | OpenAI (Chat Completions) |
|---|---|---|
| Endpoint | `POST /v1/messages` | `POST /v1/chat/completions` |
| System prompt | a separate top-level `system` field | a message with role `system` (newer models: `developer`) |
| `max_tokens` | **required** | optional |
| Reply text | `response.content[0].text` (a list of blocks) | `response.choices[0].message.content` (a string) |
| Why it stopped | `stop_reason` | `choices[0].finish_reason` |
| Token usage | `usage.input_tokens`, `usage.output_tokens` | `usage.prompt_tokens`, `usage.completion_tokens` |
| Streaming | typed events (`content_block_delta` ...) | chunks (`chat.completion.chunk`) |

- OpenAI also has a newer **Responses API** (`input` and `instructions`, reply as a list of output items). The ideas are the same.
- Ollama and Gemini copy the OpenAI shape, which is why one client worked for both on Day 4.
- To support several providers I keep **my own internal message format** (role plus text or blocks) in the database, and convert to each provider's shape at the edge. Then switching a provider changes one function, not the whole app.

## 7. The official Python SDKs
```python
from anthropic import Anthropic, AsyncAnthropic      # sync and async
from openai import OpenAI, AsyncOpenAI

client = Anthropic()          # reads ANTHROPIC_API_KEY from the environment
reply = client.messages.create(
    model="<model name>",
    max_tokens=300,
    system="Answer in one sentence.",
    messages=[{"role": "user", "content": "What is an API?"}],
)
print(reply.content[0].text, reply.stop_reason, reply.usage)
```
- The **sync** client blocks the thread while it waits. Inside a FastAPI `async def` route I must use the **async** client (`AsyncAnthropic`, `AsyncOpenAI`) with `await`, or the whole server stalls (Day 2 asyncio).
- Create the client **once** (at start-up) and reuse it; it holds a connection pool.
- The SDK retries some errors itself (rate limits, 5xx) and has a `timeout`; I still handle `APIError` in my code.
- The key comes from the environment, never from the source code (`.env`, Day 4).
- Model names change often, so the model name is **configuration**, not a string hidden in the code.

## 8. Mistakes to avoid
| Mistake | What happens |
|---|---|
| Not appending the assistant reply | The next turn has no memory of it |
| Two `user` messages in a row (on a strict API) | An error, or the messages get merged |
| Ignoring `stop_reason` / `finish_reason` | Truncated answers treated as complete |
| Sync client inside an async route | The event loop blocks, other requests wait |
| Sending the whole history forever | Cost and latency grow every turn (Day 4); trim or summarise |
| User text in the `system` role | Prompt-injection risk; user text belongs in `user` |
| Hard-coding one provider's shape everywhere | Switching providers means rewriting the app |
