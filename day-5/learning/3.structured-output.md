# Structured output: getting data, not prose

## 1. Why free-text parsing breaks
Task: turn a messy student enquiry into data. If I ask for JSON in the prompt and parse the reply myself, it fails in ways that only show up in production:
- The model adds words around it ("Sure! Here is the JSON:") or wraps it in a code fence.
- A comma is missing, a quote is not closed, or the answer is cut off by `max_tokens`.
- Field names drift (`phone`, `phone_number`, `mobile`), or a number arrives as `"25 years"`.
- A value is invented to fill a field the text never mentioned.
- A regex that works on 20 samples fails on the 21st.

Structured output removes the first four problems; the fifth needs design (section 6).

## 2. Three levels of control
| Method | What is guaranteed | Notes |
|---|---|---|
| **Prompt only** ("reply with JSON") | Nothing | Only for quick tests |
| **JSON mode** (`response_format={"type": "json_object"}`) | The text is **valid JSON** | Not the shape: any keys, any types |
| **Strict JSON-schema mode** (native structured output) | The reply **matches my schema**: keys, types, enums | The provider constrains the tokens while decoding; this is the one to use |
| **Tool call as schema** | The tool arguments follow the tool's `input_schema` | Define a "tool" whose arguments are my schema, force it with `tool_choice`, read the arguments; the classic method before native support |

- Native structured output is supported by the big providers (OpenAI `response_format` with `json_schema` and `strict: true`; Anthropic with its structured-output option or the tool method) and by Ollama (the `format` field takes a JSON schema, so a local model can be constrained too). Exact parameter names change, so I check the current docs.
- Strict mode has limits: only a subset of JSON Schema is accepted, and for OpenAI every field must be listed as required and extra keys are forbidden (`additionalProperties: false`). "Optional" is written as "this type or `null`".
- Constrained decoding makes small local models give **valid** output far more often, but valid is not the same as correct (section 6).

## 3. Pydantic is the schema
I do not write JSON Schema by hand. I write a Pydantic model (Day 3), and generate the schema from it:

```python
from typing import Literal
from pydantic import BaseModel, Field

class Enquiry(BaseModel):
    name: str | None = Field(None, description="Student's name, null if not given")
    course: Literal["python", "data-science", "web", "unknown"]
    city: str | None = None
    phone: str | None = Field(None, description="Digits only, with country code if present")
    urgency: Literal["low", "normal", "high"] = "normal"
    summary: str = Field(description="One sentence")

schema = Enquiry.model_json_schema()          # send this to the provider
data = Enquiry.model_validate_json(reply_text)   # validate what came back
```
- `description` on a field is sent to the model, so it works as a **mini prompt for that field**.
- One model, three uses: the schema for the model, validation of the reply, and the response type of my FastAPI endpoint.
- The SDK helpers do the whole round trip: OpenAI's `client.chat.completions.parse(..., response_format=Enquiry)` returns `message.parsed` as an `Enquiry` object (check the current name in the docs).

## 4. Always validate, even with strict mode
- `Enquiry.model_validate_json(...)` can still raise `ValidationError` (refusal, truncated output, a provider without strict mode, a local model).
- Check `stop_reason` / `finish_reason` first: `max_tokens` means the JSON is cut off and cannot be parsed; a refusal is not JSON at all.
- On failure: **retry once** with the error message added, then give a clear `422` or `502` from my API. Never return half-parsed data.
- Treat the model output as **untrusted input**: bound lengths, and never put it straight into SQL or a shell.

## 5. The `instructor` library
A small library that wraps the SDK clients and does the schema, the call, the validation and the retry in one step:

```python
import instructor
from openai import AsyncOpenAI

client = instructor.from_openai(AsyncOpenAI())
enquiry = await client.chat.completions.create(
    model="<model>",
    response_model=Enquiry,        # the Pydantic class
    max_retries=2,                 # on ValidationError, send the error back to the model and try again
    messages=[{"role": "user", "content": text}],
)
```
- The reply comes back as an `Enquiry` object, not text.
- Its retry feeds the **validation error** to the model, so it can fix its own mistake.
- It works with many providers (Anthropic, Gemini, Ollama through the OpenAI-compatible client) with the same Pydantic model.
- Worth knowing even if I use native structured output directly: it is the same idea packaged.

## 6. Enums, Literal, optional and "unknown"
- Use `Literal[...]` or an `Enum` for any field with a fixed set of values (`urgency`, `course`, `category`). The model can no longer invent `"super urgent"`, and my code can `match` on the value.
- Make a field **optional (`str | None`)** when the text may not contain it. If every field is required, the model has to **make something up** to satisfy the schema, which is hallucination (Day 4) by design.
- Add an explicit `"unknown"` / `"other"` choice for enums, and say in the field description: "null if not stated in the text".
- A valid shape does not make the **content** true. The schema stops a bad phone *format*, not a wrong phone *number*. For important fields, check against the source text (does the value really appear in it?).
- Keep schemas small and flat. A 40-field schema gives worse accuracy and higher cost than two focused calls.

## 7. Streaming versus structured
- A structured result is only usable when **complete**, so `/extract` does not need streaming; `/chat` does.
- Partial JSON can be streamed and parsed progressively by some libraries, but it is rarely worth the complexity for a small object.

## 8. Local model comparison (for the task)
Same `/extract` through Ollama (`gemma3:270m` on this machine) versus a hosted model. What to measure on the same set of messy messages:
- **Validity rate:** how many replies pass `model_validate_json` (with and without the schema constraint).
- **Correctness:** compare fields against a hand-made answer for each message.
- **Speed:** time per request (the tiny local model on CPU was 18 tokens per second in Day 4).
- A small model is often valid but wrong: right shape, bad values.

## 9. Mistakes to avoid
| Mistake | What happens |
|---|---|
| `json.loads` on raw model text with no checks | Crashes on fences, extra words or truncation |
| Trusting JSON mode to enforce keys | It only guarantees valid JSON, not my fields |
| Every field required | The model invents values for missing data |
| No `description` on fields | The model guesses what `type` or `code` means |
| Skipping validation because "strict mode" | Refusals and truncation still produce bad output |
| Free-text where an enum belongs | Values like "High", "high ", "HIGH!!" in the database |
| One huge schema | Lower accuracy, more tokens, slower |
