# Streaming (SSE) from the model to the browser

## 1. Why stream
A full answer can take 5 to 30 seconds to generate. If I wait for all of it, the user stares at a spinner. With **streaming** the model sends the answer in small pieces as it writes, and the screen fills word by word.
- Total time is the same; **perceived latency** is much lower, because the first words appear at the **TTFT** (Day 4 task 6: 1.3 s for the small Gemini, 23 s for the 31B model).
- The user can start reading, and can stop early.
- Switch it on with `stream=True` (OpenAI style) or `client.messages.stream(...)` (Anthropic SDK).

## 2. What the provider sends
The stream is a series of small events. Anthropic's event types, in order:

| Event | What it carries |
|---|---|
| `message_start` | The empty message: `id`, `model`, `role`, and the input token usage |
| `content_block_start` | A block begins (text, or a tool call) |
| `content_block_delta` | **The new text** in `delta.text` (many of these) |
| `content_block_stop` | The block is finished |
| `message_delta` | The `stop_reason` and the final output token usage |
| `message_stop` | The end |
| `ping` | Keep-alive; ignore |
| `error` | Something failed **during** the stream (for example `overloaded_error`) |

- OpenAI-style streams (also Ollama and Gemini) send `chat.completion.chunk` objects: the text is in `choices[0].delta.content`, `finish_reason` arrives on the last chunk, and **usage only arrives at the end if I ask** (`stream_options={"include_usage": True}`, as in Day 4).
- Some chunks have no text (role only, usage only), so code must check before using `delta.content`.
- The Anthropic SDK hides the event parsing: `async with client.messages.stream(...) as s:` then `async for text in s.text_stream:`, and `await s.get_final_message()` gives the complete message with `stop_reason` and `usage`.

## 3. SSE: how my API streams to the client
**SSE (Server-Sent Events)** is a plain HTTP response that stays open. The server keeps writing text lines in a fixed format:

```
Content-Type: text/event-stream

data: {"text": "Hello"}

data: {"text": " Asha"}

event: done
data: {"stop_reason": "end_turn", "tokens": 12}

```
- Each event is one or more lines (`data:`, optionally `event:` and `id:`) ended by a **blank line**.
- SSE is one direction only (server to client), over normal HTTP, works through most proxies, and is simpler than WebSockets for this job.
- Express comparison: `res.setHeader("Content-Type", "text/event-stream")` and `res.write("data: ...\n\n")`. FastAPI does it with an **async generator**.

```python
from fastapi.responses import StreamingResponse

async def event_stream():
    async with client.messages.stream(...) as stream:
        async for text in stream.text_stream:
            yield f"data: {json.dumps({'text': text})}\n\n"
        final = await stream.get_final_message()
    yield f"event: done\ndata: {json.dumps({'stop_reason': final.stop_reason})}\n\n"

@router.post("/chat")
async def chat(...):
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```
- `sse-starlette` (`EventSourceResponse`) adds proper SSE formatting, keep-alive pings and disconnect handling; I check my FastAPI version too, because newer versions may ship their own SSE helper.
- Send JSON inside `data:` so the client can add fields later (ids, usage, errors).
- Useful headers: `Cache-Control: no-cache`, and `X-Accel-Buffering: no` so nginx does not hold the stream back in a buffer.

## 4. The client side (browser)
- The browser's `EventSource` only does **GET**, but `/chat` is **POST** (it carries the message). So the front end uses `fetch()` and reads `response.body.getReader()`, or a library such as `@microsoft/fetch-event-source`.
- For testing: `curl -N -X POST ... ` (`-N` turns off curl's buffering) shows the events arriving.
- In Python tests, `httpx` can stream a response with `client.stream("POST", ...)` and `aiter_lines()`.

## 5. Save the full text while streaming
The client sees pieces, but the **database needs the whole assistant message** when it is done.
```python
parts: list[str] = []
async for text in stream.text_stream:
    parts.append(text)                    # collect while relaying
    yield sse(text)
full_text = "".join(parts)                # save this when the stream ends
```
- Save the message **in a `finally`** so that a partial answer is still stored if something breaks, and store a flag or the stop reason (`end_turn`, `max_tokens`, `client_disconnected`, `error`).
- Take the final token counts from the provider's usage (Anthropic: `message_start` for input, `message_delta` for output), and store them in the message row.
- Do not open a database transaction for the whole stream; write the user message first, stream, then write the assistant message.

## 6. When the client disconnects
If the user closes the tab or presses stop, nobody reads the tokens any more, but the model keeps generating and I keep paying until the upstream call is closed.
- Starlette cancels the response generator when it notices the disconnect; the cancellation arrives as `asyncio.CancelledError` (or `GeneratorExit`) at an `await` inside my generator.
- Because I opened the upstream call with `async with client.messages.stream(...)`, leaving the block **closes the upstream connection**, and the provider stops generating. That is how "stop the upstream stream" works.
- Put the saving code in `try / finally`, and re-raise `CancelledError`; swallowing it hides the cancellation.
- Another way: poll `await request.is_disconnected()` between chunks and `break`.
- **Verify in logs:** log "stream started", "client disconnected after N chunks", "upstream closed", and compare the token usage with a full run. Tokens already generated before the close are still billed; later ones are not.

## 7. Errors in the middle of a stream
- The HTTP status line (`200`) is sent **before** the first token, so I cannot change it afterwards when something fails.
- Errors before the first byte (bad request, auth, rate limit) can still be normal HTTP errors, so do the cheap checks first (validate input, load history) and only then return the `StreamingResponse`.
- Errors after streaming has started (provider overload, network drop, timeout) must be sent **as an event**: `event: error` with a short message, then end the stream. The front end shows "something went wrong" and keeps the partial text.
- Save the partial answer with an `error` status, and never leak the stack trace to the client.
- Set a **timeout** on the upstream call so a stalled stream does not hang forever.

## 8. Mistakes to avoid
| Mistake | What happens |
|---|---|
| Forgetting the blank line after `data: ...` | The client never receives the event |
| Using a normal (sync) client in the generator | The event loop blocks; other users freeze |
| Not collecting the text | Nothing to save at the end |
| Letting the upstream call run after a disconnect | Paying for tokens nobody reads |
| Trying to return a 500 after streaming started | Impossible; use an `error` event |
| Proxy buffering | The text arrives all at once, which defeats the purpose |
| Assuming every chunk has text | Crashes on role-only or usage-only chunks |
