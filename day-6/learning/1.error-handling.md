# Error handling for LLM calls: what fails, what to retry, what to fail fast

An LLM call is a slow, rate-limited network call to someone else's servers, so it fails more often than a database call. In Day 5 I set `LLM_MAX_RETRIES=1` and a timeout and left it there. Day 6 is the full version.

## 1. The errors I will meet
| Error | Status | What it means | Retry? |
|---|---|---|---|
| **Rate limit** | 429 | Too many requests or tokens per minute (my Google AI Studio table showed 15 RPM for Flash Lite) | Yes, after waiting |
| **Quota exhausted** | 429 (some providers use the same code) | The daily limit or the money is used up | **No**, waiting for a minute does not help |
| **Overloaded** | 529 (Anthropic) or 503 | The provider has no capacity right now | Yes, with backoff |
| **Server error** | 500, 502, 504 | Their bug or a bad gateway | Yes, a few times |
| **Timeout** | none (no answer) | Connect, read or total time ran out | Yes, once or twice |
| **Network drop** | none | Connection reset, DNS | Yes |
| **Bad request** | 400 | My request is wrong (bad parameter) | **No**, same request fails again |
| **Context too long** | 400 (or 413) | Input plus `max_tokens` is bigger than the model's window | **No**, shorten the input first (Day 4: tokens, context) |
| **Auth** | 401, 403 | Wrong or missing key, no access to the model | **No**, fix the key |
| **Not found** | 404 | Wrong model name | **No** |
| **Content refusal** | 200 with a finish reason such as `content_filter`, `SAFETY` or `refusal` | The model or a safety filter refused to answer | **No**, not an error in HTTP terms |

The last row is the tricky one: the call succeeded, so no exception is raised. I must look at the finish reason and the content myself.

## 2. Retry or fail fast
The rule: **retry only when waiting or trying again can change the result.**
- Retry: 429 (rate), 5xx, 529, timeouts, connection errors.
- Fail fast: 400, 401, 403, 404, context-too-long, refusals, and quota exhausted. Retrying these only burns time (and sometimes money) and delays the real error message.
- Retrying a **validation failure** (the model answered, but the JSON does not match my Pydantic model) is a different loop: send the Pydantic error back to the model and ask it to fix the output, at most 2 times. I already built the one-retry version in `/extract` on Day 5.
- A stream can only be retried **before the first token** was sent to the client. After that, the client has already seen text, so I send an `error` event instead (Day 5, `2.streaming.md`, section 7).
- Retrying a request is safe here because a chat completion has no side effects on my side, except that I pay again for the input tokens. A request that triggers a **tool with side effects** (send an email) must not be blindly retried.

## 3. Rate limits and `retry-after`
- A 429 response usually carries a `retry-after` header (seconds to wait). If it is there, **wait that long** instead of guessing.
- Anthropic and OpenAI also send headers such as the remaining requests and tokens. I can log them to see how close I am to the limit.
- Limits are per project and per model, and they have three dimensions: requests per minute (RPM), tokens per minute (TPM) and requests per day (RPD). The numbers come from the AI Studio rate-limit page, not from the docs.
- Better than reacting to a 429 is **not hitting it**: a semaphore or a rate limiter in front of the provider (see `4.provider-abstraction.md`).

## 4. Exponential backoff with jitter
Without a pause, a retry loop hammers a server that is already struggling. With a fixed pause, 100 clients all retry at the same moment and fail together again.
```python
delay = min(cap, base * 2 ** attempt)    # 1 s, 2 s, 4 s, 8 s ... up to the cap
sleep_for = random.uniform(0, delay)     # "full jitter": spread the clients out
```
- `base` is about 0.5 to 1 s and `cap` about 20 to 30 s.
- **Jitter** means a random part of the delay, so clients do not retry in step.
- If `retry-after` is present, use `max(retry_after, sleep_for)`.
- Stop after **N attempts** (3 or 4) and also after a **total time budget**, so a request does not wait for minutes. Day 5 showed why: one stuck call took 182 s with the SDK's defaults.
- This is the Day 2 decorator idea: a decorator that wraps an async function, catches the retryable exceptions, sleeps and tries again. It needs `asyncio.sleep` (never `time.sleep`, which would block the event loop).
- The OpenAI SDK has its own `max_retries` with backoff built in. Writing my own retry gives me one place to log, count, honour a total budget and **switch to a fallback**. If I write my own, I set the SDK's `max_retries=0` so the two do not multiply (2 x 3 = 6 calls).

## 5. Timeouts: three kinds
| Timeout | Meaning |
|---|---|
| **connect** | Time to open the connection (set small, 5 s) |
| **read** | Time to wait for the **next bytes**. In a stream this is the gap between chunks, not the whole answer |
| **overall** | The whole call from start to end; `httpx` has no single "total" timeout, so I wrap the call in `asyncio.timeout(...)` or `anyio.fail_after(...)` |

- A long streamed answer can take 60 s and still be healthy, because each chunk arrives in time. A model that is stuck sends nothing, and the read timeout catches it.
- For a non-streaming call, the read timeout is the time to the first byte, which can be the whole generation. So the timeout must be longer than a normal answer.
- Day 5 gotcha: Gemini's first token took 1 to 25 s and 60 s once, so a 60 s timeout was borderline.

## 6. Context-length errors
- The error says the prompt plus `max_tokens` is more than the window. Retrying cannot fix it.
- Prevent it: count tokens before sending (Day 4), keep `CHAT_HISTORY_LIMIT` small, trim or summarise old history.
- If it still happens: return a clear error to the user ("this conversation is too long"), or retry **once** with less history. Do not loop.

## 7. Content-policy refusals
- Shapes differ: Anthropic returns `stop_reason: "refusal"` on newer models; OpenAI has `finish_reason: "content_filter"` or a `refusal` field on the message; Gemini has `finishReason: SAFETY` or a blocked prompt with no candidates.
- Treat it as a normal **result of type "refused"**, not a crash. Store it with its own status and show a polite message.
- For `/extract`, a refusal on an injection attempt can be the **correct** answer (the Day 6 report has a "correctly refused" column).

## 8. Circuit breaker (awareness)
If a provider is down, every request still waits for its timeout and retries, which makes my service slow for everyone. A **circuit breaker** stops calling a failing provider for a while.
- **Closed**: normal, calls go through; failures are counted.
- **Open**: after N failures in a row (or a failure rate) the breaker opens; calls fail immediately (or go to the fallback) for a cool-down time, for example 30 s.
- **Half-open**: after the cool-down, let one test call through. Success closes the breaker; failure opens it again.
- Libraries exist (`pybreaker`, `aiobreaker`), and the logic is about 30 lines. For now I only need to understand it.

## 9. Fallback to a second model or provider
- After N failed attempts on the primary (or when its breaker is open), call the **secondary**: another provider, a smaller model, or the local Ollama model.
- Things to remember: the fallback may give a worse answer (Day 5: the 270M model got only 39% of fields right), may have a different context size, and costs differently. So I **record which model actually answered** in the response and the log (`meta.model`, `meta.fallback_used`).
- Fallback is for availability errors (429 after waiting, 5xx, timeouts). It is not for 400 or auth errors: those would fail on the second provider too, or hide a bug.

## 10. Mistakes to avoid
| Mistake | What happens |
|---|---|
| Retrying 400, 401 or quota errors | Wasted time, and the real error is hidden |
| Retry with no jitter | All clients retry together and fail together |
| No total time limit | A request waits for minutes |
| My own retry plus the SDK's retry | Calls multiply (3 x 3 = 9) |
| Retrying a stream after text was sent | The client gets the answer twice |
| Treating a refusal as success (or as a crash) | Empty text saved, or a 500 for the user |
| Fallback that hides which model answered | I cannot explain a bad answer later |
| `time.sleep` in async code | The whole event loop freezes |
