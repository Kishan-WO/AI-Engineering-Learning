# Token accounting and cost: knowing what every request costs

Day 4 task 2 estimated the cost of 1 million messages from token counts. Day 6 does it for **real requests**: read the usage from every response, turn it into money, and group it by tenant, user and feature.

## 1. Read `usage` from every response
Every provider returns the token counts. I save them, because the bill is built from them and a stream only gives them at the end.
| Provider | Where | Fields |
|---|---|---|
| OpenAI style (also Gemini and Ollama compat) | `usage` (in a stream: last chunk, only with `stream_options={"include_usage": True}`) | `prompt_tokens`, `completion_tokens`, `total_tokens`, and `prompt_tokens_details.cached_tokens` |
| Anthropic | `usage` on the message (stream: `message_start` for input, `message_delta` for output) | `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens` |

The four numbers I want for every request:
1. **input** tokens (normal, not cached)
2. **output** tokens
3. **cache-read** tokens (input that came from the cache)
4. **cache-write** tokens (input that was stored in the cache; Anthropic charges extra for this)

**Gotcha: the providers count differently.** In Anthropic's `usage`, `input_tokens` does **not** include the cache read and write tokens, so total input = the three added together. In the OpenAI style, `prompt_tokens` **includes** the cached tokens, and `cached_tokens` is a part of it. If I do not normalise this in the adapter, my cost numbers are wrong for one of the two. The adapter must return one shape:
```python
@dataclass
class Usage:
    input_tokens: int          # new (uncached) input only
    output_tokens: int
    cache_read_tokens: int = 0
    cache_write_tokens: int = 0
```
For OpenAI style: `input_tokens = prompt_tokens - cached_tokens`.

Other things to remember:
- If the provider gives no usage (some local servers, or a cancelled stream), the value is `None`. I keep `None`, not 0, so "unknown" is not mistaken for "free" (the Day 5 cancelled messages have `None` tokens).
- Thinking tokens of reasoning models are usually billed as output tokens and may be reported separately; check each provider.
- A cancelled stream is still billed for the tokens already generated.

## 2. Cost per request from a price table
Prices live in **config**, not in code, because they change every few months. Day 4 said the same: the real prices come from the provider's current price page.
```python
PRICES = {   # USD per 1,000,000 tokens
    "gemini-3.1-flash-lite": {"input": ..., "output": ..., "cache_read": ..., "cache_write": 0},
    "gemma3:270m":           {"input": 0,   "output": 0,   "cache_read": 0,   "cache_write": 0},
}
```
(The numbers stay `...` here on purpose: I copy them from the price page on the day I build it.)

```
cost = (input_tokens       * price.input
      + output_tokens      * price.output
      + cache_read_tokens  * price.cache_read
      + cache_write_tokens * price.cache_write) / 1_000_000
```
- It is the same split as in Day 4 task 2: input and output are billed separately, and the output price is usually several times the input price.
- Cache reads cost a fraction of normal input (see `3.prompt-caching.md`), so a cached request is cheaper.
- A **local model** has a price of 0 per token, but it is not free (hardware, power, slow). I can add a "compute cost" later if I want a fair comparison.
- Use `Decimal` or integer micro-dollars for stored money, not float, if the numbers will be summed many times. For a learning project a float with rounding at display time is acceptable, but I should know the difference.
- Store the **price version** (or the price used) with the request. If a price changes next month, the old rows must still show the old cost.
- An unknown model has no price: log a warning and store `cost = None`, never crash a request over a missing price.

## 3. Cost per user, per tenant, per feature
One request has a cost; the value comes from grouping them. For that, every LLM call must be saved with its labels:
| Column | Why |
|---|---|
| `tenant_id`, `user_id` | Who to bill or limit (my tables are already scoped by tenant) |
| `feature` | `chat`, `extract`, later `rag`, `router`: which part of the product spends the money |
| `model`, `backend` | Compare models; see if the fallback was used |
| `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens` | The raw facts |
| `cost_usd` | The computed result |
| `latency_ms`, `request_id`, `status` | Debugging, tied to the request log |

- A table like `llm_calls` (one row per **provider call**, not per user message) is better than the `messages` table, because one user message can cause several calls (a retry, a fallback, a repair after a validation error), and I want to pay attention to all of them.
- Then the questions are one `GROUP BY` away: `SUM(cost_usd) ... GROUP BY tenant_id`, per feature, per day, per model.
- The log line (JSON, with `request_id`) should carry the same fields, so cost can be read from logs too.

## 4. Budgets and alerts
- **Per-tenant budget**: a monthly limit in USD (or tokens). Before a call, check `spent_this_month + estimate <= limit`.
- **Soft limit** (for example 80%): send an alert or log a warning. **Hard limit**: stop and answer `429` or `402`-style ("budget used up"), so one tenant cannot create an unlimited bill.
- Check cost **before** the call from an estimate (input tokens are known; output is capped by `max_tokens`, so the **worst case is known**), and **record** the real cost after.
- Alerts can be a log line at first; later a message to a channel. A **daily total** check catches a loop that is calling the model in a runaway.
- Keep counters cheap: a running total updated per call (or Redis later), not a `SUM` over millions of rows on every request.

## 5. Mistakes to avoid
| Mistake | What happens |
|---|---|
| Treating `prompt_tokens` and Anthropic's `input_tokens` as the same thing | Cached tokens are counted twice or not at all |
| Hard-coding prices in the code | Wrong costs after the next price change |
| One row per user message instead of per provider call | Retries, repairs and fallbacks are invisible |
| Saving `0` when usage is unknown | Looks free; hides a missing measurement |
| Float sums stored as the source of truth | Small rounding drift in the totals |
| No tenant in the cost row | I cannot answer "who spends the money?" |
| Checking the budget only after the call | The overspend has already happened |
