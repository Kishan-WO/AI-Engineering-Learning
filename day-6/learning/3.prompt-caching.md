# Prompt caching: paying less for the part of the prompt that never changes

My `/chat` sends the same system prompt and a growing history on every turn (Day 5: input tokens went from 29 to 56 on turn 2). Everything that repeats can be cached by the provider, which makes it cheaper and faster.

## 1. What it is
- The provider remembers the **already-processed beginning** of my prompt (its internal state after reading those tokens). If the next request starts with exactly the same tokens, it skips the work for that part.
- The result: **cache-read tokens** are billed at a **fraction** of the normal input price, and the first token comes sooner (lower TTFT).
- It is not a cache of **answers**. The model still generates a fresh reply; only the reading of the repeated input is saved. (Caching answers myself, for identical questions, is a separate idea.)
- It matters most when the repeated part is **big**: a long system prompt, a list of tools, a document, a few-shot set, or a long conversation history.

## 2. Stable prefix first, variable content last
The cache works on a **prefix**: the match goes from the start of the prompt and stops at the first token that differs. So the order is everything:
```
[ system prompt ]      stable   -> cacheable
[ tool definitions ]   stable   -> cacheable
[ few-shot examples ]  stable   -> cacheable
[ older history ]      grows, but the old part stays the same -> cacheable
[ new user message ]   changes every time -> not cached
```
Things that silently break the cache if placed early:
- the current date or time in the system prompt
- a request ID, user name or random value at the top
- tool definitions that change order between requests
- a different system prompt per tenant (each tenant gets its own cache, which is fine, but be aware)

The fix is always the same: **move the changing part to the end**.

## 3. Explicit markers vs automatic caching (depends on the provider)
| Style | How it works | Example |
|---|---|---|
| **Explicit** | I mark where the cacheable prefix ends | Anthropic: `cache_control: {"type": "ephemeral"}` on a content block (system, tools or a message) |
| **Automatic** | The provider caches long prefixes by itself; I do nothing except keep the prefix stable | OpenAI and Gemini (implicit caching) |
| **Explicit object (Gemini)** | I create a cached content object, with a name and a lifetime, and refer to it | Gemini "context caching" API |

What to check in each provider's **current docs** (these numbers change, so I do not memorise them):
- **Minimum size** of the prefix to be cached (often around 1,024 tokens; it differs by model). A short prompt is never cached.
- **Lifetime** (TTL): for example a few minutes that refresh on each use; some providers offer a longer TTL at a higher write price.
- **Price**: cache reads are cheaper than normal input; on Anthropic **cache writes cost more** than normal input, so a prefix that is used only once loses money.
- **Which models** support it.
- On Anthropic the cache covers **tools, then system, then messages** in that order, and changing an earlier part invalidates the later parts.

Anthropic example (explicit marker):
```python
system=[{
    "type": "text",
    "text": LONG_SYSTEM_PROMPT,
    "cache_control": {"type": "ephemeral"},   # cache everything up to here
}]
```
My project talks to Gemini through the OpenAI-compatible endpoint, which uses **automatic (implicit)** caching, so for `/chat` the work is mostly: keep the system prompt first and stable, make it long enough, and **measure** whether it hits.

## 4. Measuring the cache hit rate from usage
I do not assume it works; the usage tells me.
| Provider | Where the cached part is reported |
|---|---|
| Anthropic | `usage.cache_read_input_tokens` (hit) and `usage.cache_creation_input_tokens` (written) |
| OpenAI style | `usage.prompt_tokens_details.cached_tokens` |
| Gemini (native) | `usageMetadata.cachedContentTokenCount` |

```
hit rate = cache_read_tokens / (cache_read_tokens + cache_write_tokens + uncached input_tokens)
```
- Log it per request, and aggregate per feature (this is the "cache-read tokens in logs" task).
- Expected pattern in a conversation: turn 1 has `cache_read = 0` (cold, a write happens), turn 2 onwards shows the prefix in `cache_read`.
- If the hit rate stays at 0 although the prompt repeats, the usual causes are: the prefix is below the minimum size, something variable sits near the top, the TTL expired between calls, or the model does not support caching.
- The saving shows in the cost: use the cache-read price in the formula from `2.token-accounting-and-cost.md`.

## 5. When it helps and when it does not
- **Helps:** a long, fixed system prompt; many users sharing the same big document; a long chat history where each turn adds a bit; few-shot examples; tool definitions.
- **Does not help:** prompts shorter than the minimum; every request has a different prefix; calls far apart in time (the cache expired); a rarely used prefix on a provider that charges extra for writes.
- A cached prompt is **not** a reason to put more text in it; fewer, shorter instructions are still better (and a hallucination risk goes with long text, Day 4).

## 6. Mistakes to avoid
| Mistake | What happens |
|---|---|
| Timestamp or user ID at the top of the system prompt | The prefix differs every time: hit rate 0 |
| Changing the order of tools or keys | Prefix differs, cache miss |
| Not reading `cache_read` from usage | I think it works, and it does not |
| Caching a prefix that is used once | Anthropic: I pay the higher write price and never read |
| Counting cached tokens as normal input in the cost | Cost shown higher than the bill |
| Prefix below the minimum size | Silent no-op |
