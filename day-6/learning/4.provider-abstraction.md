# Provider abstraction: one `LLMClient`, many models

In Day 5 I already started this: `LLMProvider` (a `Protocol`) with `stream_chat` and `complete_json`, one `OpenAICompatProvider` for Gemini and Ollama, and a registry that builds them from settings. Day 6 grows it into a proper layer.

## 1. Why a thin adapter
- **Swap models by config**, not by editing code: change `LLM_MODEL` or the provider name in `.env`.
- **A/B test** two models on the same inputs (I did this by hand in Day 5 with `compare_extract.py`).
- **Fallback** when a provider fails (`1.error-handling.md`, section 9).
- **One place** for retries, timeouts, logging, usage and cost, so a route handler never touches an SDK.
- **Tests** use a fake provider and never call a real model.
- The rest of the app depends on **my types** (`ChatMessage`, `Usage`, `StreamEvent`), not on `openai` or `anthropic` types. Only the adapter files import an SDK.
- "Thin" matters: the adapter translates and normalises. It should not grow into a framework with its own prompt language.

## 2. One `LLMClient` Protocol with three methods
```python
class LLMClient(Protocol):
    name: str                                   # "gemini-flash-lite", "claude-haiku", "local"

    async def generate(self, request: LLMRequest) -> LLMResponse: ...
    def stream(self, request: LLMRequest) -> AsyncIterator[StreamEvent]: ...
    async def generate_structured(
        self, request: LLMRequest, schema: type[T]
    ) -> StructuredResponse[T]: ...
```
- **`generate`**: one full answer (text, stop reason, usage).
- **`stream`**: async iterator of events: text deltas, then a final event with stop reason and usage.
- **`generate_structured`**: returns a validated Pydantic object, using the provider's native structured output when it has one, and a tool-as-schema fallback when not (Day 5 `3.structured-output.md`).
- The request and response are **my own dataclasses**: model, messages, system prompt, `max_tokens`, `temperature`, and in the response the text, the stop reason, **normalised `Usage`** (input, output, cache-read, cache-write), latency and the model that really answered.
- Protocol (structural typing) means an adapter does not inherit from anything: if it has the methods, it fits. A `FakeClient` for tests fits the same way.

## 3. The adapters (task 1)
| Adapter | Talks to | Notes |
|---|---|---|
| OpenAI-compatible | OpenAI, Gemini (compat endpoint), Ollama, vLLM | What I have; one class, different `base_url`, key and model |
| Anthropic | Anthropic Messages API | Different shape: `system` is separate, content blocks, `cache_control`, its own stream events and usage names |
| Ollama (local) | `http://localhost:11434/v1` | Can reuse the OpenAI-compatible adapter; price 0 |

- The adapter hides the differences: the system prompt position, stop-reason names (`stop` vs `end_turn`, `length` vs `max_tokens`), the usage field names, and how errors look.
- **Error mapping** is part of the adapter: it turns each SDK's exceptions into my own few types (`RateLimited(retry_after)`, `Overloaded`, `Timeout`, `ContextTooLong`, `Refused`, `AuthError`, `BadRequest`). Then the retry code and the fallback code work on **my** errors, for every provider.
- Selection through settings: a name such as `LLM_PROVIDER=gemini` or a list for fallback `LLM_FALLBACKS=["local"]`, and the registry builds the clients.

## 4. Where the wrapper goes (middleware, retry, fallback)
Decorator style: each layer wraps a client and is itself an `LLMClient`, so they stack.
```
route  ->  LoggingClient  ->  RetryingClient  ->  FallbackClient  ->  [primary, secondary]
```
- **Logging / accounting wrapper** (task 2): per call, log `request_id`, tenant, model, input / output / cached tokens, cost, latency and status as one JSON line, and save the `llm_calls` row.
- **Retry wrapper** (task 3): backoff with jitter on the retryable errors only.
- **Fallback wrapper**: after N failures (or an open circuit breaker) call the next client; record `fallback_used`.
- **Validation-repair loop** (task 4): in `generate_structured`, on a Pydantic error send the error back and ask for a fix, at most 2 times; count the attempts.
- Because every layer has the same interface, I can test each one alone with a fake client that fails on purpose.

## 5. Concurrency limiting: a semaphore per provider
- My own service can create **too many parallel calls** (50 inputs at once, many users) and hit the provider's rate limit or make my own server slow.
- A `asyncio.Semaphore(n)` per provider limits the calls in flight:
```python
async with self._semaphore:           # at most n calls at the same time
    return await self._call(request)
```
- Pick `n` from the provider's limit (the AI Studio page showed 15 RPM for Flash Lite, so a small number) and from how many I want in parallel for a local model on CPU (1 or 2).
- A semaphore limits **concurrency**, not **rate per minute**. For RPM I also need a rate limiter (a token bucket) or to rely on backoff after a 429.
- Release happens automatically with `async with`, even on errors and cancellation.
- For the 50-input test: run them with `asyncio.gather` but behind the semaphore (and not 50 at once).

## 6. LiteLLM or OpenRouter instead of writing it myself
| | Own thin adapter | LiteLLM (library or proxy) | OpenRouter (hosted gateway) |
|---|---|---|---|
| What | My `LLMClient` + adapters | One interface to 100+ providers, can run as a proxy | One API and one key for many models |
| Good | Full control, a small surface, no extra dependency, I understand every line | Fast to add providers; has retries, fallbacks, cost tracking | Easy model switching; one bill |
| Cost | I write and maintain each adapter | A big dependency; its bugs and its release speed become mine; its own idea of normalising usage | An extra hop (latency), an extra party sees my data, a price margin, it can be down too |

- For learning, and while I use two or three providers, **my own thin adapter** is right: I learn the real differences. At ten providers, or when a team needs a central gateway, a library or a proxy pays off.
- Whatever I choose, keep it **behind my `LLMClient` Protocol**, so I can change my mind without touching the routes.

## 7. Batch APIs for large offline jobs (awareness)
- Providers offer a **batch API**: I upload many requests, they process them within hours (often up to 24 h), and I download the results. Typical discount is large (around half the price); check the current price page.
- Good for: re-labelling 100,000 enquiries, running an evaluation set, creating embeddings or summaries overnight.
- Not for: anything a user is waiting for.
- Results come back unordered, so every request carries a `custom_id` and I match by it. Some requests in a batch can fail while others succeed.
- It can combine with prompt caching on some providers.

## 8. Mistakes to avoid
| Mistake | What happens |
|---|---|
| SDK types leaking into the routes | Changing provider means changing everything |
| An adapter that does not normalise usage | Wrong cost for one provider |
| Retry in the adapter and in the SDK | Calls multiply |
| Different error types per provider reaching the retry code | A `429` handled for one provider and not for another |
| No concurrency limit on a batch of inputs | Self-inflicted 429s |
| A fallback that is silent | I cannot tell which model gave the answer |
| Over-building (my own mini-LangChain) | The "thin" adapter becomes the thing I have to maintain |
