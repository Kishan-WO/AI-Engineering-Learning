# Re-rankers

A re-ranker takes the candidates from retrieval and reorders them with a cross-encoder (note 3). It is a switchable stage: today's flag is `RERANKER=none|cohere|bge`.

## 1. The options
| Type | Examples | Good | Limits |
|---|---|---|---|
| **Hosted** | Cohere Rerank, Voyage, Jina | no model to run; one HTTP call; often multilingual | network latency, cost per search, data leaves my infrastructure, rate limits |
| **Open (self-run)** | `BAAI/bge-reranker-v2-m3`, mixedbread rerankers | free per query, private, no network hop | needs CPU or GPU, a model download, memory; speed on my laptop CPU is something I **measure** |
| **LLM as re-ranker** | a chat model asked to rank the chunks | flexible, can explain | expensive and slow; awareness only |

- I check the current model names, languages and prices in each provider's docs (they change often).
- For Hindi and Hinglish I need a **multilingual** model; the BGE reranker v2 m3 is built for that, and a hosted provider's multilingual model is the equivalent. I test both on my Hindi queries.

## 2. Two-stage retrieval
```
query
  -> vector search (top 50)  \
  -> keyword search (top 50) /-> RRF -> top 50 candidates
  -> re-ranker scores 50 pairs -> sort -> keep top 5
  -> prompt (Day 12)
```
- **Retrieve many cheaply, re-rank few expensively.** The candidate count `N` is the main knob: more candidates raise the chance that the right chunk is in the list and raise the latency and cost almost linearly.
- **Keep fewer** for the prompt (5), because each chunk costs input tokens and adds noise (Day 12).
- The re-ranker also gives each chunk a **relevance score** that is usually more informative than a cosine, so it can drive the "nothing relevant" decision (Day 12). Its scale is model-specific, so the threshold must be calibrated on my own answerable and unanswerable questions, as on Day 12.

## 3. The latency budget
- Interactive use needs a stated budget. The plan's example: **the re-ranker adds at most +300 ms at p95**. I write my own number before measuring, so I cannot choose it to fit the result.
- **p95** means 95% of requests were faster than this. The average hides the slow tail that users actually feel.
- What drives the time:
  - number of candidates `N` (the main lever)
  - chunk length (longer pairs cost more, and long ones are truncated)
  - hosted: network round trip, provider load
  - open: CPU against GPU, model size, batch size
- Levers if I am over budget: reduce `N` (for example 50 to 30), shorten chunks passed to the re-ranker, switch model, use a hosted service with a near region, run the model on a GPU, **skip the re-ranker when it is not needed** (a short exact-ID query that keyword search already solved).
- How to measure honestly is in `Notes/02` (enough samples, warm and cold, per stage).

## 4. Fail open
- The re-ranker is an **improvement**, not a requirement. If the hosted call times out or errors, the pipeline returns the **fused order** from stage 1 and logs the failure, instead of failing the question.
- A timeout is part of the budget: a call that exceeds it is cancelled, not awaited. Use the retry rules from Day 6 only if the budget allows a second attempt (usually it does not).
- The same idea returns on Day 21 as graceful degradation.

## 5. What to log
For every query: candidate count `N`, the stage-1 order of the final top 5, the re-ranked order, each stage's latency, whether the re-ranker was skipped or failed, and the cost for hosted calls (Day 6). Then "did the re-ranker move the right chunk up?" is a question with an answer. Task 6 builds on the same log.

## 6. Does it help? Not assumed
- A re-ranker usually helps. It is not free, and on some corpora with a very good first stage it changes little. The rule from the plan stands: **no stage is accepted without a number.**
- Today I compare on my 20 Day 9 queries (recall@5, MRR) and the 5 exact-code queries. The proper answer comes on Day 14 with the golden set: "did the re-ranker help?" with a number.

## 7. Mistakes to avoid
| Mistake | What happens |
|---|---|
| Re-ranking only the top 5 | nothing to reorder; the right chunk may be at rank 12 |
| Re-ranking 200 candidates | the latency budget is gone |
| No timeout on the hosted call | one slow call stalls the user's question |
| Using an English-only re-ranker on Hindi | confident wrong ordering |
| Judging by the average latency | the p95 hides in the tail |
| Using the re-ranker score as a threshold without calibration | wrong refusals |

## 8. What I need to remember
- The re-ranker only reorders the shortlist: first-stage recall decides what it can do.
- `N` is the cost and quality knob; the budget is written down before I measure.
- Fail open to the fused order. Log which stage found the final top chunk.
