# Bi-encoders versus cross-encoders

The embedding model of Day 9 and the re-ranker of today are two different designs for the same job: scoring how well a document answers a query. They trade speed for accuracy.

## 1. Bi-encoder (what I already use)
```
query    -> encoder -> vector q
document -> encoder -> vector d     (computed once, stored)
score = cosine(q, d)
```
- The query and the document are encoded **separately**. They never see each other.
- **Fast:** document vectors are precomputed at ingestion (Day 11); a query costs one encoding plus a nearest-neighbour search (Day 10), a few milliseconds over my 2,097 vectors.
- **Less precise:** each side is squeezed into one vector before the comparison, so fine details (negation, a number, which entity does what) can be lost.
- This is the **retrieval** stage: it must find a few good candidates among thousands.

## 2. Cross-encoder (the re-ranker)
```
[query + document together] -> model -> one relevance score
```
- The query and the document go **in the same input**. Every word of the query can attend to every word of the document, so the model reads them together, the way a person checks whether a passage answers a question.
- **More accurate** on the final ordering, especially for questions where the exact relationship matters.
- **Slow:** nothing can be precomputed, because the score depends on the pair. One model run **per (query, document) pair**, at query time. For 50 candidates that is 50 runs per question, and the cost grows with the length of each document.
- So it cannot scan the whole corpus: it only sees a **shortlist** from the first stage.

## 3. Side by side
| | Bi-encoder | Cross-encoder |
|---|---|---|
| Input | query and document separately | query and document together |
| Precompute documents? | yes | no |
| Cost per query | one encoding + ANN search | one model run per candidate |
| Accuracy | good | better on the top of the list |
| Scales to the corpus? | yes | no, shortlist only |
| Role | stage 1: retrieve | stage 2: re-rank |
| Output | a vector | a score for the pair |

## 4. Two stages, because of the numbers
- Running a cross-encoder on all 2,097 chunks for one query is 2,097 model runs: far too slow for an interactive request. At 100,000 chunks it is impossible.
- Running it on the **top 50** from retrieval is affordable and fixes most of the ordering mistakes at the top.
- The first stage is tuned for **recall** (do not lose the right chunk), the second for **precision at the top** (put it first). That is why the stage-1 candidate count matters: a re-ranker cannot rescue a chunk that was never retrieved. (Diagram in `Notes/02`.)

## 5. ColBERT and late interaction: awareness
- Late interaction keeps **one vector per token** instead of one per document. At query time each query token finds its best-matching document token, and the matches are summed.
- A middle ground: more precise than a single vector, cheaper than a full cross-encoder, because document token vectors are still precomputed.
- The price is storage (many vectors per chunk) and special indexes. Out of scope for this course; I know it exists and why.

## 6. What this means for my pipeline
- Stage 1 (vector + keyword + RRF) returns about 50 candidates, tuned so the right chunk is almost always among them.
- Stage 2 (cross-encoder) scores each (query, chunk) pair and I keep the top 5 for the prompt.
- **Input length:** the cross-encoder has a maximum length for query plus chunk. A chunk longer than that is cut off, so the chunk size I chose on Day 11 matters here too.
- **Languages:** the re-ranker must be multilingual if my queries and chunks are Hindi or Hinglish.

## 7. What I need to remember
- Bi-encoder: separate, fast, precomputed, good for finding candidates.
- Cross-encoder: together, slow, per pair, good for ordering a shortlist.
- Two stages exist because of cost, and the second stage can only reorder what the first one found.
