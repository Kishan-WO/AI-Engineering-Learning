# Keyword search

Vector search finds text with similar **meaning**. Keyword search finds text with the same **words**. A real system needs both, because users ask both kinds of question.

## 1. BM25 at an intuitive level
BM25 scores a chunk for a query by three ideas:
| Idea | Meaning | Example |
|---|---|---|
| **Term frequency (TF)** | a chunk that mentions the query word more often is a better match, with **diminishing returns** (the 10th mention adds much less than the 2nd) | "refund" 3 times beats once |
| **Inverse document frequency (IDF)** | a rare word says more than a common one | "ERR_4021" is worth far more than "the" |
| **Length normalisation** | a short chunk that mentions the word is more specific than a long one that mentions it once | a 100-word chunk beats a 3,000-word one |

- The score is a sum over the query words. There is no understanding of meaning: "car" does not match "automobile".
- Two parameters (usually called `k1` and `b`) control the TF saturation and the length effect. The defaults work; I do not tune them before measuring.
- BM25 scores are **not** cosine similarities and cannot be compared with them (note 2).

## 2. Why vector search misses exact identifiers
- An embedding compresses a chunk into 1,024 numbers about its overall meaning. A rare token like `ERR_4021` or `ROLL-2024-117` has no meaning to encode, so it contributes little to the vector.
- Where this shows up:
  - product codes, error IDs, roll numbers, ticket numbers
  - names of people, functions, parameters, libraries
  - formulas and symbols, section references ("Table 3.2", "Article 21")
  - acronyms the model never saw
- The vector search returns chunks that are **about** error handling in general. The keyword search returns the one chunk that contains the exact string.
- The reverse: a user who asks "how do I stop the app from crashing when the input is wrong" shares no words with a chunk titled "Validation errors". Keyword search fails, and the vector search finds it. This is the Day 10 "find a document using words that never appear in it".
- My Day 9 task 6 (3 queries where both models failed): I check whether any of them was an exact-term query. If so, today is the fix.

## 3. The options
| Option | How it works | Good | Limits |
|---|---|---|---|
| **Postgres full-text search** | `tsvector` column (the text turned into normalised terms), `tsquery` for the query, a **GIN** index, `ts_rank` to order | same database as the vectors; the tenant filter is a normal `WHERE`; no new service | `ts_rank` is not full BM25 (it does not use how rare a word is across the corpus the way IDF does); few languages have stemmers |
| **`bm25s` / `rank-bm25`** | a Python library that builds a BM25 index in memory | real BM25, `bm25s` is fast; easy to experiment | the index lives in the app process; rebuilt when documents change; **tenant filtering is my job** |
| **Elasticsearch / OpenSearch** | a dedicated search engine with BM25, analyzers per language, filters | the most capable; scales | a new service to run and keep in sync with Postgres (awareness today) |

### Postgres full-text search in four lines
```sql
-- a generated column and an index (my sketch; the exact syntax goes in the Alembic migration)
ALTER TABLE chunks ADD COLUMN tsv tsvector
  GENERATED ALWAYS AS (to_tsvector('simple', text)) STORED;
CREATE INDEX chunks_tsv_idx ON chunks USING GIN (tsv);

SELECT id, ts_rank(tsv, q) AS score
FROM chunks, websearch_to_tsquery('simple', 'ERR_4021') AS q
WHERE tenant_id = :tenant_id AND tsv @@ q
ORDER BY score DESC LIMIT 50;
```
- The `WHERE tenant_id = ...` is in the query, the same rule as Day 10: isolation is **inside** the query, not applied afterwards.
- `'simple'` lowercases and splits on word boundaries with no stemming and no stop words. `'english'` stems ("running" to "run"), which helps English prose and can hurt identifiers.
- The `tsvector` is built from the same chunk text that I embed. If I add the contextual header (Day 11), I decide whether the keyword index includes it.

### The trap in that query: all words must match
`websearch_to_tsquery` joins the words with **AND**. That is right for `ERR_4021` and wrong for a whole question. On my 2,097 chunks (2026-11-25, read-only queries, text converted at query time without an index):
```
question: "How do I define a path parameter in FastAPI?"
websearch_to_tsquery('simple', ...)   -> 'how' & 'do' & 'i' & 'define' & 'a' & 'path' & 'parameter' & 'in' & 'fastapi'
websearch_to_tsquery('english', ...)  -> 'defin' & 'path' & 'paramet' & 'fastapi'

chunks matched:  simple, all words   ->   0
                 english, all words  ->  21
                 english, any word   -> 937
exact identifier 'response_model', simple  ->  36
```
- With `simple` there are no stop words, so "how", "do" and "a" all have to be in the chunk: **0 matches**, and the keyword list would be empty for a normal question.
- "Any word" (OR) matches far too much on its own, and then the ranking has to do the work.
- So the keyword retriever needs a decision about the query: `english` or `hindi` with AND, an OR query ordered by `ts_rank`, or the important terms only. I choose by measuring on my queries.

## 4. Tokenisation problems: Hindi and mixed-script text
- **PostgreSQL 16 does have a `hindi` configuration** (checked in my container with `select cfgname from pg_ts_config`). It stems Hindi words with `hindi_stem` and English words with `english_stem`. `simple` finds exact forms only:
```
to_tsvector('simple', 'किताब किताबें पढ़ाई।')  -> 'किताब':1 'किताबें':2 'पढ़ाई':3
to_tsvector('hindi',  'किताब किताबें पढ़ाई।')  -> 'किताब':1,2 'पढ़':3
search "किताब" in "किताबें":   hindi -> match      simple -> no match
```
- **Its limits:** it removed no Hindi stop words ("के", "है", "में" stayed), and the stemmer is rough ("के" became "क", "कैसे" became "कैस"). I measure it on real Hindi queries before I choose it.
- **Unicode normalisation (NFC)** must be applied the same way at indexing and at query time, or a word typed with a different byte sequence will not match.
- **The danda `।`** ends sentences; make sure it is not glued to the last word.
- **Hinglish is romanised Hindi** with free spelling ("fees", "fee", "fis"; "kya", "kia"). Keyword matching works on spelling, so recall falls. The vector model (multilingual, Day 9) helps here. This is one more reason for hybrid.
- **Identifiers are split in different ways.** What `to_tsvector('simple', ...)` really stored in my database:
```
'ERR_4021'        -> 'err':1 '4021':2
'response_model'  -> 'response':1 'model':2       (a query becomes 'response' <-> 'model': the two words side by side)
'user.id'         -> 'user.id':1                  (kept as one term, so searching only "user" will not find it)
'ROLL-2024-117'   -> 'roll':1 '-2024':2 '-117':3  (the numbers are read as negative numbers)
```
  That can match too much or too little. I test with the 5 exact-code queries and look at what was actually indexed.
- **Mixed scripts in one chunk** (English terms inside Hindi text) are common in textbooks; test them.

## 5. Keyword search and the other stages
- It returns a **ranked list of chunk IDs with a BM25-style score**. Alone it is just another retriever; the value comes from fusing it with the vector list (note 2).
- It must return the same shape as the vector retriever (chunk ID, rank, score), so that fusion and logging do not care which one produced it.
- Every result is tenant-filtered, so the tenant with zero documents gets an empty list (the Day 10 test) from this retriever too.

## 6. Mistakes to avoid
| Mistake | What happens |
|---|---|
| Keyword search without the tenant filter in the query | another tenant's chunk can appear: the Day 10 failure again |
| Using the `english` configuration on identifiers | `ERR_4021` and stemmed words behave unexpectedly |
| Comparing `ts_rank` with cosine scores | meaningless; use ranks (note 2) |
| Rebuilding an in-memory BM25 index per request | slow; build once, rebuild on change |
| Not testing Hindi and Hinglish | looks fine in English, fails for the real users |

## 7. What I need to remember
- Vector search finds meaning; keyword search finds exact terms; each fails where the other works.
- Postgres full-text search keeps tenant isolation in one query; `bm25s` gives real BM25 but moves filtering into my code.
- Tokenisation decides what "the same word" means, and it is the weak point for Hindi and identifiers.
