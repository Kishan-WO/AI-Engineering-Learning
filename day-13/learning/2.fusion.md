# Fusion

I now have two ranked lists for one query: one from the vector search, one from the keyword search. Fusion turns them into one list.

## 1. Why I cannot just add the scores
| | Vector search | Keyword search |
|---|---|---|
| Score | cosine similarity, roughly 0 to 1 | BM25 or `ts_rank`, an unbounded number |
| Meaning of "high" | depends on the embedding model | depends on the query length and the corpus |
| Same scale as the other? | no | no |

- A BM25 score of 14.2 and a cosine of 0.71 cannot be compared or added. Normalising them (min-max) is possible, but it depends on the other results in that list, so a list with one very strong hit squeezes all the rest.
- What both lists do give reliably is the **rank**: first, second, third.

## 2. Reciprocal Rank Fusion (RRF)
For every chunk, add up one term per list in which it appears:
```
RRF(chunk) = sum over lists of  1 / (k + rank_in_that_list)
```
- `rank` starts at 1. A chunk missing from a list adds nothing for that list.
- `k` is a constant, 60 by default in the original paper and in most libraries. It softens the gap between rank 1 and rank 2.
- Sort by the total, highest first.
- A chunk that appears in **both** lists gets two terms, so it rises above chunks that are first in only one list. Agreement of two different methods is evidence.
- Worked numbers are in `Notes/01`.

### Why it is the default
- **No score comparison:** only ranks are used.
- **Nothing to tune** to get a good start (`k = 60`).
- **Robust:** one list having a bad day does not ruin the result.
- **Simple:** a few lines of Python, easy to unit test with hand-computed examples.
- It extends to any number of lists: the **multi-query** of note 5 fuses one list per query variant with the same function.

### What it cannot see
- **Score magnitude:** a chunk that is a perfect keyword match (a huge gap over rank 2) gets the same weight as a rank-1 hit with a tiny lead.
- **List quality:** it treats both lists as equally trustworthy. For a query full of exact codes the keyword list deserves more weight; for a vague question the vector list does.
- **Ties:** two chunks can have the same total. Decide the tie rule (for example the better single rank) and keep it fixed so tests are stable.

## 3. Weighted fusion: awareness
- Multiply each list's contribution by a weight (`w_vector / (k + rank)` + `w_keyword / (k + rank)`), or normalise the scores and take a weighted sum.
- It can beat plain RRF when I know one retriever is better for my data, but the weights have to be tuned on a labelled set, and the best weights change when the corpus or the model changes.
- I start with plain RRF. I consider weights only if the Day 14 eval shows a gap and I have the data to tune on.

## 4. Practical details
- **How many candidates from each retriever?** More candidates (for example 50) give the fusion and the re-ranker more to work with and cost a little time. The number is a knob I vary and measure.
- **Same chunk, two lists:** match by the **chunk ID**; a chunk found by both is one row.
- **Keep the provenance:** for each fused result store the rank and score from each list (`vector_rank=3, keyword_rank=None`). Task 6 needs this to say which stage found the final top chunk.
- **Tenant filter:** both lists are already filtered; fusion cannot add a chunk that neither retriever returned, so it cannot leak.
- **Thresholds:** the Day 12 "nothing relevant" threshold was on cosine scores. An RRF score is only a function of ranks (with two lists of 50, the maximum is about `2/61`), so it says nothing about relevance in absolute terms. A query about a topic the corpus does not cover still gets a full ranked list. Options: apply the threshold to the **vector cosine score of the top hit before fusion**, or to the **re-ranker score** after (note 4). I decide and write it in `decisions.md`.

## 5. Mistakes to avoid
| Mistake | What happens |
|---|---|
| Adding raw BM25 and cosine scores | one list dominates by accident |
| Fusing only the top 5 of each list | little overlap, little benefit; fuse a longer list |
| Losing the per-list ranks | cannot tell which retriever helped (task 6) |
| Applying a cosine threshold to RRF scores | meaningless cutoff |
| Not fixing the tie rule | tests that sometimes fail |

## 6. What I need to remember
- Ranks are comparable across retrievers; scores are not.
- RRF adds `1/(k+rank)` per list, with `k = 60`, and rewards chunks found by both.
- It is blind to score magnitude and list quality: weighted fusion is the next step only if the eval asks for it.
- Keep the provenance of every fused result.
