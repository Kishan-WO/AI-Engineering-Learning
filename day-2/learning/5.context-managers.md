# `contextlib.contextmanager`

## The problem: setup and cleanup that must always happen
Some things need **cleanup even when something goes wrong**: close a file, release a lock, restore a setting, end a database transaction. The long way:

```python
f = open("data.txt", encoding="utf-8")
try:
    data = f.read()
finally:
    f.close()          # runs even if read() raises
```
The `with` statement does this for me:
```python
with open("data.txt", encoding="utf-8") as f:
    data = f.read()
# f is closed here, even if an exception happened inside the block
```
I have already used `with` for files and for `tempfile.TemporaryDirectory()` in the Day 1 tests.

## How `with` works: the protocol
An object works with `with` if it has two dunder methods:

| Method | Runs | Purpose |
|---|---|---|
| `__enter__(self)` | when the block starts | does the setup; its return value goes into `as x` |
| `__exit__(self, exc_type, exc, tb)` | when the block ends, **always** | does the cleanup; gets the exception details, or `None, None, None` if there was no error |

```python
class Opened:
    def __init__(self, name):
        self.name = name

    def __enter__(self):
        print(f"open {self.name}")
        return {"name": self.name}          # becomes `r` in `as r`

    def __exit__(self, exc_type, exc, tb):
        print(f"close {self.name}")
        return False                         # False/None: let any exception continue

with Opened("db") as r:
    print("using", r)
# open db
# using {'name': 'db'}
# close db
```
If `__exit__` returns a **truthy** value, the exception is **swallowed**. Return `False` or `None` unless hiding the error is the goal.

## `@contextmanager`: the same thing as a generator
Writing a class with two methods for every little case is heavy. `contextlib.contextmanager` turns a **generator with exactly one `yield`** into a context manager:

```python
from contextlib import contextmanager

@contextmanager
def opened(name):
    print(f"open {name}")              # setup: runs on entering the block
    resource = {"name": name}
    try:
        yield resource                 # the value handed to `as`; the with-block runs now
    finally:
        print(f"close {name}")         # cleanup: runs on leaving the block

with opened("db") as r:
    print("using", r)
```
It prints exactly the same as the class version. The code is split by the `yield`:

```
@contextmanager
def thing():
    ...setup...           <- __enter__
    try:
        yield value       <- value goes to `as x`; the with-block runs while paused here
    finally:
        ...cleanup...     <- __exit__
```
This reuses what I learnt about `yield`: the generator is **paused** at the `yield` while the `with` block runs, then **resumed** afterwards.

## What happens when the block raises
The exception is thrown back into the generator **at the `yield` line**:
```python
with opened("db") as r:
    raise ValueError("boom")
# open db
# close db                      <- the finally still ran
# ValueError: boom              <- then the exception continues
```
This is why the `yield` should sit inside `try`/`finally`. Without it:
```python
@contextmanager
def opened_badly(name):
    print(f"open {name}")
    yield {"name": name}
    print(f"close {name}")      # NEVER runs if the block raised, because the exception stops the generator at the yield
```
**Rule: put the `yield` in a `try`, and the cleanup in `finally`.**

## A real example: temporarily change something
```python
import os
from contextlib import contextmanager

@contextmanager
def working_directory(path):
    previous = os.getcwd()
    os.chdir(path)
    try:
        yield
    finally:
        os.chdir(previous)          # always restored

with working_directory("sample_docs"):
    print(os.listdir()[:3])
# back in the original folder here
```
This one yields nothing (`yield` with no value), so I use `with working_directory(...):` without `as`.

The `timer()` in daily task 2 follows the same shape: record something before the `yield`, and use it after the `yield`.

## Handling or hiding exceptions
Catching the exception **inside** the generator hides it from the caller:
```python
@contextmanager
def ignore_errors(*error_types):
    try:
        yield
    except error_types:             # a tuple of exception classes is allowed here
        pass                        # swallowed

with ignore_errors(KeyError):
    {}["missing"]
print("still running")              # no crash
```
To let the error through after cleaning up, either don't catch it, or `raise` again inside the `except`. The standard library already has this exact tool: `contextlib.suppress(KeyError)`.

## More tools in `contextlib`
| Tool | Purpose |
|---|---|
| `suppress(*errors)` | Ignore the listed exceptions in the block |
| `closing(obj)` | Call `obj.close()` at the end, for objects with a `close()` but no `with` support |
| `ExitStack` | Manage a variable number of context managers (for example, open every file in a list) |
| `nullcontext()` | A do-nothing context manager, for optional behaviour like `with (lock or nullcontext()):` |
| `redirect_stdout(f)` | Send `print` output somewhere else, handy in tests |
| `asynccontextmanager` | The async version (see below) |

## Several at once
```python
with open("a.txt", encoding="utf-8") as a, open("b.txt", "w", encoding="utf-8") as b:
    b.write(a.read())
```
Both close at the end, in **reverse** order: `b` first, then `a`. From Python 3.10 the managers can be wrapped in parentheses to span several lines.

## Comparing with JavaScript
| JavaScript | Python |
|---|---|
| `try { ... } finally { ... }` | `with` does the same job with less code |
| `using` declarations (newer, `Symbol.dispose`) | The closest feature, but `with` has existed for years |
| No built-in setup/cleanup block in older code | `with` is everywhere: files, locks, DB sessions, HTTP clients |

## Common mistakes
| Mistake | What happens |
|---|---|
| `yield` outside `try`/`finally` | Cleanup is skipped when the block raises |
| Two `yield`s | `RuntimeError: generator didn't stop` |
| No `yield` at all | `RuntimeError: generator didn't yield` |
| Returning a truthy value from `__exit__` | Exceptions are silently swallowed |
| Calling the function without `with`, e.g. `opened("db")` | Nothing runs; I just get a context manager object |
| Using `as` on a manager that yields nothing | The variable is `None` |
| Catching `Exception` inside the generator "just in case" | Hides real bugs from the caller |

## Where this comes back
- **Tests:** `tmp_path`, `monkeypatch` and `pytest.raises(...)` are context managers or fixtures built on the same idea.
- **Async (later today):** `async with httpx.AsyncClient() as client:` guarantees the connection pool is closed.
- **FastAPI (Day 3):** a database session dependency uses `yield` to open and close a session per request, and the app's startup and shutdown live in a `lifespan` context manager:
```python
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app):
    # startup: connect to DB, create the HTTP client
    yield
    # shutdown: close everything
```
- **Observability (Day 15):** wrapping each pipeline stage in a trace span (`with span("retrieve"):`).
