# Blocking the event loop, `asyncio.to_thread`, and `httpx.AsyncClient`

## 1. Why blocking is the biggest async mistake
The event loop is one thread. Any call that doesn't `await` holds that thread, and every other task stops, including timers, other requests and streams.

| Blocker | Why |
|---|---|
| `time.sleep(n)` | Sleeps the whole thread |
| `requests.get(...)`, reading a big file, a database driver without async support | They wait for I/O, but not through the loop |
| CPU work: parsing, hashing, big loops, embeddings | The thread is busy computing and never reaches an `await` |

## 2. What it looks like (measured)
Three jobs of 0.5 s each, with a "ticker" task running every 0.05 s to show whether the loop is alive:

| Version | Total time | Ticker ran | Longest freeze |
|---|---|---|---|
| `time.sleep` inside `async def` | **1.50 s** | **1 time** | the whole 1.5 s |
| `await asyncio.to_thread(blocking_job, i)` | **0.51 s** | 9 times | 0.07 s |

With `time.sleep`, the jobs ran one after another **and** the loop was frozen for the whole 1.5 seconds. In a web server every user would wait.

## 3. The fix: `asyncio.to_thread`
```python
def blocking_job(n):
    time.sleep(0.5)               # or requests.get(...), a file read, etc.
    return n

async def main():
    result = await asyncio.to_thread(blocking_job, 3)
    results = await asyncio.gather(*(asyncio.to_thread(blocking_job, i) for i in range(3)))
```
- It runs a **normal function** in a worker thread and gives me an awaitable. The loop stays free.
- Arguments go after the function: `to_thread(fn, a, b, key=value)`. I pass the function itself, not `fn()`.
- It works with `gather`, `TaskGroup`, `Semaphore` and `asyncio.timeout`.

| Case | Does it help? |
|---|---|
| Blocking I/O (old libraries, file reads, `requests`) | **Yes** |
| CPU-bound work | **No**, because of the GIL. Measured: 3 CPU jobs took 0.75 s through threads vs 0.60 s sequentially. It frees the *loop*, but the work isn't faster |
| CPU work that must go faster | `ProcessPoolExecutor` with `await loop.run_in_executor(pool, fn, arg)` |
| Cancelling a task that awaits it | The waiter is cancelled, but the **thread keeps running** to the end |

Order of preference: an **async library** first; if there isn't one, `to_thread`; for heavy CPU, processes.

## 4. `httpx.AsyncClient`
`httpx` is the standard async HTTP library, with an API close to `requests`.
```bash
uv add httpx
```

### One shared client
```python
import httpx

async def main():
    async with httpx.AsyncClient(base_url="https://api.example.com", timeout=10.0) as client:
        r = await client.get("/hello")
        print(r.status_code, r.json())
```
Why **one client for the whole program**:
- It keeps a **connection pool**, so repeated requests reuse open connections and skip the TCP/TLS handshake.
- Shared settings live in one place: `base_url`, `headers`, `timeout`, `auth`.
- `async with` closes the pool at the end. Afterwards `client.is_closed` is `True`, and using it raises an error.

Creating an `AsyncClient` inside every function works but is slow and wasteful. I build it once in `main` and pass it to the functions that need it.

Many requests at once use the same tools as before:
```python
responses = await asyncio.gather(*(client.get("/slow") for _ in range(3)))
# measured: 3 requests that each take 1 s finished in 1.02 s
```
I add a `Semaphore` to respect rate limits.

### Timeouts
`httpx` has a **default timeout of 5 seconds**. I should still set my own:
```python
httpx.AsyncClient(timeout=10.0)                              # same limit for each phase
httpx.AsyncClient(timeout=httpx.Timeout(30.0, connect=5.0))  # 30 s default, 5 s to connect
httpx.AsyncClient(timeout=None)                              # no limit (avoid)
await client.get("/slow", timeout=0.3)                       # override for one request
```
Four phases: `connect`, `read`, `write`, `pool` (waiting for a free connection). **`read` is the gap between chunks, not the whole response**, so a stream can run for minutes as long as chunks keep coming. LLM calls need a larger `read` timeout, because the model may think a while before the first byte.

Errors (measured):
```
ReadTimeout    -> TimeoutException -> TransportError
ConnectTimeout (connecting to a closed port on Windows timed out instead of refusing)
```
`TimeoutException`, `ConnectError`, `ReadError` and so on are all `TransportError`s, which are `RequestError`s. Catch `httpx.TimeoutException` for slowness, or `httpx.RequestError` for any network trouble. This is separate from `asyncio.timeout`, which limits a whole block.

### `raise_for_status`
A `404` or `500` is **not an exception** by default:
```python
r = await client.get("/missing")
print(r.status_code, r.text)              # 404 nope   <- no error raised

try:
    r.raise_for_status()                  # raises on 4xx and 5xx
except httpx.HTTPStatusError as e:
    print(e.response.status_code)         # 404
    print(e)                              # Client error '404 Not Found' for url '...'
```
Habit: call `r.raise_for_status()` right after every request. `e.response` still holds the body, which usually has the provider's error message.

| Problem | Exception |
|---|---|
| Network, DNS, timeout, connection | `httpx.RequestError` and subclasses |
| Server answered 4xx/5xx and I called `raise_for_status()` | `httpx.HTTPStatusError` |

Useful pieces: `r.status_code`, `r.json()`, `r.text`, `r.headers`, `r.content`. Request options: `json={...}`, `params={...}`, `headers={...}`.

### Streaming with `aiter_lines`
```python
async with client.stream("GET", "/stream") as response:
    response.raise_for_status()
    async for line in response.aiter_lines():
        print(line)
```
Measured: lines arrived about 0.1 s apart, as sent, not all at the end.

- `client.stream(...)` is used with **`async with`**, so the connection closes even if I `break`.
- `response.aiter_lines()` is an **async generator**. Others: `aiter_bytes()`, `aiter_text()`.
- Call `raise_for_status()` **before** reading the stream. An error body hasn't been read yet; use `await response.aread()` first to see its text.
- Streaming LLM APIs use **Server-Sent Events**: lines starting with `data: {...}`, ending with `data: [DONE]`.

```python
async def stream_chat(client: httpx.AsyncClient, payload: dict):
    async with client.stream("POST", "/v1/chat", json=payload) as response:
        response.raise_for_status()
        async for line in response.aiter_lines():
            if not line.startswith("data: "):
                continue
            data = line.removeprefix("data: ")
            if data == "[DONE]":
                return
            yield json.loads(data)
```

## Comparing with JavaScript
| JavaScript | Python |
|---|---|
| `fetch` | `httpx.AsyncClient().get(...)` |
| `fetch` does not throw on 404 | Same: use `raise_for_status()` |
| `response.ok` check by hand | `response.raise_for_status()` |
| `AbortSignal.timeout(ms)` | `timeout=` on the client or request |
| `for await (const chunk of response.body)` | `async for line in response.aiter_lines()` |
| `axios.create({ baseURL })` | `AsyncClient(base_url=...)` |
| `worker_threads` for blocking work | `asyncio.to_thread` |

## Common mistakes
| Mistake | What happens |
|---|---|
| `time.sleep` or `requests.get` inside `async def` | The whole loop freezes |
| `to_thread(fn())` instead of `to_thread(fn)` | Calls it now, then fails |
| Using `to_thread` to speed up CPU loops | No speed-up (GIL); use processes |
| New `AsyncClient` per request | No connection reuse; slow |
| Using the client after its `with` block | Error: client is closed |
| Forgetting `raise_for_status()` | A 404/500 body is parsed as good data |
| No timeout, or `timeout=None` | A hung server blocks a task forever |
| Default 5 s timeout for LLM calls | `ReadTimeout` on slow answers; raise `read` |
| Not using `async with client.stream(...)` | The connection stays open |
| Catching only `HTTPStatusError` | Network errors still crash the program |
| `r.json()` on an HTML error page | `JSONDecodeError` |
