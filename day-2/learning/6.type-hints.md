# Type hints

## The most important fact: Python doesn't enforce them
Type hints are **labels for humans and tools**. Python ignores them when the program runs:

```python
def add(a: int, b: int) -> int:
    return a + b

add("x", "y")      # 'xy'  <- no error at runtime
```
A separate tool, a **type checker** such as `mypy` or `pyright`, reads the hints and reports mistakes **before** the code runs:
```bash
mypy file.py
# error: Argument 1 to "add" has incompatible type "str"; expected "int"
```
That is the same relationship as TypeScript, with one difference: TypeScript needs a build step that strips the types, while Python runs the file as it is, hints included.

## 1. The basics
```python
name: str = "Asha"
count: int = 0
ratio: float = 0.5
active: bool = True

def greet(name: str, times: int = 1) -> str:
    return ("hi " + name + " ") * times
```
- `param: type` annotates a parameter, and `-> type` annotates the return value.
- A function that returns nothing is `-> None`.

## 2. Collections: `list[str]`, `dict[str, int]`
Put the type of the contents in square brackets:
```python
names: list[str] = ["a", "b"]
scores: dict[str, int] = {"asha": 90}
unique: set[int] = {1, 2}
point: tuple[int, int] = (3, 4)           # exactly 2 items
numbers: tuple[int, ...] = (1, 2, 3)      # any number of ints
matrix: list[list[int]] = [[1, 2], [3, 4]]
```
These lowercase forms work directly since Python 3.9. Older code imports `List`, `Dict` from `typing`, so I will see it, but I shouldn't write it.

For function parameters, prefer the **most general** type that works. `collections.abc.Iterable[str]` accepts a list, tuple, set or generator, while `list[str]` accepts only lists:
```python
from collections.abc import Iterable

def total_length(words: Iterable[str]) -> int:
    return sum(len(w) for w in words)
```

## 3. `X | None`: values that might be missing
```python
def find_title(doc_id: str) -> str | None:
    ...
```
`str | None` means "a string or `None`". It is the same as TypeScript's `string | null`. (Older code writes `Optional[str]`.)

The checker then **forces me to check before using it**. This is called narrowing:
```python
def shout(name: str | None) -> str:
    return name.upper()          # error: Item "None" of "str | None" has no attribute "upper"

def shout(name: str | None) -> str:
    if name is None:
        return ""
    return name.upper()          # fine: here the checker knows name is a str
```
`X | None` is **not** the same as "optional parameter". A parameter that can be left out needs a default value: `def f(x: str | None = None)`.

Any union works: `int | str`. Use `isinstance(x, int)` to narrow it.

## 4. `Any` and `object`
- `Any` turns checking **off** for that value. Anything goes, so it hides mistakes. Use it rarely.
- `object` means "any value, but I can't assume anything about it", so the checker makes me narrow it first.

## 5. `Literal`: only these exact values
```python
from typing import Literal

Role = Literal["user", "assistant", "system"]

def send(role: Role, content: str) -> None: ...

send("user", "hi")      # fine
send("admin", "hi")     # mypy error: "admin" is not one of the allowed values
```
It's the same as a TypeScript string-literal union (`"user" | "assistant"`). Use it instead of `str` when a field has a small fixed set of values.

## 6. `TypedDict`: a dict with known keys
```python
from typing import TypedDict, NotRequired

class Message(TypedDict):
    role: Literal["user", "assistant"]
    content: str
    name: NotRequired[str]          # this key may be missing

msg: Message = {"role": "user", "content": "hi"}
msg["content"]                      # checker knows this is a str
msg["colour"]                       # mypy error: no such key
```
- It's the equivalent of a TypeScript `interface` for an object.
- At runtime it is **just a plain `dict`**: nothing validates it. It only helps the checker.
- It fits JSON-shaped data that I don't want to turn into a class.

## 7. `Callable`: a function as a value
```python
from collections.abc import Callable

def apply(func: Callable[[int], int], value: int) -> int:
    return func(value)

apply(lambda n: n * 2, 5)        # 10
```
`Callable[[arg types...], return type]`:
| Hint | Meaning |
|---|---|
| `Callable[[int], int]` | takes one `int`, returns an `int` |
| `Callable[[str, int], bool]` | takes a `str` and an `int`, returns a `bool` |
| `Callable[[], None]` | takes nothing, returns nothing |
| `Callable[..., Any]` | any function at all |

This is TypeScript's `(x: number) => number`. For decorators that must keep the original signature, `ParamSpec` (see the decorators note) is used inside `Callable[P, R]`.

## 8. `Protocol`: "anything with these methods"
A `Protocol` describes a **shape**. Any class that has the right methods matches, **without inheriting** from it. This is called structural typing, and it is how TypeScript interfaces work:

```python
from typing import Protocol

class Searchable(Protocol):
    def search(self, keyword: str) -> list[str]: ...

class Index:                                    # does not inherit from Searchable
    def search(self, keyword: str) -> list[str]:
        return []

def run(source: Searchable) -> None:
    source.search("python")

run(Index())            # fine: Index has a matching search method
run(42)                 # mypy error: int has no attribute "search"
```
Compared with the `ABC` used for `Storage` in docstore:
| | `ABC` | `Protocol` |
|---|---|---|
| A class must inherit from it | Yes | No |
| Checked | At runtime (can't create an incomplete subclass) | By the type checker only |
| Style | "is a" | "can do" (duck typing, made checkable) |

Use an `ABC` when I own the classes and want shared code. Use a `Protocol` when I only care about what an object can do, especially for classes I don't control.

## 9. `Annotated`: a type plus extra information
```python
from typing import Annotated

Age = Annotated[int, "must be positive"]

def register(age: Age) -> None: ...
```
- To the type checker, `Annotated[int, ...]` is simply `int`.
- At runtime, Python **keeps the extra metadata** next to the type, and libraries can read it. That is how a library can say "this `int` must be greater than 0" using only a hint, for example `Annotated[int, Field(gt=0)]`.
- On its own it does nothing. Its value comes from a library that reads it.

## 10. Generics: types with a placeholder
A generic function works on **any** type but keeps track of which one:
```python
def first[T](items: list[T]) -> T:
    return items[0]

first([1, 2, 3])        # the checker knows the result is an int
first(["a", "b"])       # ...and here it is a str
```
`T` is a **type variable**: a blank that gets filled in at each call. Without it, I would have to write `-> Any` and lose the information.

Generic classes work the same way:
```python
class Stack[T]:
    def __init__(self) -> None:
        self._items: list[T] = []

    def push(self, item: T) -> None:
        self._items.append(item)

    def pop(self) -> T:
        return self._items.pop()

numbers = Stack[int]()
numbers.push(1)
numbers.push("x")       # mypy error: expected int
```
This `[T]` syntax is for Python 3.12 and later. Older code declares the variable first:
```python
from typing import TypeVar
T = TypeVar("T")
def first(items: list[T]) -> T: ...
```
`list[str]` and `dict[str, int]` are generics too: `list` is a generic class and `str` fills in its blank.

A type can also be named for reuse, in 3.12 and later:
```python
type Messages = list[Message]
```

## Comparing with TypeScript
| TypeScript | Python |
|---|---|
| `string[]` or `Array<string>` | `list[str]` |
| `Record<string, number>` | `dict[str, int]` |
| `string \| null` | `str \| None` |
| `"a" \| "b"` | `Literal["a", "b"]` |
| `interface Msg { role: string }` | `class Msg(TypedDict)` (plain dict) or a class |
| `(x: number) => string` | `Callable[[int], str]` |
| `interface` used structurally | `Protocol` |
| `function first<T>(x: T[]): T` | `def first[T](x: list[T]) -> T` |
| `any` | `Any` |
| `unknown` | `object` |
| Checked at build time by `tsc` | Checked on demand by `mypy` / `pyright` |

## Common mistakes
| Mistake | What happens |
|---|---|
| Expecting the hints to stop bad input at runtime | They don't; only a checker (or a validation library) catches it |
| Using plain `list` where `list[str]` is meant | The checker treats the contents as unknown |
| Writing `-> str` on a function that can return `None` | The checker reports it; write `-> str \| None` |
| Using `Any` to silence an error | Hides real bugs |
| Using `List`, `Dict`, `Optional` from `typing` in new code | Works, but is the old style |
| Forgetting `None` checks on a `X \| None` value | `AttributeError` at runtime; the checker would have caught it |
| Annotating `dict` when I mean a fixed structure | `TypedDict` or a class says more |
