# I/O-bound vs CPU-bound, the GIL, and `concurrent.futures`

## 1. Two kinds of "slow"
A program is slow because it is either **waiting** or **working**:

| | I/O-bound | CPU-bound |
|---|---|---|
| The program spends its time | **Waiting** for something outside: network, disk, database | **Calculating**: using the CPU flat out |
| The CPU is | Mostly idle | Busy at 100% on one core |
| Examples | HTTP requests, LLM API calls, reading many files, database queries | Parsing a huge file, hashing, image or video work, computing embeddings locally, big loops |
| What makes it faster | Doing **other waiting at the same time** | Using **more CPU cores** |

**Quick test:** if the program is slow but the CPU graph is nearly flat, it's I/O-bound. If one core is pegged, it's CPU-bound.

Almost everything in AI engineering that calls an API is **I/O-bound**: the program sends a request, then waits seconds for the answer. That's the reason concurrency pays off so much there.

## 2. The GIL, at a practical level
CPython (the standard Python) has a **Global Interpreter Lock**: **only one thread can run Python code at any moment**, even on a 12-core machine.

Three practical consequences:

1. **Threads do not speed up CPU-bound Python code.** Four threads take turns on one core.
2. **Threads do speed up I/O-bound code.** A thread that is waiting for the network **releases the GIL**, so another thread can run in the meantime.
3. **To use several cores, use several processes.** Each process is a separate Python with its own GIL.

Other things to know:
- Libraries written in C, such as NumPy, often release the GIL during heavy calculations, so threads can help there.
- The GIL does **not** make code thread-safe. `counter += 1` is several steps (read, add, write), and two threads can interleave inside it and lose an update. Shared changes still need a `threading.Lock`.
- Recent Python versions have an experimental "free-threaded" build without the GIL. My installed Python 3.14.2 is the normal build, and I checked that the GIL is on. Everything below applies to the normal build.

## 3. `concurrent.futures`: one simple API for both
`concurrent.futures` gives threads and processes **the same interface**, so switching between them is a one-word change:

| | `ThreadPoolExecutor` | `ProcessPoolExecutor` |
|---|---|---|
| Runs tasks in | A pool of threads (shared memory) | A pool of separate processes |
| Good for | I/O-bound work | CPU-bound work |
| Start-up cost | Tiny | Noticeable (a new Python per worker) |
| Data passing | Direct (same memory) | Copied between processes (must be picklable) |

### `map`: the simplest way
```python
from concurrent.futures import ThreadPoolExecutor
import urllib.request

def fetch(url: str) -> int:
    with urllib.request.urlopen(url, timeout=10) as response:
        return len(response.read())

urls = [...]                                   # many URLs

with ThreadPoolExecutor(max_workers=8) as pool:
    sizes = list(pool.map(fetch, urls))        # results come back in the SAME ORDER as urls
```
- `with` waits for all tasks to finish and shuts the pool down (a context manager, as in the context-managers note).
- `max_workers` is how many tasks run at once.
- `pool.map(fn, items)` is the parallel version of `map(fn, items)`.
- If one task raised an exception, it is re-raised **when I reach that item** in the results.

### `submit` and `as_completed`: handle results as they arrive
```python
from concurrent.futures import ThreadPoolExecutor, as_completed

with ThreadPoolExecutor(max_workers=8) as pool:
    futures = {pool.submit(fetch, url): url for url in urls}    # future -> url
    for future in as_completed(futures):                         # fastest finishes first
        url = futures[future]
        try:
            size = future.result()                               # returns the value or re-raises
        except Exception as error:
            print(url, "failed:", error)
        else:
            print(url, size)
```
- `submit(fn, *args)` starts one task and returns a **`Future`**: a placeholder for a result that isn't ready yet.
- `future.result()` waits for the result. If the task raised, `result()` **raises the same exception here**. Exceptions never disappear, but they only surface when I ask.
- `future.result(timeout=5)` gives up waiting after 5 seconds (it raises `TimeoutError`, but the task itself keeps running).
- `as_completed` gives results in **finish order**, unlike `map`, which keeps input order.
- A `Future` also has `done()`, `cancel()` (only works if the task hasn't started) and `exception()`.

### Processes for CPU work
```python
from concurrent.futures import ProcessPoolExecutor

def heavy(n: int) -> int:
    total = 0
    for i in range(6_000_000):
        total += i * i
    return total

if __name__ == "__main__":                       # REQUIRED on Windows
    with ProcessPoolExecutor(max_workers=4) as pool:
        results = list(pool.map(heavy, range(4)))
```
The `if __name__ == "__main__":` guard is mandatory on Windows. Each worker process **re-imports the file**, and without the guard it would start more pools, endlessly.

## 4. What I measured on this machine
Each case ran on Python 3.14.2 with 12 CPU cores:

| Task | Sequential | 8 threads | 4 processes |
|---|---|---|---|
| **I/O-bound**: 8 tasks, each waiting 0.5 s | 4.00 s | **0.51 s** | not tried |
| **CPU-bound**: 4 tasks of 6 million loop steps | 1.16 s | 1.11 s | **0.50 s** |

Reading it:
- **I/O:** 8 threads cut 4 s to 0.5 s, about 8 times faster, because all 8 waits overlapped.
- **CPU with threads:** 1.11 s vs 1.16 s. **No real gain**: that's the GIL at work.
- **CPU with processes:** 0.50 s, over twice as fast. It isn't a full 4 times faster because starting four Python processes and passing data costs time. The more work each task does, the smaller that overhead is in comparison.

## 5. Choosing the right tool
```
What is slow?
 |
 +-- waiting on network / disk / API
 |     +-- a handful of tasks ........... ThreadPoolExecutor
 |     +-- hundreds or thousands ........ asyncio
 |
 +-- heavy Python calculation
       +-- ProcessPoolExecutor (or a C library like NumPy)
```
| Situation | Use |
|---|---|
| 20 API calls, simple code | `ThreadPoolExecutor` |
| Thousands of concurrent requests, streaming, precise control | `asyncio` |
| Parsing or hashing 1,000 big files | `ProcessPoolExecutor` |
| Tiny tasks (microseconds each) | Neither: the overhead is larger than the work |
| Order of results matters | `map`; use `as_completed` if it doesn't |

Rate limits matter for APIs: `max_workers` is also the **limit on simultaneous requests**, so set it with the provider's limits in mind.

## 6. Pitfalls
**Processes**
- Arguments and return values are **pickled** (copied between processes). Lambdas, open files and database connections can't be pickled, and passing huge objects is slow.
- Memory is **not shared**: changing a global in a worker changes only that worker's copy.
- Start-up cost means they only pay off for tasks that take a meaningful time, roughly tens of milliseconds or more.

**Threads**
- Memory **is shared**, so shared changes need a lock:
```python
import threading

lock = threading.Lock()
counter = 0

def work() -> None:
    global counter
    for _ in range(100_000):
        with lock:                 # a context manager again
            counter += 1
```
- Exceptions in a worker are invisible until `result()` is called. A `submit` whose future is never looked at fails silently.
- `ThreadPoolExecutor` can't be interrupted instantly with Ctrl+C: running tasks must finish.

## Comparing with JavaScript
| JavaScript / Node | Python |
|---|---|
| Single thread plus an event loop; I/O overlaps automatically | Threads or `asyncio` give the same overlap, but I choose |
| `Promise.all(urls.map(fetch))` | `pool.map(fetch, urls)` |
| `Promise.allSettled` | `as_completed` with `try`/`except` around `result()` |
| `worker_threads` for CPU work | `ProcessPoolExecutor` |
| A `Promise` | A `Future` |

## Common mistakes
| Mistake | What happens |
|---|---|
| Using threads for CPU-bound code | No speed-up (the GIL) |
| Using processes for tiny tasks | Slower than sequential, because of the start-up cost |
| No `if __name__ == "__main__":` with processes on Windows | Errors or an endless spawn of processes |
| Passing a lambda or a connection to a process pool | `PicklingError` |
| Never calling `result()` | Exceptions are silently lost |
| Setting `max_workers` to 100 for an API with a rate limit | `429 Too Many Requests` |
| Updating a shared variable from threads without a lock | Lost updates, random wrong results |
| Assuming `as_completed` keeps order | Results come back in finish order |
| Measuring once | Timing varies; run it a few times |
