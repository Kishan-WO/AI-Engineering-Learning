# Pydantic v2

Pydantic uses type hints **at runtime** to validate and convert data. Plain hints are only checked by `mypy`, while a Pydantic model actually rejects bad data when the program runs. The closest JavaScript tool is **Zod**.

Every example below was run with Pydantic 2.14.

```bash
uv add pydantic
```

## 1. `BaseModel`: a class that validates itself
```python
from pydantic import BaseModel

class Student(BaseModel):
    name: str
    age: int
    email: str | None = None
    tags: list[str] = []

s = Student(name="Asha", age="21")
print(repr(s))      # Student(name='Asha', age=21, email=None, tags=[])
print(type(s.age))  # <class 'int'>
```
Three things happened:
- Each field is declared with a type hint, like a dataclass.
- The string `"21"` was **converted** to the integer `21`. Pydantic's default mode is **lax**: it converts when the conversion is safe (`"21"` to `21`), and refuses when it isn't.
- Fields with no default (`name`, `age`) are **required**.

A plain mutable default like `tags: list[str] = []` is safe here: Pydantic copies it for every instance, so there is no shared-list bug. (Unlike a function default or a plain class attribute.)

**Gotcha:** `email: str | None` with no `= None` is **still required**. It means "required, but may be `None`". Write `= None` to make it optional.

## 2. `ValidationError`: all the problems at once
```python
from pydantic import ValidationError

try:
    Student(name="Asha", age="abc", tags="x")
except ValidationError as e:
    print(e.error_count())     # 2
    print(e)
```
Output:
```
2 validation errors for Student
age
  Input should be a valid integer, unable to parse string as an integer [type=int_parsing, input_value='abc', input_type=str]
tags
  Input should be a valid list [type=list_type, input_value='x', input_type=str]
```
Pydantic collects **every** error, not just the first one. For code, use `e.errors()`, which returns a list of dicts:
```python
e.errors()[0]
# {'type': 'int_parsing', 'loc': ('age',), 'msg': 'Input should be a valid integer, unable to parse string as an integer', 'input': 'abc', 'url': '...'}
```
| Key | Meaning |
|---|---|
| `loc` | Where the problem is: `('age',)`, or `('items', 2, 'name')` for nested data |
| `msg` | Human-readable message |
| `type` | Machine-readable code such as `int_parsing`, `missing`, `string_too_short` |
| `input` | The bad value that was supplied |

`ValidationError` is a subclass of `ValueError`, so a broad `except ValueError` also catches it.

## 3. `Field`: constraints, defaults and descriptions
```python
from typing import Literal
from pydantic import BaseModel, Field

class Enquiry(BaseModel):
    name: str = Field(min_length=2, max_length=50)
    budget: int = Field(gt=0, le=1_000_000, description="Budget in INR")
    course: Literal["python", "ai"] = "python"
    phone: str
```
Common `Field` options:
| Option | Applies to | Meaning |
|---|---|---|
| `gt`, `ge`, `lt`, `le` | numbers | greater than, greater or equal, less than, less or equal |
| `min_length`, `max_length` | strings, lists | length limits |
| `pattern` | strings | must match a regular expression |
| `default` | any | the default value |
| `default_factory` | any | a function that builds the default (`list`, `dict`) |
| `description` | any | text for documentation and for the JSON schema |
| `alias` | any | the key name in incoming data |

Bad input shows exactly which rule failed:
```python
Enquiry(name="R", budget=0, course="java", phone="123")
```
```
('name',)   String should have at least 2 characters   string_too_short
('budget',) Input should be greater than 0             greater_than
('course',) Input should be 'python' or 'ai'           literal_error
```
`Literal` from the type-hints note now **actually rejects** `"java"` at runtime.

## 4. `field_validator`: my own rules and cleaning
For rules `Field` can't express, add a validator:
```python
from pydantic import field_validator

class Enquiry(BaseModel):
    name: str = Field(min_length=2, max_length=50)
    phone: str

    @field_validator("phone")
    @classmethod
    def clean_phone(cls, v: str) -> str:
        digits = "".join(c for c in v if c.isdigit())
        if len(digits) != 10:
            raise ValueError("phone must have 10 digits")
        return digits

Enquiry(name="Ravi", phone="98765-43210").phone     # '9876543210'
```
Rules for validators:
- Put `@classmethod` **under** `@field_validator(...)`.
- It **must return the value**, cleaned or not. Forgetting `return` makes the field `None`.
- To reject, `raise ValueError("message")`. Pydantic wraps it into a `ValidationError` with type `value_error` and my message.
- By default it runs **after** Pydantic's own type check (`mode="after"`), so `v` is already a `str`. Use `mode="before"` to clean the raw input first.
- One validator can cover several fields: `@field_validator("phone", "alt_phone")`.

For a rule involving several fields at once (for example `end > start`), use `@model_validator(mode="after")`.

## 5. Config: strictness and cleaning
```python
from pydantic import ConfigDict

class Enquiry(BaseModel):
    model_config = ConfigDict(str_strip_whitespace=True, extra="forbid")
    name: str
```
| Setting | Effect |
|---|---|
| `str_strip_whitespace=True` | Trim spaces from every string, so `"  Ravi "` becomes `"Ravi"` |
| `extra="forbid"` | An unknown key is an error (`extra_forbidden`). The default is `"ignore"`, which silently drops it |
| `strict=True` | No conversion: `"1"` for an `int` is an error (`int_type`) |

By default, `age=1.5` for an `int` field fails with `int_from_float`, because the conversion would lose information.

## 6. Creating models from data: `model_validate`
Calling `Student(**data)` works, but **`model_validate`** is the standard way to validate a dict that came from outside (JSON, a request, an LLM):
```python
Enquiry.model_validate({"name": "Ravi", "budget": 10, "phone": "9876543210"})
Enquiry.model_validate_json('{"name": "Ravi", "budget": 10, "phone": "9876543210"}')
```
- `model_validate(dict)` validates a dict.
- `model_validate_json(str)` parses JSON text **and** validates it in one step (faster than `json.loads` followed by `model_validate`).

## 7. Getting data out: `model_dump`
```python
e = Enquiry(name="  Ravi ", budget="5000", phone="98765-43210")

e.model_dump()
# {'name': 'Ravi', 'budget': 5000, 'course': 'python', 'phone': '9876543210'}

e.model_dump_json()
# '{"name":"Ravi","budget":5000,"course":"python","phone":"9876543210"}'
```
Useful options:
```python
s.model_dump(exclude_none=True)         # drop fields that are None
s.model_dump(exclude={"tags"})          # drop specific fields
s.model_dump(include={"name", "age"})   # keep only these
```
The old v1 names `.dict()`, `.json()` and `.parse_obj()` are deprecated. If a tutorial uses them, it is out of date.

## 8. `model_json_schema()`: the schema to send to an LLM
```python
import json
print(json.dumps(Enquiry.model_json_schema(), indent=2))
```
```json
{
  "properties": {
    "name":   {"maxLength": 50, "minLength": 2, "title": "Name", "type": "string"},
    "budget": {"description": "Budget in INR", "exclusiveMinimum": 0, "maximum": 1000000, "title": "Budget", "type": "integer"},
    "course": {"default": "python", "enum": ["python", "ai"], "title": "Course", "type": "string"},
    "phone":  {"title": "Phone", "type": "string"}
  },
  "required": ["name", "budget", "phone"],
  "title": "Enquiry",
  "type": "object"
}
```
(Shortened to one line per property.) This is a standard **JSON Schema**. The type hints, the constraints, the `Literal` choices, the defaults and the `description` all end up in it.

**Why it matters for LLMs:** to get structured output, I give the model this schema as the shape its answer must follow, then validate the reply with the same class:

```
 Pydantic model --model_json_schema()-->  LLM (told: "answer in this shape")
       ^                                        |
       +-------- model_validate_json(reply) ----+
                 ValidationError -> send the error back and retry
```
- **One class** defines the schema, the validation and the Python object, so they can never drift apart.
- Write good `description=` text on fields: the model reads it as instructions.
- LLMs sometimes return wrong types, missing fields or invented values, so always validate the reply. Pydantic says exactly what was wrong, which can even be fed back to the model.

## Comparing with JavaScript
| Zod / TypeScript | Pydantic |
|---|---|
| `z.object({ name: z.string() })` | `class M(BaseModel): name: str` |
| `.min(2).max(50)` | `Field(min_length=2, max_length=50)` |
| `.refine(...)` / `.transform(...)` | `@field_validator` / `@model_validator` |
| `schema.parse(data)` | `Model.model_validate(data)` |
| `schema.safeParse(data)` returns `{ success }` | `try`/`except ValidationError` |
| `zod-to-json-schema` | `Model.model_json_schema()` (built in) |
| `z.infer<typeof schema>` | The class itself is the type |

## `BaseModel` vs `@dataclass` vs `TypedDict`
| | `TypedDict` | `@dataclass` | `BaseModel` |
|---|---|---|---|
| Validates at runtime | No | No | **Yes** |
| Converts types (`"21"` to `21`) | No | No | **Yes** |
| JSON schema | No | No | **Yes** |
| Weight | Plain dict | Light | Heavier |

Use a dataclass for internal data I already trust, like the `Document` in docstore. Use `BaseModel` where data **crosses a boundary**: user input, an HTTP request, a file, an LLM reply.

## Common mistakes
| Mistake | What happens |
|---|---|
| Using v1 names (`.dict()`, `.parse_obj()`, `@validator`) | Deprecated warnings or errors; use `model_dump`, `model_validate`, `field_validator` |
| Forgetting `@classmethod` under `@field_validator` | An error when the class is defined |
| A validator without `return` | The field becomes `None` |
| `x: str \| None` without `= None` | Still a required field |
| Catching only the first error | `ValidationError` holds all of them; loop over `e.errors()` |
| Trusting lax conversion for IDs or money | `"1e3"`, `True` and similar can pass as numbers; use `strict=True` when it matters |
| Mutating a model and expecting re-validation | Assignments aren't validated unless `validate_assignment=True` |
| Assuming extra keys raise | They are silently ignored unless `extra="forbid"` |
| Using Pydantic for trusted internal data | Extra overhead for no benefit |

## Practice
1. Write the `Student` model, create it with `age="21"`, and check the type of `age`. Then try `age="abc"` and print `e.errors()`.
2. Write the `Enquiry` model with the `phone` validator and call it with five different messy phone formats.
3. Make `email` optional and confirm that the model without `= None` still requires it.
4. Print `Enquiry.model_json_schema()` and find where each constraint appears. Add a `description=` to a field and see it show up.
5. Turn on `extra="forbid"` and send a dict with an unknown key.
6. Validate a list of dicts in a loop, collect the valid models, and print a summary of the `type` values from all the errors (use a `Counter`).
7. Nest one model inside another (for example `Course` inside `Enquiry`) and look at the `loc` of an error in the inner model.
8. Write a model for the `Document` from docstore (`id`, `title`, `text`, `source`, `tags`, `created_at`) and compare it with the dataclass.
