# `asyncio` vs the Node event loop

## 1. The same idea as Node
Node and `asyncio` both work the same way:
- **One thread** runs everything.
- When a task has to wait (network, timer, disk), it **hands control back** to an event loop.
- The loop runs another task in the meantime, then comes back when the first one's wait is over.

This is **cooperative multitasking**: tasks switch only at points where they choose to wait. There are no threads to lock, and the GIL is not a problem, because only one piece of code runs at a time.

| | Node.js | Python `asyncio` |
|---|---|---|
| The event loop | **Always there.** Node starts it for me | **I start it** with `asyncio.run(...)` |
| Calling an `async` function | **Starts running immediately**, up to its first `await` | **Does nothing.** It only creates a coroutine object |
| `await` | Used inside `async` functions | The same, and **required** to get the result |
| Forgetting `await` | The promise still runs, I just get a promise back | The code **never runs**, and Python prints a warning |

## 2. `async def` and coroutines
```python
import asyncio

async def fetch(name: str, delay: float) -> str:
    print(f"  start {name}")
    await asyncio.sleep(delay)          # a non-blocking wait
    print(f"  end   {name}")
    return name.upper()
```
Calling a coroutine function does **not** run the body:
```python
coro = fetch("a", 0.1)
print(type(coro).__name__)              # coroutine
# nothing was printed by fetch: its body has not started
```
`coro` is a paused recipe. It runs only when someone **awaits it** or **schedules it** on the event loop. **Coroutines do nothing until awaited or scheduled.**

## 3. `await`: explicit, and the only switching point
```python
result = await fetch("a", 0.1)          # runs the body, waits, gives the return value
```
`await` does two things:
1. **Runs** the coroutine (or waits for a Task or Future) until it finishes, and gives back its result.
2. While waiting, **lets the event loop run other tasks**.

Rules:
- `await` is only allowed **inside an `async def`**. In a normal function it is a `SyntaxError`.
- Control switches to other tasks **only at an `await`**. Code that runs for a long time without one blocks everything.
- I can await coroutines, **Tasks** and **Futures**.

## 4. Starting the loop: `asyncio.run`
```python
async def main() -> None:
    result = await fetch("a", 0.1)
    print(result)

asyncio.run(main())                      # creates the loop, runs main() until done, closes the loop
```
- Called **once**, at the very top of the program.
- It takes a **coroutine object** (`main()` with parentheses), not the function itself.
- Calling it while a loop is already running raises `RuntimeError: asyncio.run() cannot be called from a running event loop`. Inside async code, use `await`.

## 5. Awaits in a row run one after another
```python
async def main():
    for n in "abc":
        await fetch(n, 0.5)              # each finishes before the next starts
```
```
  start a / end a / start b / end b / start c / end c      1.54s
```
This is **sequential**. The concurrency does not come from `async`; it comes from **scheduling several things at once**.

## 6. Scheduling: `gather` and `create_task`
**`asyncio.gather`** runs several coroutines concurrently and waits for all (like `Promise.all`):
```python
results = await asyncio.gather(fetch("a", 0.5), fetch("b", 0.5), fetch("c", 0.5))
```
```
  start a / start b / start c / end a / end b / end c      0.51s ['A', 'B', 'C']
```
**0.51 s instead of 1.54 s**, and results come back in the order given.

**`asyncio.create_task`** schedules one coroutine in the background and returns a `Task` straight away:
```python
task = asyncio.create_task(fetch("bg", 0.3))
print("task created, doing other work")      # prints first
await asyncio.sleep(0)                        # gives the loop a chance to start the task
result = await task                           # wait when I need the answer
```
The task does not start at `create_task`. It starts the next time the current task **hits an `await`**. I keep a reference to the task, because a task nobody refers to can be garbage collected before it finishes.

| Way | Result |
|---|---|
| `await coro` | Runs it now, and I wait for it |
| `create_task(coro)` | Runs it in the background; I `await` the task later |
| `gather(c1, c2, ...)` | Runs them all at once and waits for all |

## 7. Forgetting `await`
```python
async def main():
    fetch("forgot", 0.1)                  # no await
```
```
RuntimeWarning: coroutine 'fetch' was never awaited
```
Nothing ran. In Node a forgotten `await` still runs the function. In Python it does nothing at all except warn. I treat that warning as an error.

## 8. Never block the loop
The loop is one thread, so a blocking call freezes **every** task:
```python
async def bad(n):
    time.sleep(0.5)                       # blocks the whole loop
    return n

await asyncio.gather(bad(1), bad(2), bad(3))
# 1.51s   instead of 0.51s
```
| Blocking (freezes the loop) | Non-blocking (use inside `async def`) |
|---|---|
| `time.sleep(1)` | `await asyncio.sleep(1)` |
| `requests.get(...)` | an async client such as `httpx.AsyncClient` |
| Huge file reads, CPU-heavy loops | `await asyncio.to_thread(fn, ...)` |

Debug mode finds blockers: run `python -X dev file.py` (or `asyncio.run(main(), debug=True)`) and it logs any step that took too long, like `Executing <Task ... bad() ...> took 0.501 seconds`.

## 9. Sync and async do not mix freely
- An `async def` **can** call normal functions.
- A normal function **cannot** `await`. It can only start a loop with `asyncio.run(...)`.
- Async spreads upward: once a function awaits, its callers must be async too.

## Comparing with JavaScript
| JavaScript | Python |
|---|---|
| Event loop built in and always running | `asyncio.run(main())` starts it |
| `async function f() {}`; `f()` runs until the first `await` | `async def f()`; `f()` creates a coroutine and **runs nothing** |
| `await p` | `await coro` |
| `Promise.all([...])` | `await asyncio.gather(...)` |
| A promise that is already running | `asyncio.create_task(...)` |
| Top-level `await` in modules | No: wrap it in `async def main()` and call `asyncio.run` |
| Forgetting `await` gives a promise | Forgetting `await` gives an unrun coroutine and a `RuntimeWarning` |
| A blocking loop freezes Node | The same: `time.sleep` in a coroutine freezes everything |

## Common mistakes
| Mistake | What happens |
|---|---|
| Calling `fetch(...)` without `await` | Never runs; `RuntimeWarning: ... was never awaited` |
| `asyncio.run(main)` instead of `asyncio.run(main())` | `ValueError`: needs a coroutine, not a function |
| Awaiting in a `for` loop and expecting concurrency | Runs one by one (1.54 s in the test) |
| `time.sleep` or `requests.get` inside `async def` | The loop freezes (1.51 s in the test) |
| Calling `asyncio.run` inside async code | `RuntimeError` |
| Using `await` in a normal `def` | `SyntaxError` |
| Creating a task and never keeping or awaiting it | It may be garbage collected, or its error ignored |
| Expecting `create_task` to start the task instantly | It starts at the next `await` |

## Practice
1. Write `fetch(name, delay)`, call it without `await`, print its type and read the warning.
2. Run three `fetch` calls with `await` in a row, then with `gather`. Time both.
3. Use `create_task` for two coroutines. Put a `print` before and after each `await` and predict the order before running.
4. Replace `asyncio.sleep` with `time.sleep` in `fetch`, run `gather`, compare the time, then run with `python -X dev`.
5. Try `asyncio.run(main)` without parentheses and read the error.
6. Write a normal `def` that uses `await` and read the `SyntaxError`.
7. Make one coroutine in a `gather` raise an exception and see what happens to the others.
8. Use `await asyncio.to_thread(time.sleep, 0.5)` in three tasks and compare with the blocking version.
