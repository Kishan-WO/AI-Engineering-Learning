# The RAG pipeline

On Day 9 I built semantic search over a corpus and called it "the retrieval part". RAG (retrieval-augmented generation) is the whole path from a file on disk to an answer with a source. Today covers the first half of that path.

## 1. The steps
```
OFFLINE (ingestion, runs once per document)
  load -> parse -> clean -> chunk -> embed -> store

ONLINE (query, runs on every question)
  retrieve -> augment -> generate
```
| Step | What happens | Output |
|---|---|---|
| Load | get the bytes: an upload, a URL, a folder | raw file |
| Parse | turn the file into text and structure | text with headings, tables, page numbers |
| Clean | remove what is not content: headers, footers, page numbers, broken hyphens | clean text |
| Chunk | cut the text into pieces that can be found and read alone | a list of chunks with metadata |
| Embed | one vector per chunk (Day 9) | vectors |
| Store | write chunk text, metadata and vector in the database (Day 10) | rows in `chunks` |
| Retrieve | embed the question, find the nearest chunks (Day 10; improved on Day 13) | top-k chunks |
| Augment | put the chunks in the prompt with IDs (Day 12) | a grounded prompt |
| Generate | the LLM answers from the context and cites it (Day 12) | answer with citations |

## 2. Offline against online
| | Offline (ingestion) | Online (query) |
|---|---|---|
| When | when a document arrives or changes | when a user asks |
| Time budget | minutes are fine | the user is waiting: seconds |
| Failure handling | retry later, show a status | answer with a clear error now |
| Runs in | a background worker | the API request |
| Cost | paid once per document | paid on every question |
| Who is affected by a mistake | every future question that needs this document | one answer |

The consequence: I can afford slow, careful, expensive work offline (a better parser, an LLM to add context to each chunk) because it is paid once. I cannot afford it online.

## 3. Where quality is usually lost
The first instinct when an answer is bad is to change the model or the prompt. In practice the cause is usually earlier:
1. **Parsing:** a table became a stream of numbers with no headers, two columns were read as one, a scanned page gave no text at all. The information is gone before the first embedding.
2. **Chunking:** the answer is split across two chunks, or a chunk is so large that its vector is an average of five topics.
3. **Retrieval:** the right chunk exists but is not in the top k (Days 12 and 13).
4. **Generation:** the model ignores or misreads good context. This is the last place to look, not the first.

A rule that follows: when a RAG answer is wrong, look at the retrieved chunks first. If the right text is not in them, no prompt can fix it. (Day 15 builds the tracing to do this properly.)

## 4. Garbage in, garbage out, in numbers I can check
- If the parser loses a table, retrieval recall for questions about that table is **0%** for any embedding model, any k.
- This is why the plan puts parsing and chunking before retrieval tuning: the later days can only recover what is in the `chunks` table.
- Day 9's chunks were sections cut by heading. They were good enough to compare two embedding models. They were not tested against tables, scans or long sections, and today's PDFs are the test.

## 5. What I need to remember
- Ingestion is an **offline job with its own failures**: it needs a status, retries and a way to run again safely (note 4).
- Every later quality problem can be traced back to a stage. I keep the intermediate results (parsed text, chunks) so that I can look at them.
- The model never sees the PDF. It sees what my pipeline made of it.
