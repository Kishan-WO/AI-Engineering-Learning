# Chunking strategies

A chunk is the unit that is embedded, stored, retrieved and put in the prompt. One chunk gets one vector, so the chunk decides what the vector means and what the model gets to read.

## 1. Why chunk at all
- An embedding of a whole 30-page chapter is an average of everything in it. A question about one paragraph is not close to that average.
- The prompt has a token budget and costs per token (Day 4). Sending whole documents for every question is expensive and noisy.
- The embedding models have a maximum input length (Day 9). Longer text is cut off, which silently drops content.
- The goal: **a chunk that makes sense alone and is about one thing.**

## 2. The size trade-off
| | Too small (about 50 tokens) | Too large (about 2,000 tokens) |
|---|---|---|
| Context | a sentence without its subject ("It costs 500.") | enough context |
| Embedding | precise, but often vague or ambiguous | diluted: several topics in one vector |
| Retrieval | many near-identical hits, answer scattered | the right chunk is found, but with much noise around it |
| Prompt cost | low per chunk, but I need more chunks | high per chunk |
| Typical failure | the answer needs two chunks and only one is retrieved | the right sentence is in the chunk but the vector does not match the question |

- Common starting points are **200 to 500 tokens with 10 to 20% overlap**. These are starting points. The right size depends on my documents and questions, and I choose it with the eval (Days 12 and 14), not by habit.
- **Count tokens with the embedding model's tokenizer.** Hindi gives more tokens than English for the same length (Day 4), so 1,000 characters is a different chunk size in each language.
- Day 9's sections (cut by heading) had no size limit. Some were short, some long; I did not measure how that hurt.

## 3. The strategies
### 3.1 Fixed-size by tokens, with overlap
- Cut every N tokens; each chunk starts `overlap` tokens before the previous one ended.
- **Overlap** exists so that a sentence cut at a boundary appears whole in one of the two chunks. Cost: 10 to 20% more chunks and storage.
- Simple, fast, predictable, and blind to meaning: it cuts mid-sentence, mid-table and across headings.
- My Day 1 `chunk_words` was the same idea over words. This one counts tokens.

### 3.2 Recursive splitting
- Try the biggest separator first (a blank line = paragraph). If a piece is still larger than the limit, split it by the next separator (a line break, then a sentence end, then a space, then characters).
- Then **merge** small neighbours back together up to the limit.
- Respects paragraph and sentence boundaries when it can, and falls back to a hard cut when it must.
- **Separators must fit the language:** the Hindi sentence end is the danda `।`, not only `.`; the separator list needs both.
- It is the usual default, and the baseline to beat.

### 3.3 Structure-aware splitting
- Use the document's own structure: Markdown headings (`#`, `##`), PDF sections found by a layout parser, list items, code blocks, tables.
- Each section becomes a chunk (or several, if it is too long, split recursively **inside** the section).
- A table or a code block is **never split in the middle**; a table is one chunk, or split by rows with the header repeated (note 2).
- The heading path goes into the metadata (and into the header, 3.6).
- Best for documents that have real structure (docs, textbooks). Poor if the structure is wrong or absent.

### 3.4 Semantic chunking
- Split text into sentences, embed each (or small windows of them), and start a new chunk where the similarity between neighbouring sentences drops below a threshold.
- Chunks follow topic changes instead of a fixed length.
- Costs an embedding call per sentence at ingestion, and the threshold needs tuning. Results against recursive splitting are **mixed** in many published comparisons, so I measure it against recursive before adopting it. It is not one of today's three strategies.

### 3.5 Parent-child (small-to-big) retrieval
- Embed **small child chunks** (precise matching) but store a link to a **parent** (the section or a larger window). Retrieval finds the child and returns the parent to the model.
- Precision of small chunks, context of large ones.
- Needs a `parent_id` and a place for the parent text. Several children can share one parent, so deduplicate parents before building the prompt.
- This is one of the three possible fixes for the broken-table question (Day 12, task 5).

### 3.6 Contextual headers
- Before embedding, prepend the **document title and section path** to the chunk: `Fees and Refunds > Refund policy > Online courses` followed by the text.
- A chunk that says "the fee is 500" is ambiguous; with the header it says which fee.
- Store the raw text and the header separately: **embed the header and text, show the text** (or both) to the model. Keep the choice behind a flag so Day 12 can measure it (task 3).
- A heavier version has an LLM write a one-sentence context for each chunk (published as "contextual retrieval"). It costs an LLM call per chunk, paid once at ingestion. Awareness for now.

## 4. Which to use when
| Document | First choice | Reason |
|---|---|---|
| Markdown docs with headings | structure-aware, recursive inside long sections | headings are good boundaries |
| Textbook PDF with chapters and tables | structure-aware after a layout parser, tables as units | tables and sections carry the meaning |
| Plain text, transcripts, chat logs | recursive, or fixed with overlap | no structure to use |
| Many tiny FAQs | one chunk per question and answer | already the right unit |

## 5. Mistakes to avoid
| Mistake | What happens |
|---|---|
| Chunk size in characters, not tokens | uneven size across English and Hindi |
| Splitting a table or a code block | half an answer is retrieved (task 5) |
| No overlap, with fixed cuts | a fact cut at a boundary exists in no chunk |
| Overlap so large that the chunks are near-duplicates | the top 5 are the same text five times |
| Chunk larger than the embedding model's maximum input | the end is silently cut off |
| Losing the heading and page number | no citations, ambiguous chunks |
| Choosing the size by habit | no evidence; Day 12 and Day 14 give the number |

## 6. What I need to remember
- Chunking decides what one vector means. It is part of the quality of retrieval, not a preprocessing detail.
- The strategies differ in how much of the document's meaning they respect: fixed < recursive < structure-aware. The right one is found by measuring.
- Always keep the metadata (document, heading path, page, block type, position): it makes citations, contextual headers and parent-child possible.

## Quick check
- Why does overlap exist, and what does it cost?
- What does recursive splitting do when a paragraph is longer than the limit?
- Why must the separator list include `।` for Hindi?
- What does a contextual header add, and what do I embed and what do I show?
- In parent-child retrieval, what is embedded and what is returned?
