# Document parsing

Parsing turns a file into text the rest of the pipeline can use. For Markdown and plain text it is trivial. For PDFs it is the hardest step of ingestion, because a PDF stores where to draw characters on a page, not paragraphs, tables or reading order.

## 1. Why PDFs are hard
- A PDF is a list of drawing instructions: "put these glyphs at these coordinates". "Paragraph", "heading", "table cell" are not stored; a parser has to guess them from positions and font sizes.
- **Born-digital PDFs** (exported from Word or LaTeX) have a text layer. **Scanned PDFs** are pictures of pages with no text at all, or with a bad OCR layer.
- The same file can give very different text from different parsers. I check by reading the output, not by trusting the parser.

## 2. Plain text extraction: PyMuPDF and pypdf
| | PyMuPDF (`pymupdf`) | pypdf |
|---|---|---|
| Speed | fast (C library) | slower (pure Python) |
| Output | text, text blocks with coordinates, fonts, images | text |
| Tables | `page.find_tables()` in recent versions | no |
| Install | wheels, no system dependency | pure Python |
| Licence | AGPL or commercial: I check it before using it in a product | BSD |

- Both give text in the order they find it, which is wrong for **two-column** pages (left line, right line, left line...). PyMuPDF's block output with coordinates lets me sort blocks by column myself.
- Both are the fast first choice and fail quietly: the text comes out, but wrongly.

## 3. Layout-aware parsers
| Tool | Idea | Cost |
|---|---|---|
| Docling | runs layout and table models, outputs structured Markdown or JSON with headings, tables and reading order | slower, needs model downloads, runs well on CPU for small files |
| Unstructured | partitions a file into typed elements (title, narrative text, table, list item) | slower for the best strategies; some features are hosted |
| Marker | PDF to Markdown with models, good on books and papers | needs a GPU for speed (awareness only) |

- They are the answer when the PDF has tables, columns or figures, and the price is time per page. So a sensible plan is: **fast parser first, layout-aware parser for the files that need it**, with a rule that decides which (note 4).
- I check the current docs before I rely on an option or an API; these tools change often.

## 4. Tables
- **What naive extraction does:** the cells come out as a line of values in reading order, the header row is far from the rows it describes, and a merged cell breaks the alignment. A model cannot tell which number belongs to which column.
- **Table to Markdown (or HTML):** keep the grid. `| Year | Fee |` followed by rows is something the model reads well, and an embedding model sees the column names next to the values.
- **Keep the table in one chunk** when it fits (note 3); if it is too long, split by rows and **repeat the header row** in each piece.
- **Add a short caption or the nearest heading** to the table chunk: "Fee structure, Course A". Questions mention what the table is about, not its cell values.
- Task 5 breaks this on purpose: the table is cut in two and only one half is retrieved.

## 5. Scanned PDFs and OCR
- **Detect them:** extract the text of each page; if a page has almost no characters although it has an image, it is scanned. The threshold (for example fewer than 20 characters) is something I choose by looking at my files.
- **OCR fallback:** Tesseract (needs the language data: `hin` for Hindi, `eng` for English) or PaddleOCR. Quality drops on skewed scans, small print and mixed scripts.
- **A vision LLM** can read a page image and return Markdown, with good quality on tables and layout, at a cost per page and a risk of invented text. Use it for the pages OCR fails on, and keep the source page number.
- OCR text can contain errors that look fine ("rn" for "m"). The embedding still works roughly, but exact-match searches (Day 13) and citations suffer.

## 6. Hindi and mixed-script text
- Some older PDFs use **legacy Hindi fonts** that are not Unicode: extraction gives garbage characters even though the page looks right. I check the extracted text, not the rendering. The fix is OCR on that file.
- Normalise to **Unicode NFC** after extraction, so the same word always has the same bytes (this matters for hashes and for keyword search later).
- Tokenisation cost is higher for Devanagari (Day 4), so chunk sizes in tokens must be counted with the real tokenizer.

## 7. Cleaning
| Problem | Fix |
|---|---|
| Header and footer repeated on every page ("Chapter 3 | Science") | find lines that repeat on most pages, in the same position, and drop them |
| Page numbers inside the text | remove lines that are only a number; **keep the page number as metadata** |
| Words broken by a hyphen at a line end ("informa-\ntion") | join them when the next line starts in lower case; check against a word list for real hyphenated words |
| Hard line breaks inside a paragraph | join lines that do not end a sentence |
| Ligatures ("ﬁ") and odd spaces | Unicode normalisation (NFKC for the Latin ligature case, NFC for Hindi) |
| Lists and bullets as odd characters | map them to `-` |

I clean **conservatively**: a rule that removes real content (a heading that repeats on every page) hurts more than a leftover page number.

## 8. Keep structure as metadata
What the parser knows now cannot be recovered later. For every piece of text I keep:
- **Page number(s)** (for citations on Day 12)
- **Heading path** ("Chapter 3 > Light > Reflection") (for contextual headers, note 3)
- **Block type** (paragraph, table, list, code)
- **Source** (file name, URL), document title, **parser name and version**

## 9. What I need to remember
- A parser's output is a decision, not a fact. I read it, especially tables, columns and the first and last lines of each page.
- Use the cheapest parser that works for each file, and know the rule for when to escalate.
- Page numbers, headings and block types are the metadata that make citations and good chunks possible. I store them at parse time.

## Quick check
- Why does a PDF have no "paragraphs" or "tables" inside it?
- What does a two-column page look like after naive extraction?
- How do I tell a scanned page from an empty one?
- Why is a table kept as a grid, and what do I repeat when I have to split it?
- Why do I keep the page number as metadata and not in the text?
