# Ingestion engineering

A script that parses and embeds a folder works once on my laptop. A service has to accept files from users, run for minutes, survive failures, and be safe to run again. This note is about that second part.

## 1. Why a background worker
- Parsing a 100-page PDF, chunking it and embedding 300 chunks takes seconds to minutes. An HTTP request that waits for it times out and blocks a server process.
- `BackgroundTasks` in FastAPI (Day 3) run inside the API process: if the container restarts, the job is lost, and there is no status, retry or queue.
- A **job queue** with a separate worker fixes that: the API stores the file, **enqueues a job** and returns `202 Accepted` with a job ID. The worker takes jobs from Redis and runs them. The client polls a status endpoint.

| | ARQ | Celery |
|---|---|---|
| Style | async, small, Redis only | mature, sync-first, many brokers and features |
| Fits | an async FastAPI project with asyncio code and `httpx` | larger systems, scheduling, complex workflows |
| Retries | per job, configurable | per task, configurable |
| Cost to learn | low | higher |

The plan allows either. ARQ matches the async code I already have, **but its README says it is in maintenance-only mode** ([arq issue 510](https://github.com/python-arq/arq/issues/510), checked 2026-11-25). It is still a small way to learn the idea; for a service that has to live long, that weighs towards Celery or another maintained queue. I decide at the start of the build; the idea is the same in both.

ARQ's docs also warn that **a job may run more than once** (a job stays in the queue until it has succeeded or failed). So the job itself must be safe to repeat (section 3).

- The worker is **a new service in Docker Compose** using the same image as the API with a different command, and `redis` is already in the file from Day 3.
- **Pass the file id or path to the job, never the bytes.** Redis is not a file store.
- **Tenant:** the job carries the `tenant_id` the API took from the authenticated user (Day 3). The worker never reads a tenant from the request body, and every row it writes has that tenant.

## 2. Job status
A table, `ingestion_jobs` (my sketch):
| Column | Meaning |
|---|---|
| `id`, `tenant_id`, `document_id` | who and what |
| `status` | `queued`, `running`, `succeeded`, `failed` |
| `stage` | `parse`, `clean`, `chunk`, `embed`, `store` (where it is, or where it failed) |
| `error` | a short readable message, not a stack trace for the user |
| `parser_version`, `chunker_version`, `embedding_model` | what produced the result (section 4) |
| `chunks_written`, timestamps | what happened and how long it took |

`GET /ingest/{job_id}` returns this for the user's own tenant only: another tenant's job ID returns 404, like the documents (Day 3).

## 3. Idempotency: running again changes nothing
Why it matters: jobs are retried, users upload the same file twice, and I will re-ingest the whole corpus after every parser or chunker change. If a second run of the same input adds rows, the table fills with duplicates and every search returns the same text several times.

Three tools make a run safe to repeat (details in `Notes/01`):
1. **Content hash of the file** (SHA-256 of the bytes): the `documents` table already has a unique `(tenant_id, content_hash)`. A file with a hash that already exists is **not processed again**. The response points to the existing document.
2. **A deterministic chunk ID:** computed from things that identify the chunk, for example `hash(document_id + pipeline_version + chunk_position + chunk_text)`. The same input gives the same ID, so the store **upserts** (insert or update by ID, Day 10) and a repeat run overwrites instead of duplicating.
3. **Job-level deduplication:** ARQ lets me give a job an explicit ID (`_job_id`). A second enqueue with that ID is refused (`enqueue_job` returns `None`) while the first is queued or running, **and also while its result is still stored**; results are kept for 3,600 seconds by default. So with an ID made only from the document, a real re-ingest within that hour would be silently skipped. The ID has to include what changed (the pipeline version), or the result must not be kept (`keep_result=0`). I also check for the `None`.

Proof for task 6: ingest the corpus, count rows, ingest again, count again, compare the IDs and the hash of all chunk texts. The numbers must be identical.

## 4. Versioning: re-ingest when the pipeline changes
The same file gives different chunks when the parser, the chunker settings or the embedding model change. Unchanged bytes do not mean unchanged results.
- Store a **pipeline version** with every chunk: `parser`, `parser_version`, `chunker`, `chunk_size`, `overlap`, `header_option`, `embedding_model`.
- A document is up to date only if its stored version equals the current one. A version bump marks documents stale and queues them for re-ingestion.
- **Replace without a gap:** do the delete and the insert in **one transaction** (or switch an "active version" pointer). Inside one transaction the order cannot create a gap: other sessions see the old rows until the commit, and a failure rolls the delete back. A gap appears only if I commit the delete on its own. With my table, **the delete has to come before the insert**, because of `UNIQUE (document_id, chunk_index)` (`Notes/01`, section 4). Embedding happens **before** the transaction, so it stays short.
- A new embedding model means re-embedding everything (Day 10); the full-corpus switch with two indexes is the blue/green idea of Day 21.

## 5. Batching embeddings and rate limits
- Send many chunk texts per embedding request (a batch), not one call per chunk. The API has a maximum batch size and a maximum number of tokens per request; I read the current limits in the provider docs.
- Handle **429** with the Day 2 `@retry` (backoff and jitter) and limit concurrency with a **semaphore** so that several jobs together do not exceed the provider's rate.
- **Never embed the same text twice:** a cache keyed by `hash(model + text)` saves cost when documents share text or when I re-ingest after a change that did not touch the chunk (Day 21 comes back to this).
- Count the tokens and the cost of every ingestion run and write them to the job row (Day 6 habits).

## 6. Failure handling
- **One bad document must not stop the batch.** Catch per document, set `failed` with the stage and a readable error, continue with the next.
- **Retry the transient** (network, 429, 5xx); **do not retry the permanent** (a corrupt PDF, an unsupported type). The same rule as Day 6.
- **Resumable:** because of idempotency (section 3) a failed job can run again from the start and the result is correct. Writing a status per stage also shows where it stopped.
- **Limits on input:** maximum file size (20 MB from Day 3), page count and parse time, so one huge or malicious file cannot hold a worker.
- **URL ingestion** (task 1 allows a URL) needs care: allow only `http` and `https`, block private and local addresses (a server-side request forgery risk: a user must not make my server fetch internal services), set a timeout and a maximum download size, and store the final URL.

## 7. What I need to remember
- The API accepts and enqueues; the worker does the slow work; the status table tells the truth.
- A repeat run must change nothing: file hash, deterministic chunk ID, upsert.
- A pipeline version is part of the data. Changing the chunker means re-ingesting, and the new chunks replace the old without a gap.
- Per-document failure handling, retries only for transient errors, and limits on input.
