# Retrieval tuning

Day 10 gave me `POST /search`: the nearest chunks and their scores. Before they go into a prompt I decide how many to take, whether any are good enough, and whether they are repeating each other.

## 1. top-k
| | k too small | k too large |
|---|---|---|
| Evidence | the answer is in rank 6 and I never see it | all the evidence is present |
| Noise | little | many chunks that are about something else |
| Cost and latency | low | more input tokens on every question (Day 4 pricing) |
| Answer quality | "I don't know" when the answer exists | distraction: the model uses a wrong chunk, or the right one is lost in the middle (Day 20) |

- k is a number I **measure**, not guess. Day 9's recall@5 of 95% says the right document is usually in the top 5, but a question that needs two chunks needs both of them.
- A common pattern: **fetch more, keep fewer.** Retrieve 20, remove duplicates and weak hits, keep 5. The re-ranker of Day 13 makes this step much better.
- Day 20 plots quality against k = 3, 5, 10, 20, 40. Today I choose a sensible start (5) and note what I see.

## 2. Similarity thresholds and "nothing relevant found"
- Without a threshold, the search **returns the nearest k chunks** even for a question about a topic the corpus never mentions. The nearest chunks are simply the least far away. (It returns fewer only when the tenant has fewer chunks, or when an HNSW index scan drops them: on Day 10 a tenant with 3 chunks got 0 results when I forced the index, and 3 with `hnsw.iterative_scan = relaxed_order`. So an empty result does not always mean "nothing relevant".)
- A **threshold** says: if the best score is below T, there is no relevant evidence, so skip the LLM and answer "I couldn't find this in the material", or let the model refuse with the weak context.
- **A score has no meaning outside its model.** Cosine 0.55 is good for one embedding model and poor for another; the same model scores a short query differently from a long one. So T must be found with **my model and my data**.
- **From my own corpus (Day 10, `jina-embeddings-v3`):** the top result of "How do I define a path parameter in FastAPI?" scored **0.7603**. The top result of a Hindi question about CORS was the right page at only **0.5092**. A threshold of 0.55 would have refused that correct Hindi result. So my test questions for T must include Hindi and Hinglish.
- **The wording moves the score:** changing "define" to "declare" took the first result from 0.7603 to 0.7568 and swapped the 4th and 5th results.
- **How I find T:** run my answerable questions and my unanswerable questions, print the top score of each, and look at the two groups. If they separate, T goes between them. If they overlap (they usually do, a little), I choose which error I prefer:
  - T high: more false "I don't know" (annoying, safe)
  - T low: more answers built on weak evidence (the prompt must refuse, note 2)
- **Two layers, not one:** a threshold alone is not enough, because an unanswerable question can still retrieve a close but irrelevant chunk. The prompt's refusal rule (note 2) is the second layer.
- Hybrid fusion (Day 13) produces RRF scores that are rank-based and cannot be compared with a cosine threshold, so the threshold logic will need to change then.

## 3. Maximal Marginal Relevance (MMR): awareness
- Plain top-k can return five chunks that say almost the same thing, so the context is repetitive and misses other aspects of the question.
- **MMR** picks chunks one at a time: each next chunk should be relevant to the query **and** different from the ones already chosen. A weight (often called lambda) sets the balance between relevance and diversity.
- Costs a little compute over the candidate list and a parameter to tune. Worth it when the corpus has many near-duplicate passages; I measure before adding it.
- Day 9's near-duplicate detection already gives a first idea: 15 pairs at a threshold of 0.97 among 2,097 sections, 13 of them inside one page.

## 4. Chunks from the same section
- Neighbouring chunks of one section often all match: they share vocabulary. The top 5 can be 5 pieces of one page.
- Options:
  - **Cap per section or per document** (for example at most 2 chunks per section), then fill the rest from other sources.
  - **Merge adjacent chunks** into one block so the model reads them in order, with overlap removed.
  - **Parent-child** (Day 11): return the parent once, however many children matched.
- Order the final chunks sensibly: by document and position within it when they belong together, or by score. A scrambled order of one section is harder for the model to read.

## 5. What goes into the final context
```
question -> embed -> search (tenant filter) -> top 20
         -> drop below threshold -> dedupe / cap per section -> keep k
         -> number them [1]..[k] -> build the prompt (note 2)
```
Every stage is logged: the candidates, their scores, what was dropped and why. On Day 15 this becomes the trace that explains a bad answer.

## 6. Mistakes to avoid
| Mistake | What happens |
|---|---|
| A fixed k for every question | simple lookups pay for noise, multi-part questions starve |
| A threshold copied from a blog post | scores of another model; refuses everything or nothing |
| No "nothing found" path | the model gets 5 irrelevant chunks and writes a confident answer |
| Five chunks from one page | no variety, the real answer is in another document |
| Tuning on one question | I fix that question and break three others |

## 7. What I need to remember
- The search always returns something; deciding that it is not enough is my job.
- Thresholds are model-specific and found from data, and they are only the first layer of refusal.
- Fetch more than I need, then filter, deduplicate and cut to k.
