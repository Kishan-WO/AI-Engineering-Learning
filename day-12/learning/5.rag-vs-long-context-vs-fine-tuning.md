# RAG versus long context versus fine-tuning

Three ways to make a model answer about my material. They solve different problems, and picking the wrong one is expensive.

## 1. What each one is
| | RAG | Long context | Fine-tuning |
|---|---|---|---|
| How | search the corpus per question, put the best chunks in the prompt | put the whole corpus (or most of it) in the prompt | train the model on examples so the behaviour changes in its weights |
| What changes | the prompt | the prompt | the model |
| Knowledge lives in | my database | the prompt | the weights (unreliably) |
| Updating knowledge | re-ingest one document | edit the text | retrain |
| Sources and citations | natural (chunk metadata) | possible, but the model must find the place | not available |
| Per-user access control | filter in the query (tenants) | decide what to include per user | cannot be done inside the weights |

## 2. Long context
- **Good when** the corpus is small, stable and fits in the window with room for the question and the answer. Provider prompt caching (Day 6) makes a repeated large prefix cheaper and faster, and there is no retrieval step to get wrong.
- **Limits:**
  - **Cost and latency per question:** a cached prefix is cheaper, but it is still read on every call, and the first call (or a cache expiry) pays in full.
  - **Quality:** more context does not mean better answers; details in the middle get missed, and distraction grows (Day 20 measures it).
  - **Size:** the corpus has to fit. I count its tokens with the real tokenizer (Day 4) and compare with the model's window.
  - **Access control:** every user would see the same prefix, or I build different prefixes and lose the cache.
  - **Growth:** the corpus that fits today does not fit next year.
- My own corpus is 234 documents. Whether it fits is something I **measure** (the token count), not assume. One number I already have: Jina billed **1,270,018 tokens** to embed its 2,097 sections (Day 9). That is the embedding model's count, so the chat model's count will differ and I still have to run its tokenizer, but it shows the size: about 1.27 million tokens, which I compare with the window and the price per question.

## 3. RAG
- **Good when** the knowledge is large or changing, answers need citations, and users must see only their own data (tenants).
- **Costs:** an ingestion pipeline (Day 11), a vector store, retrieval quality to tune and evaluate (Days 13 and 14), and one more way to fail: the answer is not in the retrieved chunks.
- It adds knowledge **at question time**, and it can show where each claim came from.

## 4. Fine-tuning
- **Changes form, not knowledge:** tone, output format, jargon, a narrow task done well by a small model, lower cost or latency at high volume (the optional topic B).
- **A bad reason:** "the model does not know our documents." Fine-tuning does not reliably store facts, cannot cite, cannot forget a deleted document, and needs retraining when the facts change.
- It is the last option, after prompting, few-shot and RAG have been measured and found short.

## 5. The decision
| Situation | Choice |
|---|---|
| A 30-page policy that rarely changes, one user group | long context with caching, then check the cost per question |
| 200+ documents, updated weekly, citations required, many tenants | RAG |
| Answers must follow a strict house format, or a small model must classify queries cheaply | prompting and few-shot first, then fine-tuning if the numbers justify it |
| Needs both fresh knowledge and a special style | RAG for the knowledge, a prompt (or a fine-tune) for the style |
| Not sure | build the simplest option and measure it against the next one on the golden set (Day 14) |

They also combine: RAG over a long-context model with caching, or a fine-tuned small model as the generator in a RAG pipeline.

## 6. A cost sketch I can fill with my own numbers
```
Long context, per question  = corpus_tokens x cached_input_price  (+ question and answer tokens)
RAG, per question           = embedding of the question
                            + k x chunk_tokens x input_price
                            + rewrite call (if history)  + answer tokens
```
Prices and cache rules change (Day 4, Day 6): I read the current price table in the config, I do not copy numbers from a note. The point of the sketch is the shape: long context pays for the whole corpus on every question; RAG pays for k chunks.

## 7. What I need to remember
- Long context for small stable corpora; RAG for large, changing, cited, access-controlled knowledge; fine-tuning for form.
- "Fits in the window" is a measured fact, and "fits" does not mean "works better".
- Fine-tuning is not a way to add documents.
