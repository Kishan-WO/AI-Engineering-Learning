# Conversational RAG

On Day 4 I saw that a chat model forgets: each call needs the whole history. The same is true of the retriever, and it is worse, because the retriever only sees the text I give it.

## 1. The follow-up problem
```
User:  What is the refund policy for online courses?
Bot:   Online courses can be refunded within 7 days [1].
User:  What about the second one?     <- what is "the second one"?
```
- If I embed "What about the second one?", the vector has no topic. Retrieval returns noise, and the generation step (which has the history) may still guess an answer from memory, ungrounded.
- Other follow-ups with the same problem: "and for Hindi?", "why?", "give an example", "explain it simply", "compare them".

## 2. Rewrite to a standalone query
- A small, cheap LLM call (the Day 8 small model) turns the last question plus the recent history into **one question that makes sense alone**:
  `"What is the refund policy for the second online course, and how does it differ from the first?"`
- Retrieval uses the **rewritten** query. Generation shows the model the **history and the original question**, plus the new sources.
- The instruction for the rewrite:
  - use only what is in the history; **do not add facts or guess names**;
  - if the question is already standalone, return it unchanged;
  - keep the language of the question;
  - output only the query.
- **No history, no rewrite:** the first message skips the call (task 1 says "if history exists"). It saves a call and avoids a way to damage a good query.
- Send the last few turns, not all of them (Day 4: cost grows with history; also old turns confuse the rewrite).

## 3. How rewriting fails
| Failure | Example | Guard |
|---|---|---|
| Wrong referent | "the second one" resolved to the wrong item | log the rewrite; check cases by hand |
| Over-rewriting | adds details the user never asked for and narrows the search | "do not add information", compare with the original |
| Dropping the key term | the exact code or name disappears | keep quoted terms and IDs; compare tokens |
| Language drift | a Hinglish question rewritten in English | state the language rule, test on Hinglish |
| An extra call on every turn | +latency and +cost | skip when no history or the question is already standalone |

I log `original_query` and `rewritten_query` on every request. The Day 15 trace needs both, and the Day 13 query-transformation work builds on the same idea (there the goal is a better query, not only a standalone one).

## 4. Retrieve again, or reuse the previous context?
| Follow-up | Better to |
|---|---|
| A new fact or topic ("what about the fees?") | retrieve again |
| Same evidence, different form ("say it simply", "translate", "shorter") | reuse the previous sources |
| Drilling deeper into the same topic ("why?") | usually retrieve again (the answer may be in neighbouring chunks) |
| An ambiguous "what about X?" | retrieve again with the rewritten query |

- **Retrieving every turn is the simple and safe default.** Reusing saves a search and an embedding call but risks answering from sources that no longer fit.
- If I add reuse, a small classifier or a rule decides, and it is measured on a set of follow-ups, like the Day 8 router.
- Reused sources must still be **numbered and cited**, and the citation check still runs.
- A middle path: retrieve again and **add** the new chunks to the old ones, within the token budget (Day 20).

## 5. History in the prompt
- The history goes in as normal alternating messages (the Day 5 array); the sources go in the **current user message** or the system prompt, labelled for this turn only.
- Do **not** save old source blocks in the stored history: they are big and they go stale. Store the question, the answer and the citation list; rebuild the sources on each turn.
- Citation numbers restart on every turn. An answer from two turns ago saying `[1]` refers to that turn's sources, so I store the mapping with each assistant message.

## 6. Where this connects
- Day 5 gave me stored conversations (the history).
- Day 13 adds multi-query and HyDE (query transformation for **quality**).
- Day 19 adds **long-term memory** (facts across sessions), which is not the same as the rewrite of the current conversation.
- Day 20 decides how much history, how many sources and how much memory fit in the context budget.

## 7. What I need to remember
- A follow-up question is not searchable alone: rewrite it with the history, with a cheap model, only when there is history.
- The retriever gets the rewritten query; the generator gets the history, the original question and the new sources.
- Log both queries. Retrieve each turn unless a measured rule says otherwise.
