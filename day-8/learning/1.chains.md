# Chains: steps that feed each other

On Day 6 and 7 I built single calls: one prompt in, one answer out. Most real features need **several** calls in a row, where the answer of one call is the input of the next. That is a chain.

## 1. A deterministic pipeline: A, then B, then C
The order of the steps is fixed in my code. The model never decides what runs next.
```
message ──> extract facts ──> classify intent ──> draft a reply
            (structured)      (one label)         (free text)
```
- Each step has **one small job**, its own prompt (a registry file, Day 7), and can use a **different model**: a cheap one to classify, a better one to write.
- Each step is easier to write, to test and to measure alone than one huge prompt that does everything.
- The code is plain `await` calls in order. No framework is needed to run a chain.

```python
facts = await extract(client, Enquiry, message)          # step A
intent = await classify(client, facts.summary)           # step B
reply = await write_reply(client, facts, intent)         # step C
```

## 2. Pass structured output, not prose, between steps
The output of a step should be an **object my code can check**, not a paragraph the next step must re-read.
| Pass this | Not this |
|---|---|
| a Pydantic object (`Enquiry`, a label from an enum) | "Here is what I found: the student is ..." |
| only the fields the next step needs | the whole previous prompt and answer |

- Day 5's strict schema and Day 6's repair loop already give me valid objects, so every step can start from data that has been checked.
- Passing only what the next step needs keeps its prompt short (cheaper) and removes text that could confuse it, or carry an injection forward.

## 3. Validation gates between steps
A **gate** is a check that decides whether the chain may continue.
| Gate | Example | If it fails |
|---|---|---|
| Schema valid | Pydantic accepts the object | repair (ask again, max 2) or stop |
| Value makes sense | budget is between 0 and 10,000,000; a phone has 8 to 15 digits (Day 6 checks) | repair or stop |
| Label allowed | the label is one of the six categories | fall back to `other` or to a larger model |
| Confidence enough | the router is sure (see `2.routing.md`) | send to the large model |
| Safety | no instruction text in the output, nothing outside the allowed set | stop and return a safe answer |

A chain without gates passes a wrong answer straight into the next step, and the final answer looks confident even though step 1 was wrong.

## 4. Where chains fail
| Failure | What happens | What I do |
|---|---|---|
| **Error propagation** | a wrong label in step B makes step C write a confident, wrong reply | gates after each step; keep the checked object, not the raw text |
| **Compounding accuracy** | four steps that are each 95% right give about 0.95 x 0.95 x 0.95 x 0.95 = **81%** for the whole chain | fewer steps; measure the whole chain, not only each step |
| **Compounding latency** | each call is about 1 to 3 s, so five steps take 5 to 15 s before the user sees anything | run independent steps in parallel (`3.parallel-execution.md`); stream the last step |
| **Compounding cost** | five calls cost about five times one call | cheap models for the early steps; cache the stable prompts (Day 6) |
| **Retries multiply** | a retry in step 2 delays steps 3, 4 and 5 | a time budget for the whole chain, not only per call |
| **One step hides the cause** | the final answer is bad and I do not know which step caused it | log every step with the request id, the prompt version and the cost (the `llm_calls` table already does this) |

## 5. How I measure a chain
- Score the **final answer** on a labelled set (Day 7 way), and also each step's output where a label exists.
- Record tokens, cost and latency **per step** and in total.
- Change one step at a time and re-run the whole set: an improved step can still make the end result worse.
