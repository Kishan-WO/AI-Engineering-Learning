# Framework trade-offs: how to choose, and what each one is for

Frameworks promise speed. They also add abstractions, hidden prompts and a dependency that changes. I want to know what I get, and what I give up, before I build on one.

## 1. The positioning of each
| Option | What it is for | In one line |
|---|---|---|
| **Plain SDK** (what I use so far) | direct calls to the provider with my own code | maximum control, least magic |
| **LangChain** | many ready-made parts: model wrappers, loaders, tools, memory, vector stores | broad integrations, many abstractions |
| **LangGraph** | flows as an explicit graph with state, cycles, checkpoints and interrupts | explicit graphs and state, strong for agents |
| **LlamaIndex** | getting data into a model: loading, chunking, indexing, retrieval | retrieval- and data-centric |
| **Pydantic AI** | agents and tools whose inputs and outputs are Pydantic models | typed, Pydantic-native agents and outputs |
| **Haystack** | pipelines of components (retrieve, rank, generate) | pipeline-centric |
| **DSPy** | writing the task as a program and letting a tool tune the prompts against a metric | awareness: programmatic prompt optimisation |

Day 8 builds the same router flow in the plain SDK and then in **LangGraph** (or Pydantic AI), so I compare on my own code.

## 2. Four questions to judge any framework
| Question | What I look for |
|---|---|
| **Debuggability** | When an answer is wrong, can I see the exact prompt that was sent, the raw reply and the cost of each step? Is a stack trace readable, or buried under layers? |
| **Hidden prompting** | Does the library add its own instructions, tool descriptions or "fix the format" prompts that I did not write? They change behaviour and cost, and they are part of my prompt even if I never see them. |
| **Lock-in** | How much of my code uses the library's types, so leaving means a rewrite? Can I keep my own models, my own prompts (my registry) and my own logging? |
| **Speed of change** | Does it release breaking changes often? Will the example I copy today still run next month? Who maintains it? |

## 3. How to find hidden prompts and extra calls
This is the measurable part of the comparison:
- **Log every request that leaves the process** (the Day 6 accounting layer does this if the framework is made to use my client; otherwise a log of the raw HTTP body). Compare the prompt text I wrote with the text that was really sent.
- **Count the calls.** A framework "agent" can make 3 calls where my code made 1 (planning, formatting, retry).
- **Compare tokens and cost** per request for the same input: framework against plain SDK.
- **Check the defaults**: temperature, retries, max tokens, timeouts. They differ from mine.

## 4. What I compare in the Day 8 rebuild
| Measure | Plain SDK | Framework |
|---|---|---|
| Lines of code for the router flow | count | count |
| Debuggability | can I see each prompt, each reply, each cost? | the same question |
| Latency per request (median, p95) | measured | measured |
| Hidden prompts or extra calls | none by design | list them |
| Dependencies added | none new | list them, with the size of the install |
| Cost per request | measured | measured |
| What I can do only in one of them | | resume after a pause, a drawn graph, streaming steps |

## 5. When each makes sense
- **Plain SDK:** a small number of steps, a team that wants to read every line, strict cost and prompt control. This is my default, and the registry, accounting, retry and fallback layers I built are what a framework would otherwise supply.
- **LangGraph:** real graphs with cycles, pauses for people and resumable state; the explicit graph is the product.
- **LangChain:** a quick prototype using many integrations; be careful with the abstraction depth in production.
- **LlamaIndex or Haystack:** retrieval-heavy products, where loaders, chunkers and retrievers save the most time.
- **Pydantic AI:** typed agents with tools when I already model everything in Pydantic.
- **DSPy:** when I have a metric and a labelled set and want the prompts tuned automatically (an extension of the Day 7 measuring work).

## 6. A fair way to decide
1. Write the flow in plain code first, so I know what it should do.
2. Rebuild it in the framework, and run the **same labelled test set** through both.
3. Compare the table above, including what the framework changed in the prompts.
4. Choose the framework only if it gives something I would otherwise have to build (pause and resume, tracing, a shared graph) **and** I can see what it sends to the model.
5. Write the decision in `decisions.md`, with the numbers and the dependency cost.
