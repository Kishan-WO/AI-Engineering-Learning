# Routing: send each request to the cheapest thing that can handle it

A router looks at a request and decides **where it goes**: which prompt, which model, or which handler. Day 8's build is a router that sends easy requests to a small, cheap model and only the hard ones to a large model.

## 1. Why route
| Request | What it really needs |
|---|---|
| "fees?" | a cheap, fast model with a fees prompt |
| "when does the next batch start?" | a lookup, maybe no model at all |
| "I paid twice and my son's batch was moved without telling us, what are my options?" | a larger model, careful reasoning, maybe a human |

Using the large model for everything is simple and safe, and it costs the most and is the slowest. If most requests are easy, a router saves money **without** lowering quality, as long as it sends the hard ones to the large model.

## 2. Rule-based routing first: it is free
Before spending a model call on routing, try plain code:
| Rule | Example | Cost |
|---|---|---|
| Keywords and regular expressions | `fees`, `fee`, `EMI`, `installment`, `kitni` go to the fees handler | none |
| Exact commands or ids | `/help`, `ticket #402` | none |
| Language or length checks | an empty message, over 8,000 characters (Day 6 limits) | none |
| Known patterns | a greeting or "thanks" goes to a canned reply | none |

- Rules are fast, free, predictable and easy to test. They fail on messy language (typos, Hinglish, two topics).
- So: rules catch the **obvious** cases, a model router handles the rest, and the large model handles what the router is unsure about.

## 3. LLM routing: a small model classifies the intent
The classifier I measured on Day 7 is exactly this step. `classify_query` v2 on a small model gave 30/30 on my hard set at about $0.0000860 per call (336 input tokens, 1 output token).
```
message ──> [rules] ──hit──> specialised handler
              │ no hit
              └──> [small model: classify into 4 or 5 intents] ──> specialised prompt for that intent
                        │ unclear / low confidence
                        └──> [large model handles it directly]
```
- Keep the labels few (4 to 5) and give an escape label (`other` or `unclear`), as on Day 7.
- Each intent has its own **specialised prompt** (a registry file) that is short and focused, which makes the second call cheaper and better than one giant prompt for everything.

## 4. Confidence and fallback to the large model
A router must be allowed to say "I am not sure".
| Way to get a confidence | Notes |
|---|---|
| An `unclear` label | the simplest: the router has a label for "none of these fits" |
| A score field in the structured output (0 to 1) | models are often over-confident; check it against my test set before trusting it |
| Token probabilities (logprobs), where a provider offers them | more honest, not available everywhere |
| Disagreement between two cheap checks (rule vs model) | cheap and useful |

The rule: **below the threshold, or `unclear`, go to the large model.** The threshold is a number I choose from the test set: higher means more requests go to the large model (safer and dearer), lower means more savings and more risk.

## 5. Measuring the router
Two different things must both be measured:
1. **Router accuracy**: does it pick the right intent? (exact match on a labelled set, as on Day 7). Look at the confusion table: which intent is mistaken for which, and above all which **hard** requests the router sends down the cheap path by mistake.
2. **End-to-end quality and cost**: compare "router" with "always the large model" on the same requests:
   - quality: the final answers are as good (scored by labels or a rubric);
   - cost per request and latency, on average and at the 95th percentile;
   - the share of requests that went to the large model.

A rough cost model (symbols, not real prices):
```
router cost per request = router call
                          + (share handled by the small model)  x small handler call
                          + (share sent to the large model)     x large call
```
The saving is large when most requests are easy **and** the router call is cheap compared with a large call. The plan's target is about **40% lower cost with no quality loss**. If the router's own call costs a lot, or too many requests escape to the large model, there is no saving.

## 6. Mistakes to avoid
| Mistake | What happens |
|---|---|
| Measuring only router accuracy | a router can be accurate and still send the hard 10% to the cheap path |
| A test set of easy requests | the router looks perfect and fails in production (Day 7 lesson) |
| No escape label or threshold | every uncertain request is forced down a path |
| Routing before trying free rules | paying a model call for `/help` |
| A router prompt that changes without a measurement | the savings or the quality quietly change |
| Forgetting that the router call itself costs money and time | no net saving |
