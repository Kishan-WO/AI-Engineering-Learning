# Graphs and state machines: when a straight line is not enough

A chain goes A, B, C. Some flows need to **branch**, **loop**, **retry** or **pause for a person**. For those, the flow is a **graph**: pieces of work (nodes) connected by rules about what comes next (edges), with a shared **state**.

## 1. Why some flows need more than a chain
| Need | Example |
|---|---|
| **Branch** | the router sends a message to the fees handler or the complaint handler |
| **Cycle** | the model drafts a reply, a checker rejects it, the model redrafts (until it passes or after 3 tries) |
| **Retry with a change** | the first answer fails validation, so go back one step with the error message (my Day 6 repair loop is a tiny cycle) |
| **Pause** | a refund above a limit needs a human to approve before the flow continues |
| **Long-running** | the flow must survive a restart and carry on where it stopped |
| **Several actors** | an agent that decides to call a tool, reads the result, and decides again |

A pure chain cannot loop or wait. Writing these in plain `while` loops and `if` statements works for small flows; it gets hard to read, test and resume as they grow.

## 2. LangGraph concepts
LangGraph is a library that models a flow as a graph. The ideas, without the API details:
| Concept | Meaning | Plain-Python picture |
|---|---|---|
| **State** | one typed object (often a `TypedDict` or a Pydantic model) holding everything the flow knows: the message, the intent, the draft, the attempts | a dict that every step reads and updates |
| **Node** | a function that takes the state and returns changes to it | one step: `classify`, `draft_reply`, `check` |
| **Edge** | "after this node, run that node" | the order of two steps |
| **Conditional edge** | a function looks at the state and **chooses** the next node | `if intent == "fees": ... else: ...` |
| **START / END** | the entry and exit points | start and return |
| **Checkpointer** | saves the state after each step under a thread id | a database row per step, so a flow can be resumed or replayed |
| **Interrupt** | stops the graph at a node and waits for outside input (a person), then resumes | "pause until the manager clicks approve" |
| **Reducer** | the rule for how a node's update is **merged** into a state field (for example append to a list) | `messages += new_messages` |

A router as a graph:
```
START ──> classify ──┬── fees ──────> fees_handler ──┐
                     ├── schedule ──> schedule_handler ┤
                     ├── complaint ─> complaint_handler ┼──> END
                     └── unclear ───> large_model ─────┘
```
The branching after `classify` is a conditional edge that reads `state["intent"]`.

## 3. Human-in-the-loop
- An **interrupt** pauses the graph at a chosen point and returns control to the caller. The state is saved by the **checkpointer**.
- Later, the caller **resumes** the same thread with the person's answer (approve, reject, an edited value) and the graph continues from where it stopped.
- This needs a checkpointer: without saved state there is nothing to resume.
- Typical uses: approval before an action with side effects (a refund, an email), or asking the user a question the flow cannot answer alone.

## 4. Streaming intermediate steps
A graph can report progress while it runs, so the user sees something before the end:
| What is streamed | Use |
|---|---|
| the state after each step ("values") | debugging, a progress bar |
| only the update each node made ("updates") | showing "classified as fees", then "drafting" |
| the model's tokens as they are written ("messages") | typing effect of the final answer, the Day 5 SSE idea |

My `/chat` already streams tokens as Server-Sent Events (Day 5); a graph's progress events can be sent through the same mechanism, with an event name per kind (`step`, `token`, `done`, `error`).

## 5. A state machine in plain code (the same idea, no library)
```python
state = {"message": text, "intent": None, "draft": None, "attempts": 0}
step = "classify"
while step != "end":
    if step == "classify":
        state["intent"] = await classify(state["message"])
        step = "draft"
    elif step == "draft":
        state["draft"] = await draft(state)
        state["attempts"] += 1
        step = "check"
    elif step == "check":
        step = "end" if passes(state["draft"]) or state["attempts"] >= 3 else "draft"
```
- State, steps and a "what is next" rule are all there. A library adds **a checkpointer, interrupts, streaming and tooling** around this.
- That is why Day 8 builds the router first in **plain SDK code**, then **rebuilds it in a framework** and compares: lines of code, how easy it is to debug, latency, and what the framework adds behind my back (`5.framework-trade-offs.md`).

## 6. When a graph is worth it
| Use plain code when | Use a graph library when |
|---|---|
| a fixed chain, or one small loop | many branches, several cycles, or an agent loop |
| no pause, no resume | pauses for humans, resuming after a restart |
| one person reads and debugs it | a team needs a shared picture (it can be drawn) |
| the flow rarely changes | the flow changes often and needs tracing |
