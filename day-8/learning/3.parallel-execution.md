# Parallel execution: fan out, limit, and survive a failure

Calls that do **not depend on each other** can run at the same time. Waiting for ten summaries one after another takes ten times as long as waiting for the slowest one.

## 1. Fan-out with `asyncio.gather`
```python
results = await asyncio.gather(*(summarise(doc) for doc in docs))
```
- `gather` starts all the coroutines together and returns the results **in the same order** as the inputs.
- Ten calls that take 2 seconds each finish in about 2 seconds, not 20.
- Only independent calls fit this. If step B needs the answer of step A, they stay in sequence (`1.chains.md`).
- This works because an LLM call is mostly **waiting** for the network (Day 2: I/O-bound work), so one thread can wait for many calls at once.

## 2. Map-reduce over many documents
The classic shape for "summarise ten documents, then combine":
```
doc 1 ──> summary 1 ┐
doc 2 ──> summary 2 ┤
...                  ├──> combine all summaries ──> one final summary
doc 10 ─> summary 10┘
      MAP (parallel)              REDUCE (one call)
```
- **Map:** the same prompt on each document, in parallel.
- **Reduce:** one call that gets the summaries (not the full documents) and combines them.
- The reduce step must **fit in the context window**. With many documents, reduce in rounds: combine groups of 5, then combine the results.
- Keep each summary in a **fixed, short shape** (a Pydantic object, or a length limit), so the combine prompt is small and predictable.

## 3. Concurrency limits
"All at once" has a ceiling:
| Limit | Where it comes from |
|---|---|
| Provider rate limit | the hosted free tier allows 15 calls per minute (Day 6); a burst of 25 calls gave 429 errors |
| Provider concurrency or tokens per minute | 250K tokens per minute on the same tier |
| My own server | too many open connections, memory |
| Cost | ten parallel calls cost the same as ten sequential ones, but arrive faster |

The tools I already have (Day 6): `LimitedClient` limits calls in flight per backend (a semaphore) and calls per minute, and `RetryingClient` waits and retries a 429. For a map step I can also limit **my own fan-out**:
```python
gate = asyncio.Semaphore(4)

async def limited(doc):
    async with gate:            # at most 4 summaries running at once
        return await summarise(doc)

results = await asyncio.gather(*(limited(d) for d in docs), return_exceptions=True)
```

## 4. Partial failures
With ten calls, the chance that one fails is real. `gather` has two modes:
| Mode | What happens when one call raises |
|---|---|
| default | the first exception is raised to the caller; the other calls keep running in the background, and their results are lost |
| `return_exceptions=True` | every call finishes; a failed call's slot in the result list holds the **exception object** instead of a value |

The second mode is the one for map-reduce, followed by an explicit decision:
```python
ok = [r for r in results if not isinstance(r, Exception)]
failed = [d for d, r in zip(docs, results) if isinstance(r, Exception)]
```
| Policy | When |
|---|---|
| **Retry the failed ones** once (Day 6 retry already retried the transient errors) | the usual first step |
| **Continue without them** and say so ("summary of 9 of 10 documents; document 7 failed") | the answer is still useful |
| **Stop** if too many fail (for example more than 2 of 10) | a result built on too little would mislead |
| **Never** silently drop a failure | the user would think all ten were read |

- Python 3.11+ also has `asyncio.TaskGroup`: if one task fails, the **others are cancelled** and an `ExceptionGroup` is raised. That fits "all or nothing" work; `gather(return_exceptions=True)` fits "best effort".
- A **timeout** per call and one for the whole fan-out stops a stuck call from holding the chain (`asyncio.timeout`).
- Make the failure testable: a fake client that raises on one chosen document (the Day 6 `FakeProvider` can do this) proves the policy works without a real outage.

## 5. What to measure
- Wall time: parallel vs sequential, for the same ten documents.
- Total tokens and cost (the same, plus the combine call).
- How many calls retried or failed, and what the result said about them.
- The effect of the concurrency limit: with a limit of 4 the ten calls take about three "waves", not one.

## Mistakes to avoid
| Mistake | What happens |
|---|---|
| `gather` with no limit on a hundred documents | 429 errors, or memory and connection problems |
| Default `gather` and one failure | the other nine results are thrown away |
| Ignoring failed items in the reduce step | a summary that claims to cover everything |
| Sending full documents to the combine call | the context window overflows |
| Parallelising steps that depend on each other | wrong results, or nothing to run |
| No timeout | one stuck call holds the whole fan-out |
