# The model landscape (overview)

This is an overview only. **Model names, sizes and prices change every few months**, so I never copy specifics from a note: I check the provider's current documentation.

## 1. Closed (API) models
I use these through a paid API. The provider keeps the weights private.

| Family | Maker | Notes |
|---|---|---|
| **Claude** | Anthropic | Several tiers of different size |
| **GPT** | OpenAI | Several sizes, plus separate reasoning models |
| **Gemini** | Google | Several tiers, strong at long input and multimodal |
| **Mistral** | Mistral AI | Also has open-weight models |
| **Cohere** | Cohere | Focus on business uses such as search and retrieval |

- **Pros:** the strongest models, no hardware to run, always updated, simple API.
- **Cons:** pay per token, data goes to a third party, the model can change or be retired, rate limits, dependence on the provider.

## 2. Open-weight models
The weights are published, so I can download and run them myself.

| Family | Maker |
|---|---|
| **Llama** | Meta |
| **Qwen** | Alibaba |
| **DeepSeek** | DeepSeek |
| **Gemma** | Google |
| **Mistral** (open ones) | Mistral AI |

- **Pros:** data stays with me, no per-token fee, I can tune or modify them, they run offline.
- **Cons:** I need hardware and effort to run them; the very top models are usually still closed.
- **"Open-weight" is not always "open source".** The weights are downloadable, but the licence may limit commercial use or the training data may not be shared. I read the licence.

## 3. Sizes and tiers
| | Small / fast / cheap | Medium | Large / slow / capable |
|---|---|---|---|
| Speed | Fastest | Balanced | Slowest |
| Cost per token | Lowest | Middle | Highest |
| Good at | Classification, extraction, simple chat, routing | General work, coding, writing | Hard reasoning, long complex tasks |
| Typical names | "mini", "flash", "haiku"-style | Middle tier | "pro", "opus"-style |

- **Pick the smallest model that does the job well.** A small model is often much cheaper and faster.
- Local models are measured in **parameters** (7B, 70B, ...). More parameters usually means smarter, bigger and slower.
- Tier names differ between providers and change with each release.
- **Reasoning models** form their own group: slower and costlier, better at hard problems.

## 4. Multimodal inputs (awareness)
Many models take more than text:
- **Images** (photos, screenshots, charts, handwriting)
- **PDFs** (text and layout)
- **Audio** (speech), and some also video

- Images and audio are converted to tokens too, so they **cost tokens** (often many).
- Not every model supports every input; I check the model's page.
- Output is usually still text; some models can also produce images or speech.

## 5. Latency metrics
| Metric | Meaning | Matters for |
|---|---|---|
| **TTFT** (time to first token) | Time from sending the request until the first token arrives | Chat feel: how long the user stares at nothing |
| **Tokens per second** | How fast tokens arrive after the first | How quickly a long answer finishes |
| **Total latency** | Time until the whole answer is complete | Background jobs, batch work, structured output |

```
total latency ≈ TTFT + (output tokens ÷ tokens per second)
```
Example with invented numbers: TTFT 0.6 s, speed 50 tokens/s, answer of 300 tokens → 0.6 + 300 ÷ 50 = **6.6 seconds** in total, but the user starts reading after 0.6 s if the reply is streamed.

- **Streaming** lowers the *felt* wait because the first words appear early (TTFT matters most).
- TTFT grows with a longer input and with reasoning models that think first.
- Small models are usually faster in both TTFT and tokens per second.
- I measure on **my own prompts**, at different times of day: published figures are averages.

## 6. Leaderboards
- **LMArena**: people compare two anonymous answers and vote; the ranking comes from the votes.
- **Artificial Analysis**: measured quality, speed and price across many models.

I use them as **signals, not decisions**:
- They show which models are worth testing.
- They do not know my task, my language or my data.
- Votes can favour style and length; benchmarks can be gamed or leak into training.
- The ranking changes often.

**The real decision:** test 2 or 3 candidate models on a small set of my own examples, and compare quality, speed and cost.

## 7. Choosing a model
| Question | Leans towards |
|---|---|
| Simple, high-volume task (tags, extraction)? | Small, cheap model |
| Hard reasoning or tricky code? | Large or reasoning model |
| Private data that must not leave? | Local open-weight model |
| Need images or PDFs? | A multimodal model |
| Chat that must feel instant? | Fast model with streaming (low TTFT) |
| Budget tight at scale? | Smallest model that passes my tests |

## Common mistakes
| Mistake | Reality |
|---|---|
| "Use the biggest model for everything" | Slower and costlier; a small one often does as well |
| "The top of the leaderboard is best for me" | It may be worse on my task; test my own examples |
| "Open-weight means open source" | Check the licence |
| "I can trust numbers I read last year" | Names, prices and speeds change every few months |
| "Latency is one number" | TTFT, tokens per second and total latency are different |
| "Local models are free" | I pay in hardware, time and speed |
