# Tokens

Every number below was measured with `tiktoken`.

## 1. What a token is
A model does not read letters or words. It reads **tokens**: small pieces of text. A token can be a whole word, part of a word, a space plus a word, a number chunk, or a punctuation mark.

```
"strawberry"       →  "st" | "raw" | "berry"          3 tokens
"unbelievably"     →  "un" | "bel" | "ievably"        3 tokens
" Paris"           →  " Paris"                        1 token (the space is inside it)
```
- In English, **one token is about 4 characters**, or roughly 3/4 of a word. A 44-character test sentence was 10 tokens.
- **A space belongs to the token that follows it.** `" Paris"` and `"Paris"` are different tokens.
- Everything the model reads or writes (prompt, answer, instructions) is counted in tokens.

## 2. BPE: how the pieces are chosen
Most models use **Byte Pair Encoding (BPE)**, a way of building a vocabulary from lots of text:
1. Start with the smallest units (single bytes or characters).
2. Find the **pair that appears most often** together and merge it into one new unit.
3. Repeat thousands of times until the vocabulary has the wanted size (roughly 100,000 to 200,000 tokens).

The result:
- **Common words** become one token (`" the"`, `" Paris"`).
- **Rare words** are split into familiar pieces (`un | bel | ievably`).
- **Anything is representable.** In the worst case it falls back to single bytes, so no input is "unknown".
- The vocabulary is fixed **after** training. Tokenising text is a lookup, not AI.

## 3. Different models, different tokenisers
Each model family has its own tokeniser and vocabulary, so **the same text gives different counts**. Same Hindi sentence, two OpenAI tokenisers:

| Text | Characters | `cl100k_base` | `o200k_base` |
|---|---|---|---|
| English: "The quick brown fox jumps over the lazy dog." | 44 | 10 | 10 |
| Hindi (same meaning) | 45 | **49** | **20** |
| Hinglish (Hindi in English letters) | 46 | 20 | 18 |

- **Counts are not portable.** A number from one tokeniser is not valid for another model family (Claude, Gemini, Llama and others each have their own).
- For billing or limits, count with **the provider's own tokeniser or token-count API**.
- A newer tokeniser can be much better for some languages (Hindi: 49 → 20).

## 4. Hindi and other Indic scripts cost more
With the older tokeniser the Hindi sentence needed **almost 5 times** the English tokens for the same meaning, and still **2 times** with the newer one.
- Scripts like Devanagari are rarer in training text, so fewer merges exist and words break into many small pieces.
- More tokens means **more cost, more latency and less room in the context window**.
- Hinglish (Roman letters) was cheaper than Hindi script in both tokenisers.
- Always measure with real messages before estimating a budget.

## 5. Numbers, code and whitespace behave unexpectedly
| Text | Tokens (o200k) | Pieces |
|---|---|---|
| `1234567890` | 4 | `123` \| `456` \| `789` \| `0` |
| `3.14159265` | 5 | `3` \| `.` \| `141` \| `592` \| `65` |
| `2026-11-05` | 6 | `202` \| `6` \| `-` \| `11` \| `-` \| `05` |
| 4 spaces | 1 | a single token |
| `def add(a, b):` and a body | 11 | `def` \| ` add` \| `(a` \| `,` \| ` b` \| `):\n` … |

- **Numbers are cut into chunks of about three digits** from the left, not by place value (`2026` becomes `202` + `6`). One reason models are weak at arithmetic.
- **Dates, IDs and long numbers** use many tokens.
- **Indentation and line breaks** in code are tokens too, and sometimes merge with neighbouring characters (`):\n`).
- **Typos split words**: `helllo` became `hell` + `lo`.

## 6. Why models struggle with character-level tasks
The model sees `st | raw | berry`, **not** the letters. These are hard for it:
- "How many r's are in strawberry?"
- "Reverse this word."
- "What is the 5th letter of this name?"

It never saw the letters one by one, so it guesses from patterns. Do such tasks **in code**.

## 7. Pricing is per token
| Kind | Meaning | Price |
|---|---|---|
| **Input** tokens | Everything I send (prompt, history, documents) | Lower |
| **Output** tokens | What the model writes | Higher (often several times the input price) |
| **Cached input** tokens | Input the provider reuses from a recent call | Much cheaper than normal input |
| **Thinking** tokens | The reasoning of a reasoning model | Billed like output tokens |

```
cost = input_tokens  × input_price
     + output_tokens × output_price
     (+ cached and thinking tokens at their own prices)
```
Prices are quoted **per million tokens** and change every few months, so I read the provider's current price page. With an invented price of 1 per million input tokens: 1,000,000 messages of 50 tokens is 50 million input tokens, so 50 units on input. If the same messages need 5 times the tokens (Hindi script, older tokeniser), it is 250 units.

## 8. What to do with this
- **Count tokens before sending**, especially long documents.
- **Use the right tokeniser** for the model I call.
- **Keep prompts short and clean**: whitespace, repeated text and long numbers cost tokens.
- **Measure non-English text separately**.
- **Do character and arithmetic work in code.**

## Common mistakes
| Mistake | Reality |
|---|---|
| "One token is one word" | About 4 English characters, or 3/4 of a word |
| "Token counts are the same everywhere" | Each tokeniser differs (Hindi was 49 vs 20) |
| "Hindi costs the same as English" | Often 2 to 5 times more tokens |
| "The model reads letters" | It reads token pieces, so letter counting is unreliable |
| "Output and input cost the same" | Output is usually priced higher |
| "Only my prompt counts" | Prompt, history, documents, answer and thinking all count |
