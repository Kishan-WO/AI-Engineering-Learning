# The context window

## 1. What it is
The **context window** is the maximum number of tokens a model can handle in **one call**. It counts both sides:

```
input tokens (everything I send)  +  output tokens (what the model writes)  ≤  context window
```
- Everything I send counts: the system instructions, the whole conversation, any documents, and my new question.
- The answer counts too. If the window is 100,000 tokens and I send 99,000, the model has only 1,000 left to answer with.
- Many APIs also have a separate cap on the output alone (`max_tokens`).
- Window sizes differ by model and change over time, so I check the provider's current docs.

## 2. The model is stateless
**The model remembers nothing between calls.** Each call starts from zero, and it only knows the text sent in that call.

A chatbot seems to remember because **my code re-sends the whole conversation every time**:

```python
messages = []

messages.append({"role": "user", "content": "My name is Asha."})
reply = call_model(messages)            # model sees: 1 message
messages.append({"role": "assistant", "content": reply})

messages.append({"role": "user", "content": "What is my name?"})
reply = call_model(messages)            # model sees: all 3 messages, so it can answer "Asha"
```
- The `messages` list lives in **my program**, not inside the model.
- If I send only `"What is my name?"` without the history, the model has no idea.
- "Memory" is something **my code does**: store the messages, send them again.
- Delete a message from the list, and the model has truly forgotten it.

## 3. The cost of re-sending
Every turn re-sends everything so far, so input grows with each turn. Say each question is 100 tokens and each answer is 200 tokens:

| Turn | Tokens sent as input | Why |
|---|---|---|
| 1 | 100 | question 1 |
| 2 | 400 | Q1 + A1 + Q2 |
| 3 | 700 | Q1 + A1 + Q2 + A2 + Q3 |
| 5 | 1,300 | |
| 10 | 2,800 | |

- Over 10 turns the **total input is 14,500 tokens**, although I typed only 1,000 tokens of questions.
- Each turn costs more than the last, and the total grows much faster than the number of turns.
- The same history is billed again every time (unless the provider caches it, which makes repeated input cheaper).
- It also gets **slower**, because a longer input takes longer to process.

## 4. What happens when the conversation exceeds the window
It depends on the provider and on my code:
- **The API returns an error** saying the input is too long. This is common.
- **Some systems cut off the oldest text** automatically. The model then forgets the beginning, without telling me.
- **My own code decides.** The reliable approach is to manage it myself before sending.

| Strategy | How it works | Trade-off |
|---|---|---|
| **Keep the last N messages** | Drop the oldest messages | Simple; the model forgets the start |
| **Summarise old messages** | Replace old turns with a short summary | Keeps the gist; costs an extra call and loses detail |
| **Keep important parts, drop the rest** | Always keep the system prompt and key facts | More work, better results |
| **Retrieve only what is needed** | Fetch relevant pieces instead of sending everything | Best for large knowledge, more complex |

Always keep the **system instructions** at the start, whatever else is trimmed.

## 5. Longer context costs more and can lower quality
A bigger window does not mean "use all of it":
- **Cost:** more input tokens means a higher bill on every call.
- **Speed:** long inputs are slower, especially the time before the first token.
- **Quality:** models can get worse as the text grows. Details in the **middle** of a very long input are often used less reliably than details at the start or the end ("lost in the middle"). Irrelevant text also distracts the model.

Good habit: **send only what the model needs**, with the key instructions clear and easy to find.

## 6. Why a chatbot "forgets"
- The model keeps nothing between calls.
- The chatbot only knows what is in the list my code sends.
- If the list is cut (to save cost or fit the window), the dropped messages are gone for the model.
- So "forgetting" is simply: **the text is no longer in the input.**

## Common mistakes
| Mistake | Reality |
|---|---|
| "The model remembers my last chat" | It is stateless; my code re-sends the history |
| "Only my new question is billed" | The whole history is billed again each turn |
| "The window only limits my prompt" | Input and output together must fit |
| "Bigger window means better answers" | More text can cost more and distract the model |
| "Old messages are safe" | If I drop them from the list, they are gone |
| "The API will trim for me" | Often it just returns an error; trim in my own code |
