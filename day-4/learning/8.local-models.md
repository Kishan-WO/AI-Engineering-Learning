# Local models

Checked on my machine: Ollama 0.40.6 is running with the model `gemma3:270m` (291 MB).

## 1. Ollama and LM Studio
Both download a model and run it on my own computer.

| | Ollama | LM Studio |
|---|---|---|
| Style | Command line and a background server | Desktop app with a window |
| Good for | Scripts and code, easy to automate | Trying models by clicking, comparing them |
| Local API | Yes, on `http://localhost:11434` | Yes, a local server switched on in the app |

```bash
ollama pull gemma3:270m     # download a model
ollama list                 # models on this machine
ollama run gemma3:270m      # chat in the terminal
```
The model files stay on disk, and nothing is sent to the internet when I use them.

## 2. Why a big model can fit on a laptop: quantisation
A model's weights are billions of numbers. Normally each is stored with high precision (16 bits). **Quantisation** stores each number with **fewer bits** (8, 5, 4, even less).

| Precision | Size of a 7 to 8 billion parameter model (rough) |
|---|---|
| 16-bit | about 14 to 16 GB |
| 8-bit | about 7 to 8 GB |
| 4-bit | about 4 to 5 GB |

- A 4-bit version is roughly **a quarter** of the original size, so a 7 to 8B model fits in a normal laptop's memory.
- Quality drops a little as the bits go down. 4 to 5 bits is often a good balance; very low bits hurt noticeably.
- File size is roughly **parameters × bits ÷ 8**. `gemma3:270m` has 270 million parameters, which is why the file is only 291 MB.

## 3. GGUF
**GGUF** is a single-file format for quantised models, used by `llama.cpp` and the tools built on it (Ollama, LM Studio).
- One file holds the weights, the tokeniser and the settings.
- Names often show the quantisation, for example `Q4_K_M` (about 4-bit) or `Q8_0` (8-bit).
- GGUF files can be downloaded from model hubs, or Ollama manages them for me.

## 4. What my machine can run
- **GPU:** GeForce GT 730 with 2 GB: too small to help, so models run on the **CPU**.
- **RAM:** about 16 GB: enough for a 4-bit model of roughly 3 to 8 billion parameters.
- **Disk:** about 26 GB free.
- On a CPU, speed is the limit: bigger models answer slowly.

My test call to `gemma3:270m` (temperature 0, `max_tokens` 40):
- Reply: **"Paris"**, `finish_reason: stop`, 21 prompt tokens, 3 completion tokens.
- Streaming a short list: 22 chunks, **first chunk after about 2.6 s**, whole reply in about 3.8 s. The first call also includes loading the model into memory.
- A 270M model is a tiny test model: fast and cheap, but weak at reasoning and facts. Good for learning the mechanics, not for quality work.

## 5. The OpenAI-compatible endpoint
Ollama (and LM Studio) copy the **same HTTP shape** as the OpenAI chat API:

```
POST http://localhost:11434/v1/chat/completions
{
  "model": "gemma3:270m",
  "messages": [{"role": "user", "content": "..."}],
  "temperature": 0,
  "max_tokens": 40
}
```
The reply has the usual fields: `choices[0].message.content`, `finish_reason`, and `usage` with token counts. `GET /v1/models` lists the installed models.

**The same client code can talk to a hosted model or a local one.** Only the configuration changes:

| Setting | Hosted model | Local model |
|---|---|---|
| `base_url` | The provider's URL | `http://localhost:11434/v1` |
| `api_key` | A real key | Any text (Ollama ignores it, but many clients require one) |
| `model` | The provider's model name | `gemma3:270m` |

So I write the code once, switch between local and hosted by changing configuration, and test cheaply on a local model before spending on a hosted one. Not every provider copies this shape exactly, and extras such as log probabilities or certain parameters may differ.

## 6. When local models make sense
| Reason | Why |
|---|---|
| **Privacy** | Data never leaves my machine or network |
| **Cost at scale** | No per-token fee; I pay for hardware and power |
| **Offline or restricted networks** | No internet needed |
| **Control** | I choose the exact model version; no surprise updates or retirements |
| **Experiments** | Free, unlimited trial calls while learning |

## 7. When they do not
| Reason | Why |
|---|---|
| **Quality** | The best models are still hosted; small local ones are weaker at reasoning, long context and rare facts |
| **Speed** | On a CPU, a small model is slow and a large one very slow |
| **Hardware** | Bigger models need lots of RAM or a strong GPU |
| **Effort** | I handle updates, scaling, monitoring and failures myself |
| **Low volume** | At small usage the API fee is lower than owning hardware |

Rule of thumb: start with a hosted model for quality, and move a task to a local model when privacy or cost at scale demands it and a small model passes my tests.

## Common mistakes
| Mistake | Reality |
|---|---|
| "Local means free" | I pay in hardware, power, time and speed |
| "A 270M model shows what LLMs can do" | It is a tiny test model; quality is far lower |
| "Quantised models are the same quality" | A small loss, bigger at very low bits |
| "Any hardware runs any model" | RAM and GPU decide what fits and how fast it runs |
| "Local and hosted APIs are identical" | Similar shape, but parameters and extras can differ |
| "My `api_key` doesn't matter for local" | Often ignored by the server, but clients may still require some text |
