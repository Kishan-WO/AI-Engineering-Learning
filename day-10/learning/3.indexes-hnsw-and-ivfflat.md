# Indexes: HNSW, IVFFlat, build time and memory

An index is what turns "compare with everything" into "look at a few hundred candidates". The settings decide how much recall I pay for how much speed.

## 1. HNSW: the idea
HNSW (Hierarchical Navigable Small World) stores the vectors as a **graph**: each vector is linked to some of its near neighbours, in several layers.

```
top layer     few nodes, long links      ──> a coarse map of the whole space
middle layers more nodes, shorter links
bottom layer  every vector, short links  ──> the detailed neighbourhood
```
- **Search:** start at an entry point in the top layer, move greedily to whichever neighbour is closer to the query, go down a layer, repeat. At the bottom layer, keep a list of the best candidates found and return the top k.
- It visits a tiny share of the vectors, so the time grows slowly with the collection size.
- It is approximate: the greedy walk can miss a true neighbour that sits behind a poor link.

## 2. The three HNSW settings
| Setting | When | Meaning | Bigger means |
|---|---|---|---|
| **`m`** | build | how many links each node keeps | better recall, more memory, slower build |
| **`ef_construction`** | build | how many candidates are considered while linking a new node | a better graph, slower build |
| **`ef_search`** | query | how many candidates the search keeps | higher recall, slower query |

- **`ef_search` is the one I tune at run time,** without rebuilding. It must be at least `k`; pgvector's default is 40, Qdrant calls the same idea `hnsw_ef`.
- `m` and `ef_construction` are fixed when the index is built. Defaults in pgvector are `m = 16` and `ef_construction = 64`; Qdrant's defaults are `m = 16` and `ef_construct = 100`. I check the docs of the installed version.
- **How I tune it:** run the same queries with the exact search as the reference, and raise `ef_search` until the index returns the exact top 5 (or close to it), then stop. More than that only costs time.

## 3. pgvector syntax
```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
    id uuid PRIMARY KEY,
    embedding vector(1024) NOT NULL,
    ...
);

CREATE INDEX chunks_embedding_hnsw
ON chunks USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

SET hnsw.ef_search = 100;                       -- per session or per transaction
SELECT id, embedding <=> :q AS distance
FROM chunks ORDER BY embedding <=> :q LIMIT 5;
```
- **The operator and the operator class must match the metric:** `<=>` is cosine distance with `vector_cosine_ops`; `<->` is L2 with `vector_l2_ops`; `<#>` is negative inner product with `vector_ip_ops`. If the query uses `<=>` but the index was built with `vector_l2_ops`, Postgres ignores the index and scans everything, with no error.
- **Distance is not similarity:** cosine distance is `1 - cosine`, smaller is closer. A score for the user is `1 - distance`.
- The vectors are already length 1, so cosine and inner product give the same order.
- **Dimension limit:** a `vector` column can be indexed up to 2,000 dimensions (a `halfvec` column, which stores float16, up to 4,000). My 1,024 is within it; Gemini's 3,072 would not have been. I confirm the limit in the README of the version I install.

## 4. IVFFlat (awareness)
- **Idea:** cluster the vectors into `lists` groups (k-means). At query time search only the `probes` groups nearest to the query.
- **Settings:** `lists` at build, `probes` at query (higher means better recall, slower). It needs **data in the table before the index is built**, because the clusters come from the data.
- **Compared with HNSW:** faster and smaller to build and uses less memory, but usually gives a worse speed and recall trade-off, and its quality drifts if the data changes a lot after the build.
- I use HNSW today and only need to recognise IVFFlat.

## 5. Build time and memory
- **HNSW build is the slow part:** every insert searches the graph and links the new node. It takes much longer than IVFFlat and grows with `m` and `ef_construction`. For a small table it is seconds.
- **Memory:** the index holds the graph links as well as (or on top of) the vectors. Roughly, each node adds a few hundred bytes of links at `m = 16`, so the graph is small next to the vectors themselves (1,024 float32 numbers is 4,096 bytes). The vectors in the table or the index still have to be read, so the whole working set should fit in memory for the speed to hold. These are my approximate figures, not measurements.
- **Postgres settings that matter for a build:** `maintenance_work_mem` (a graph that fits in it builds much faster) and parallel workers. I read the build notice Postgres prints.
- **Inserts after the build** update the graph. Frequent writes and deletes make the graph less tidy over time; a rebuild or `REINDEX` restores it.
- **Deletes:** removing a row leaves a dead entry until vacuum; I check that deleted vectors are really gone from the results (task 7).
