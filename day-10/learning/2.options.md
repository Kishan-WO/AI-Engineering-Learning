# Options: the vector database landscape

There are many products. I only need to know what each is for, and then choose by my own constraints. The facts below are the ones I know today; I check the docs of the version I install before I rely on a number or a feature name.

## 1. The map
| Option | What it is | Strong at | Watch for |
|---|---|---|---|
| **pgvector** | an extension inside Postgres | one database for everything: transactions, joins, backups, row filters and vectors together | the index limit on dimensions, and filtered ANN behaviour (note 5) |
| **Qdrant** | a dedicated vector database (Rust) | strong filtering on payload, many index and quantisation options, simple to run in Docker | a second system to run, back up and keep in step with Postgres |
| **Chroma** | a simple, local, developer-friendly store | quick prototypes with almost no setup | not the usual choice for a multi-tenant production service |
| **Weaviate** | a vector database with built-in modules and hybrid search | search features out of the box | heavier to run and learn |
| **Pinecone** | a managed, hosted service | no servers to run; namespaces for tenants | a paid hosted service, my data lives with the vendor |
| **Milvus** | a distributed vector database | very large collections | complex to run; more than I need |
| **LanceDB** | an embedded, file-based store | local analytics and small to medium data | newer, fewer production examples |
| **FAISS** | a **library**, not a database (from Meta) | very fast index structures in memory | no server, no storage of metadata, no filters, no deletes by itself |
| **MongoDB Atlas Vector Search**, **Elasticsearch or OpenSearch kNN**, **Redis** | vectors added to a database I may already run | one fewer system if I already use it | the vector features follow the main product; I would check filters and limits |

## 2. pgvector, in a few lines
- A Postgres extension: `CREATE EXTENSION vector;`, a column type `vector(1024)`, and operators for distance.
- It stays inside the database I already have: the `chunks` table can have a real foreign key to `documents`, and a delete of a document can cascade to its chunks in the same transaction.
- Filters are ordinary SQL (`WHERE tenant_id = ...`), so my tenant rules and my vector search live in one query.
- My `docker-compose.yml` already uses the `pgvector/pgvector:pg16` image.

## 3. Qdrant, in a few lines
- A separate server with its own storage. Data is organised in **collections** of **points**. A point has an id, a vector and a **payload** (JSON metadata).
- Filters work on payload fields, and a payload field can have its own index so filtered search stays fast (note 5).
- It runs from one Docker image, and it has a Python client.
- The cost is a second system: ingestion must write to both Postgres (documents) and Qdrant (vectors), and a failure between the two leaves them out of step.

## 4. How I choose (my own rules)
| Question | pgvector | Qdrant |
|---|---|---|
| Do I already run Postgres, and do I need transactions with my other data? | **yes, a strong reason** | no, I would need to keep two stores consistent |
| How many vectors? | up to millions is common, with enough memory | millions to billions |
| How complex are the filters? | fine for SQL filters, with care on very selective ones | designed for it |
| How much do I want to operate? | nothing new | one more service |
| Can I swap later? | yes, if I keep a thin interface (below) | yes, the same |

For this course: **start with pgvector** (it is already in my stack), and **port to Qdrant behind an interface** so I see the difference and so the choice is a setting, not a rewrite.

## 5. The interface that makes the choice reversible
Day 6 gave me an `LLMClient` protocol: routes depend on the interface, and an adapter hides the provider. Vectors get the same shape, a `VectorStore` protocol:
- `upsert(chunks)`: insert or replace chunks with their vectors and metadata.
- `search(query_vector, tenant_id, k, filters)`: nearest chunks for one tenant.
- `delete_document(tenant_id, document_id)`: remove every vector of a document.
- A setting (for example `VECTOR_STORE=pgvector` or `qdrant`) picks the adapter, and the `/search` route never knows which one it uses.
- **`tenant_id` is a required argument of `search`**, not an optional filter. That makes it impossible to call the store without saying whose data it is (note 6).

## 6. What I do not need to decide today
- Managed or self-hosted at scale, sharding and replicas, and costs per million vectors. At 2,097 vectors any option works; the value of today is learning how the pieces behave.
