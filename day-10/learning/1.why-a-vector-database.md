# Why a vector database

On Day 9 I searched with one NumPy line: `scores = vectors @ query`. It was exact and took 0.5 to 0.7 ms for 2,097 vectors. A vector database is what I reach for when that line stops being enough, and it also gives me things NumPy never will.

## 1. What brute force costs
- **Exact search is O(n):** the query is compared with every stored vector. Twice the vectors means about twice the time and twice the memory read.
- **My own measurement (Day 9):** 2,097 vectors of 1,024 float32 numbers, 0.5 to 0.7 ms. If time grows in a straight line, 100,000 vectors would be about 30 ms and 1,000,000 about 300 ms (estimates from my number, not measurements).
- **Memory:** `n x d x 4 bytes`. 100,000 x 1,024 x 4 is about 410 MB; 1,000,000 is about 4.1 GB. Everything has to sit in memory for a fast scan.

## 2. Approximate nearest neighbour (ANN)
- **The idea:** build an index once, so a query looks at a few hundred vectors instead of all of them. It may miss a true neighbour, so the answer is "approximately" the nearest.
- **The trade:** a little **recall** (the share of the true top-k that the index finds) for a large gain in **speed**. With a good setting it finds 95 to 99% of the true neighbours in a small fraction of the time.
- **Two recalls, not one:**
  - **ANN recall:** how many of the exact search's top-k does the index return? It measures the index.
  - **Retrieval recall@k:** how often is the right document in the top k? It measures the model and the chunks (Day 9).
  - A good index gives ANN recall near 100% against the exact search, so retrieval recall stays what the model already had. Task 4 of today measures both.

## 3. When brute force is still the right answer
- Under about **100,000 vectors** brute force is often fast enough (tens of milliseconds) and has no index to build, tune or keep in step.
- It is exact, so there is no recall to lose and no setting to tune.
- It is simple: one array and one function, easy to test.
- A **filtered** search over a small set (one tenant's few hundred chunks) can be an exact scan of just those rows.
- So my 2,097 vectors do not need an index. Building one today is practice for the real case, and the comparison of HNSW with exact search is part of the task.

## 4. What a vector database gives besides speed
| Need | NumPy array | Vector database |
|---|---|---|
| Find the nearest vectors | yes | yes, faster at scale |
| Keep vectors and text and metadata together | I keep three files in step by hand | one row or point |
| Filter by tenant, document, date | I mask the array myself | built in |
| Add, change and delete one vector | rebuild the array | upsert and delete |
| Survive a restart, many readers and writers | no | yes |
| Transactions with the rest of my data | no | yes in Postgres (pgvector) |
| Big collections that do not fit in memory | no | some (disk-based indexes, quantisation) |

The Day 9 weak spot was exactly this: `meta.json` and `vectors.npy` had to be rebuilt together, and nothing checked that they matched.

## 5. What I need to remember
- A vector database stores and searches **vectors made by one embedding model**. It does not make them. The query must be embedded with the same model (Day 9), and the model name and dimensions belong in the data.
- ANN settings are a **speed against recall** knob. I set them by measuring against the exact search, not by copying a number.
- A database does not fix a bad embedding model or bad chunks. If the right chunk is not close to the query, no index brings it back.
