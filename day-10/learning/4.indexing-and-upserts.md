# Indexing and upserts: keeping the vectors right as the documents change

Embedding the corpus once is easy. The hard part is that documents are added, edited and deleted, and the embedding model can change. The index must always match what the documents say today.

## 1. Upsert by a stable chunk id
- **Upsert** means insert the chunk, or replace it if it already exists. Running the same load twice must give the same table, not duplicates.
- **A stable id is what makes that possible.** The id of a chunk must be the same every time the same chunk is processed. Two good ways:
  - a **deterministic id** from where the chunk is: `uuid5(namespace, f"{document_id}:{chunk_number}")`;
  - or from what the chunk is: a hash of the document id, chunk number and text.
- **A random id (`uuid4`) is the wrong choice for ingestion:** every run makes new ids, so the second run duplicates the whole corpus.
- In Postgres:
  ```sql
  INSERT INTO chunks (id, ...) VALUES (...)
  ON CONFLICT (id) DO UPDATE SET text = EXCLUDED.text, embedding = EXCLUDED.embedding, ...;
  ```
  In Qdrant, a point with an existing id is replaced when it is upserted.
- **What changes the id and what does not:** if the chunking changes (a section is cut in a different place), the old ids no longer match the new chunks. Re-ingesting must delete the document's old chunks first, or the old chunks stay as orphans (section 3).

## 2. What to store with each vector
| Field | Why |
|---|---|
| `id` | the stable chunk id |
| `tenant_id` | isolation (note 6) |
| `document_id` | to delete or refresh a document's chunks as a group |
| `chunk_number` or heading path | order and a readable citation |
| `text` | what the chat model will read later (Day 12) |
| `content_hash` of the chunk text | to skip re-embedding unchanged chunks |
| **`embedding_model`** (name and version), dimensions | vectors from different models cannot be compared (Day 9) |
| metadata (source, title, licence, page) | filters and citations |
| `created_at`, `updated_at` | debugging and audits |

**The model name next to the vector is not optional.** Nothing inside a vector says which model made it. If two models' vectors end up in one index, searches return nonsense with no error.

## 3. Deleting vectors with their document
- **In Postgres:** `chunks.document_id` is a foreign key to `documents.id` with `ON DELETE CASCADE`. Deleting a document removes its chunks in the same transaction, so there is no moment where the document is gone and its chunks are still searchable.
- **In Qdrant** there is no foreign key. I delete the points whose payload `document_id` matches (a delete by filter), and I have to make that part of the document-delete code path. A failure between "delete the document in Postgres" and "delete its points in Qdrant" leaves orphans, which would still be returned by searches. So the store call must be retried or reconciled, and a periodic check can compare the ids in both.
- **Proof for task 7:** count the chunks of the document before, delete it, count again (zero), and search with a query that used to find it: it must not appear.

## 4. When a document changes
`documents` already has a `content_hash`. The plan for an updated document:
1. Compute the new content hash. If it is the same as the stored one, do nothing (idempotent).
2. Otherwise cut it into chunks again and compute each chunk's text hash.
3. **Replace** the document's chunks: upsert the new ones, and delete the old chunks that no longer exist (those whose ids are not in the new set).
4. Embed only the chunks whose text hash is new or changed, which saves cost on a big document with a small edit.

## 5. When the embedding model changes
- **A new model means re-embedding everything.** Old and new vectors live in different spaces and must never be searched together.
- **A safe way (blue and green):** build a second index (a new table or collection, or a new vector column) with the new model, fill it completely, check recall on my labelled queries, then switch the search to it and drop the old one.
- **Changing the number of dimensions** also needs a new column or table, because the size is part of the column type (`vector(1024)`).
- The model name stored with each row lets me see at any time which model an index holds, and refuse a query from another model.

## 6. Ingestion as a script today, a worker tomorrow
- Today a script loads the Day 9 sections and upserts them in batches (`embed` then `upsert`, as in Day 9's `embed_jina.py`: batches, retries, and a saved state so a stop can be resumed).
- Day 11 moves this into a background worker with an idempotent pipeline, so the id and hash rules above are what that pipeline will build on.
- **Order of writes:** the document row first, then its chunks. If the embedding step fails half way, the next run finds the chunks missing or stale (by hash) and completes them.

## 7. Mistakes to avoid
| Mistake | What happens |
|---|---|
| A random id for chunks | a second run doubles the corpus |
| Not storing the model name | a model change silently mixes two spaces |
| Deleting the document but not its vectors (Qdrant) | deleted content still shows up in answers |
| Re-embedding the whole corpus for a one-word edit | cost and time for nothing |
| Changing the chunking but keeping the old ids | stale chunks that never get deleted |
