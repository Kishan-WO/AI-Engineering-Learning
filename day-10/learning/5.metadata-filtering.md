# Metadata filtering: why a filter can break a nearest-neighbour search

A real search is almost never "the nearest vectors in the whole index". It is "the nearest vectors **of this tenant**, of this source, in this date range". The way a filter is combined with an ANN index decides whether I get the right results.

## 1. Two ways to combine a filter with the search
| | Pre-filtering | Post-filtering |
|---|---|---|
| Order | restrict to the rows that match the filter, then search them | search the whole index for the nearest k, then drop the ones that fail the filter |
| Result size | always k, if k matching rows exist | **can be fewer than k, even zero** |
| Cost | depends on how the index handles the filter | cheap, but may waste work |
| Exact? | yes, for the restricted set | no: the nearest k overall may all belong to other tenants |

### The failure of post-filtering, in numbers
- The index holds 1,000,000 vectors of 1,000 tenants. I ask for the top 5 for tenant 7 and the index returns its nearest 40 candidates.
- Tenant 7 owns 0.1% of the data, so on average 0.04 of those 40 belong to tenant 7. I filter, and I get **zero** results, although tenant 7 has the right chunks.
- The more selective the filter (a small tenant, a rare source), the worse it gets. This is also why a test with a tenant who has few documents is important.

## 2. How the two systems handle it
### pgvector (inside Postgres)
- The index scan (HNSW) returns candidates, and the `WHERE` clause is applied **after** them, so a selective filter can return fewer than `LIMIT` rows.
- **Raising `hnsw.ef_search`** gives more candidates, which helps but is a blunt tool (the cap is 1,000).
- **Iterative index scans** (added in pgvector 0.8; the setting is `hnsw.iterative_scan`, with `strict_order` or `relaxed_order`, and `hnsw.max_scan_tuples` as a limit): when a filtered query has not found enough rows, the index keeps scanning further until it does or reaches the limit. I check the version I install supports it.
- **Other tools in Postgres:** a normal B-tree index on `tenant_id` (the planner may skip the vector index and sort the tenant's rows exactly, which is perfect for a small tenant), a **partial index** per big tenant, or **table partitioning** by tenant.
- I look at `EXPLAIN` to see which plan Postgres picked.

### Qdrant
- Filters work on the **payload** (the JSON metadata of a point).
- A **payload index** on a field (for example `tenant_id` as a keyword) makes the filter fast, and Qdrant builds its HNSW graph so that filtered search still follows useful links, so it does not suffer the "zero results" failure of plain post-filtering.
- Without a payload index on the field, the filter still works but can be slow on a big collection.
- For multi-tenant data, Qdrant's documentation recommends one collection with a tenant field in the payload, indexed as a tenant key (note 6).

## 3. Which filters I need
| Filter | Purpose |
|---|---|
| `tenant_id` | isolation: must be on every query (note 6) |
| `source` or `document_id` | search inside one source or one document |
| `embedding_model` | never mix models: the search must only touch rows of the model that made the query vector |
| date, language, document type | later: freshness and routing |

## 4. What to test
- **A selective filter:** a tenant with 5 chunks, and k = 5: do I get all 5 back? With HNSW and plain post-filtering I might not.
- **A tenant with zero chunks:** the answer must be an empty list, with no error and no rows from anyone else.
- **Compare with the exact search over the same filter:** the filtered ANN result against an exact scan of that tenant's rows. If they differ, the index is losing recall under the filter.

## 5. Mistakes to avoid
| Mistake | What happens |
|---|---|
| Trusting `LIMIT k` to give k rows under a filter | fewer results, with no error |
| Building the filter only "if the tenant has documents" | the tenant with zero documents sees everyone's data (note 6) |
| Filtering on a payload field that has no index (Qdrant) | correct but slow |
| Testing filters only with a big tenant | the failure only shows for small ones |
| Leaving out the embedding-model filter after a model change | results mix two spaces |
