# Multi-tenancy: one tenant must never see another tenant's chunks

`ai-service` already has tenants: every user belongs to one, and every document has a `tenant_id`. The vector store must respect that on every search. A leak here is a data breach, not a bug.

## 1. Three ways to separate tenants
| Approach | How | Good for | Cost |
|---|---|---|---|
| **A tenant column and a filter** (pgvector) | one `chunks` table, a `tenant_id` column, `WHERE tenant_id = :t` in every query | most apps; simplest; one index | the filter must be in every query without exception |
| **Payload-based partitioning** (Qdrant) | one collection, a `tenant_id` payload field, indexed as the tenant key | many tenants, each small | the filter must be in every query without exception |
| **A collection (or table or schema) per tenant** | separate storage per tenant | a few big tenants, strict separation, per-tenant deletion | many collections cost memory and management; does not scale to thousands of tenants |

- With a **namespace** (Pinecone's word) the idea is the same as a collection per tenant, made cheap.
- For this course: a `tenant_id` column plus filter in pgvector, and a payload field in one Qdrant collection.

## 2. The rule: isolation is inside the query
- **The tenant comes from the logged-in user** (the JWT, as `/documents` already does with `user.tenant_id`), **never from the request body or a query parameter.** A client that can say "search as tenant 2" can read tenant 2.
- **The filter is not added by the route; it is built into the store.** The `VectorStore.search(query_vector, tenant_id, k)` signature has `tenant_id` as a required argument, so there is no way to call it without one.
- **The filter has to be applied inside the database query**, not by fetching results and removing the wrong ones in Python. A filter in Python after a search gives fewer than k results (note 5) and relies on every code path remembering to do it.

```python
# wrong: tenant picked from the request, filter applied afterwards
hits = store.search(vector, k=5)
hits = [h for h in hits if h.tenant_id == body.tenant_id]

# right: tenant from the authenticated user, filter inside the query
hits = store.search(vector, tenant_id=user.tenant_id, k=5)
```

## 3. The classic bugs
| Bug | Why it happens |
|---|---|
| **The tenant with no documents sees everyone's data** | the filter is built conditionally ("if the tenant has documents, add the filter") or an empty filter means "no filter" |
| A new query path forgets the filter | the filter is a habit and not part of the function signature |
| The tenant id comes from the client | an attacker changes one value |
| A cache keyed only by the query | tenant 2 gets tenant 1's cached answer |
| Deleting a tenant's document leaves its vectors | the deleted content is still returned (note 4) |

Task 6 tests the second one directly: a query from tenant 2 who has **zero documents** must return an empty list.

## 4. Defence in depth
- **Postgres row-level security (RLS):** a policy such as `USING (tenant_id = current_setting('app.tenant_id')::uuid)` makes the database itself refuse other tenants' rows even if a query forgets the filter. The app sets `app.tenant_id` for each request. I look at it as a second layer, not a replacement for the filter.
- **A test that tries to break it:** two tenants with real data, and queries from each, checked against each other's chunk ids. This test should stay in the suite for good.
- **Logging:** record the tenant id with each search (Day 6 already logs `tenant_id` in the request logs and the `llm_calls` table).

## 5. How the test for today looks
1. Create tenant 1 and tenant 2. Tenant 1 owns the corpus chunks. Tenant 2 owns a few small chunks with distinctive text (or none).
2. As tenant 2, search with a query that tenant 1's chunks answer perfectly. The result must contain **only tenant 2's chunks**, and an empty list when tenant 2 has none.
3. As tenant 1, search with a query that only tenant 2's text answers. It must not appear.
4. Repeat step 2 with a **tenant that has zero chunks**, and with a made-up tenant id.
5. Check the same on **both stores**, pgvector and Qdrant, through the same `VectorStore` interface.

## 6. Qdrant's tenant optimisation (awareness)
For a collection with many small tenants, Qdrant lets me mark the tenant payload field as the tenant key when I index it, so that a tenant's points are stored and linked together and the filtered search stays fast. I read the multitenancy page of the version I install before I set it.
