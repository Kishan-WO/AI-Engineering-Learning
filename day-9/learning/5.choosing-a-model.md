# Choosing a model: a leaderboard to start, my own queries to decide

The choice of embedding model is made on my own text and my own questions. A public score is where I start looking, not what I trust.

## 1. The MTEB leaderboard as a starting point
- **MTEB** (Massive Text Embedding Benchmark) is a public leaderboard that scores models on many tasks (retrieval, classification, clustering and more) across many datasets. It is hosted on Hugging Face.
- How I use it:
  - filter to the **retrieval** results, not only the overall average;
  - filter by language or use the multilingual list when Hindi matters;
  - note the **model size and the maximum input length**, which the table shows, because the top model may be too large to run locally;
  - take 3 to 5 candidates, including one small and one large, and test those.
- What its limits are:
  - the datasets are mostly **English and general**, not documentation of one framework or Hindi school textbooks;
  - a model can be tuned to the benchmark, so a top rank does not guarantee a top result on my text;
  - an average hides the failures I care about (one language, long inputs, tables);
  - a gap of one or two points between neighbours is smaller than the noise in how it was measured.

## 2. My own queries are the real test
- The corpus, the questions and the language of the product are mine. A model that wins on a public benchmark and loses on my 20 queries is the wrong model for me.
- The measuring habit from Day 7 and 8 applies again:
  - write the test **before** running any model;
  - record the correct answer for each query up front;
  - print every result, not only the average;
  - state what the number cannot show.

## 3. Writing the test queries
| Rule | Why |
|---|---|
| Write each query from the **meaning** of the document, not by copying its sentences | a query that copies the words makes a keyword match look like semantic search, and every model passes |
| Use the words a real user would use ("how do I make a field optional") | users do not know the documentation's own terms |
| Mix easy and hard: some with shared words, some paraphrased, some where the document's term is different | an all-easy set cannot separate two models |
| Include 5 Hindi or Hinglish queries | the plan requires it, and it separates multilingual models from the rest |
| Record the correct document **and the section** before running anything | otherwise I will adjust the answer after seeing the result |
| Decide up front what counts as correct when the answer is in two documents | otherwise the scoring changes with each model |

I record each query as a row: `id`, `query`, `language`, `correct_doc_id`, `correct_section`, `type` (easy, paraphrased, hard).

## 4. Recall@k
- **recall@k** is the share of queries for which the correct document appears in the **top k** results.
```
recall@5 = (queries whose correct document is in the top 5) / (all queries)
```
- With one correct document per query this is a "hit rate". If a query has several correct documents, recall@k is the share of them found, and I say which definition I use.
- **MRR** (mean reciprocal rank) adds the position: a hit at rank 1 scores 1, at rank 2 scores 0.5, at rank 5 scores 0.2, and a miss scores 0. It separates a model that puts the answer first from one that puts it fifth.
- I report recall@1, recall@5 and MRR, plus the **rank of the correct document** for every query, so I can see how far off the misses were.
- If the corpus is split into chunks, "found" must be defined: the correct chunk, or any chunk of the correct document. I choose before the run and keep it the same for both models.

> A worked example of recall@k and MRR (hit rate against share found, per-query ranks) is in `../Notes/11-recall-at-k-and-mrr.md`.

## 5. How little 20 queries can prove
- One query out of 20 is **5 points** of recall.
- With 20 queries, a measured recall of 0.80 has a rough 95% margin of about **plus or minus 17 points** (the standard error is the square root of 0.8 x 0.2 / 20, about 0.09, and the margin is about twice that).
- So two models at 0.80 and 0.85 on the same 20 queries **are not shown to be different**. I can say "the same on this set" and no more.
- Three things make the comparison fairer than the margin suggests: both models see the **same** queries (a paired comparison), I look at which queries each one misses, and I read the misses.
- Five Hindi queries are a smaller sample still. I report "3 of 5" and read each miss.
- What I do with a small set: treat it as a **smoke test and a way to find failures**, not as a ranking. The three failures in task 6 are worth more than the averages.

## 6. More than recall
| Also compare | Why |
|---|---|
| **Latency** of one query and of the corpus | an API round trip against a local forward pass |
| **Cost** to embed the corpus, and per query | small now, large at scale |
| **Vector size** | storage and search time (note 6) |
| **Maximum input length** | chunking limits and truncation |
| **Operational risk** | a provider can retire a model; a local model needs hardware and updates |
| **Data sensitivity** | an API sends my text to the provider |

## 7. Swapping models later
- Changing the model means **re-embedding the whole corpus**, because vectors from two models cannot be mixed.
- So I store the **model name, version, dimensions and the metric** next to the vectors (in the metadata JSON). A vector file with no record of its model is unusable later.

## Mistakes to avoid
| Mistake | What happens |
|---|---|
| Choosing by leaderboard rank only | a model that is good on English averages and bad on my text |
| Queries copied from the document | every model scores high; nothing is learned |
| Writing the expected answers after seeing results | the test is fitted to the winner |
| Reporting a difference of one query as a result | noise taken for a finding |
| Judging only the average | the misses, where the real lessons are, go unread |
| Using the model without its query prefix or input type | a worse score that is blamed on the model |
