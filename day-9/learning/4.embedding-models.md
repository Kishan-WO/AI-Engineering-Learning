# Embedding models: the landscape and what to compare

There are many embedding models. They differ in quality, languages, input length, vector size, cost and where they run. This note is the map. The specific numbers below come from the model cards and pricing pages as I know them, so **I re-check each one on the provider's page before the benchmark**: models and prices change.

## 1. Two families
| | API models | Open models (run by me) |
|---|---|---|
| How I use them | an HTTP call with my key | download the weights and run them (`sentence-transformers`) |
| Cost | per token, billed by the provider | free to use, but I pay in hardware and time |
| Setup | an API key | a 0.1 to 2+ GB download, and a CPU or GPU |
| Speed | network round trip, with rate limits | no network; CPU is slow, GPU is fast |
| Data leaves my machine | yes | no |
| Changes under me | the provider can retire or change a model | the version I downloaded stays the same |

## 2. API models
| Provider | Models to know | Notes |
|---|---|---|
| **OpenAI** | `text-embedding-3-small` (1,536 dimensions), `text-embedding-3-large` (3,072) | input up to about 8,191 tokens; a `dimensions` parameter shortens the vector; no query and document distinction; priced per million input tokens (small is the cheaper one) |
| **Google Gemini** | `gemini-embedding-001` and newer ones on the model list | multilingual; a `task_type` for query and document; the vector can be shortened (note 6); a free tier exists, which is my default for the benchmark |
| **Cohere** | Embed v3 and v4 families, including multilingual variants | an `input_type` parameter; strong multilingual models; a free trial key |
| **Voyage AI** | `voyage-*` models, including general and domain-specific ones | an `input_type` parameter; long inputs; an optional free allowance |

- I compare these on the same four questions: how many dimensions, how long an input, which languages, and what it costs per million tokens.
- Each provider has limits on **requests per minute**, **tokens per minute** and **inputs per request**. They decide how I batch (section 6).

## 3. Open models
| Model | What it is | Dimensions | Max input | Languages |
|---|---|---|---|---|
| **BGE-M3** (`BAAI/bge-m3`) | large, strong multilingual model that can also give sparse and multi-vector output | 1,024 | about 8,192 tokens | 100+ including Hindi |
| **multilingual-e5** (`intfloat/multilingual-e5-small/base/large`) | the E5 family, trained with `query:` and `passage:` prefixes | 384 / 768 / 1,024 | 512 tokens | 100 languages |
| **Nomic embed** (`nomic-ai/nomic-embed-text-v1.5`) | long input, shortenable vectors | 768 | about 8,192 tokens | mainly English (check the newer multilingual release) |
| **GTE** (`Alibaba-NLP/gte-*`) | the GTE family, with long-input and multilingual variants | 768 and up | up to about 8,192 tokens | depends on the variant |
| **sentence-transformers classics** (`all-MiniLM-L6-v2`, `all-mpnet-base-v2`) | small and fast, the usual first model | 384 / 768 | about 256 to 384 tokens | English |

- `sentence-transformers` is the library that loads most of them behind one interface:
```python
from sentence_transformers import SentenceTransformer
model = SentenceTransformer("BAAI/bge-m3")
vectors = model.encode(texts, batch_size=16, normalize_embeddings=True)   # (n, 1024) float32
```
- The first call downloads the model (BGE-M3 is a few GB), so it is done once and the files are cached.
- On a laptop CPU, a 200-document corpus is fine with a small or base model. BGE-M3 on CPU takes minutes for a few hundred texts, not seconds, and that time goes into the latency column of the benchmark.

## 4. Multilingual support: essential for Hindi and Hinglish
- An **English-only** model (`all-MiniLM-L6-v2`, many `*-en-*` models) does badly on Hindi text, because most Devanagari words are rare or split into many pieces for it.
- **Hinglish** (Hindi in Latin letters, "fees kitni hai?") is a harder case again: it is not a language the model's data covers in a clean way. Test it, because a model that handles Devanagari Hindi may still stumble on Hinglish.
- A multilingual model also gives **cross-lingual search**: a Hindi query can find an English document, because both land in the same space. That is why the benchmark includes Hindi and Hinglish queries against an English corpus.
- The plan's benchmark needs 5 Hindi or Hinglish queries. With 5 queries, one result is 20 points of that subgroup, so I report it as a count ("3 of 5") and not as a percentage.

## 5. Max input length
| Model type | Typical limit |
|---|---|
| older sentence-transformers | 256 to 512 tokens |
| E5, Cohere v3 | 512 tokens |
| OpenAI v3, BGE-M3, Nomic, GTE long | about 8,000 tokens |
| Voyage and some newer models | 16,000 to 32,000 tokens |

- Text beyond the limit is **cut off silently by some libraries** (the library truncates and never warns) or **rejected with an error by some APIs**. Either way, the end of a long chunk is not embedded.
- A section of documentation of 1,200 words is roughly 1,600 tokens. A 512-token model sees only the first third of it. This is a reason to split by heading and to check the length of my longest chunks against each model's limit.
- A longer limit is not a reason to embed a whole chapter: one vector for a chapter blurs everything (note 2).

## 6. Cost, throughput and batching
- **Cost:** an embedding call is billed on **input tokens only**. Embedding 200 documents of about 700 tokens each is roughly 140,000 tokens, which is a few cents or free on a free tier. The real cost comes later: re-embedding when the model changes, and embedding every query.
- **Batching:** an API accepts a list of texts per request (the maximum per request differs by provider, from a few dozen to 2,048). One request of 100 texts is much faster than 100 requests, and it uses far fewer of the per-minute request limit.
- **Rate limits:** a free tier is limited per minute and per day. A run of several hundred texts needs a batch size under the per-request limit and a pause or retry on a 429 (the Day 6 retry layer already does this for chat calls).
- **Throughput** for open models depends on hardware and batch size; on CPU it is the slowest part of the benchmark.
- **Idempotence:** I save each batch's vectors as soon as it returns, so a failed run resumes without paying for the finished batches again.
