# What an embedding is

An embedding turns a piece of text into a list of numbers of a fixed length. Texts with similar meaning get lists that are close to each other. That one idea makes search by meaning possible.

## 1. Text to a fixed-length vector
```
"How do I add a path parameter?"  ->  [0.012, -0.044, 0.130, ... ]   (1,024 numbers)
"Declaring URL variables"         ->  [0.009, -0.051, 0.122, ... ]   (1,024 numbers)
"Chocolate cake recipe"           ->  [-0.200, 0.071, -0.015, ... ]  (1,024 numbers)
```
- The length is **fixed by the model** (384, 768, 1,024, 1,536, 3,072 and so on), whatever the length of the text. A word and a page both come out as the same number of values.
- Each number alone means nothing I can read. The meaning is in the **position of the whole vector** relative to other vectors.
- A model turns text into a vector with no memory of earlier calls: the same text and the same model give the same vector (apart from tiny numeric differences on some hardware).

## 2. Similar meaning, nearby vectors
- Think of each vector as a point in a space with 1,024 directions. The model is trained so that texts used in similar contexts land close together.
- The first two texts above share **no words** ("path parameter" and "URL variables"), but they mean nearly the same, so their vectors are close. The third is far from both.
- This is the difference from keyword search:

| | Keyword search (BM25, `LIKE`, full text) | Embedding search |
|---|---|---|
| Matches on | the same words (or stems) | the same meaning |
| "car" finds "automobile" | no | yes |
| Exact names, codes, error numbers | strong | weak |
| A rare word the model never saw | strong | the model may place it badly |
| Needs a model and vectors | no | yes |

- Neither wins everywhere. Day 12 combines them (hybrid search); today only the embedding half is built.

## 3. An embedding model is not a chat model
| | Chat model (Day 4 to 8) | Embedding model |
|---|---|---|
| Input | a conversation | a text |
| Output | generated text, token by token | one vector of numbers |
| Size and cost | large, billed for input and output tokens | smaller and much cheaper, billed for input tokens only |
| Speed | seconds | milliseconds to a few seconds per batch |
| Used for | answering, writing, deciding | searching, comparing, grouping |
| Can it follow instructions | yes | no: it does not answer, it only places the text |

- Asking an embedding model a question does not give an answer. It gives the position of the question, and the answer is the document **nearest** to that position.
- In a RAG system (Day 12 onward) the embedding model finds the passages and the chat model writes the answer from them. They are two models with two jobs.

## 4. Queries and documents are not the same kind of text
- A query is short and often a question ("how to validate an email field?"). A document is long and states facts ("`EmailStr` validates email addresses...").
- Many models are trained for this asymmetry, and they want to be told which kind of text they are given.

| Model family | How the kind is given |
|---|---|
| E5 (`intfloat/multilingual-e5-*`) | text prefixes: `"query: ..."` and `"passage: ..."` |
| Nomic embed | `"search_query: ..."` and `"search_document: ..."` |
| BGE (v1.5 English models) | a prefix on the **query only**: `"Represent this sentence for searching relevant passages: ..."` (BGE-M3 needs none) |
| Gemini embeddings | a parameter: `task_type` = `RETRIEVAL_QUERY` or `RETRIEVAL_DOCUMENT` |
| Cohere, Voyage | a parameter: `input_type` = `search_query` or `search_document` |
| OpenAI `text-embedding-3-*` | nothing: the same call for both |

- **Forgetting the prefix or the input type does not raise an error.** The search still returns results, only worse ones. This is a silent quality bug, so the benchmark has to use each model the way its own documentation says (the exact current wording is on the model's page; I check it when I build).
- Documents are embedded **once** (when the corpus is built) and queries **every time**. A query-time call must use the query form, and the stored vectors the document form.
- The same model must embed both sides. Vectors from two different models live in two different spaces and cannot be compared, even when they have the same length.

## 5. What it can and cannot do
| Good at | Weak at |
|---|---|
| paraphrases and synonyms | exact identifiers, version numbers, error codes |
| a question matching the passage that answers it | negation ("works" and "does not work" can be close) |
| matching across languages (in a multilingual model) | numbers and comparisons ("under 5,000 rupees") |
| grouping similar items | very long texts (the vector is one average of the whole text) |
| ignoring typos and word order a little | domain words the model never saw |

- Every weakness above is a place where task 6 (three queries where both models fail) will find its examples.

## 6. Text length and chunking
- A model reads only up to its **maximum input length** (note 4) and cuts or rejects the rest.
- One vector for a whole long document blurs many topics into one point. Splitting into **chunks** (by heading today, smarter on Day 11 and 12) gives each topic its own vector.
- A chunk must carry enough of its own context to be understood alone: a section titled "Parameters" is hard to place unless the title of the page is kept with it. I store the page title and the heading in the metadata, and consider adding them to the text that gets embedded.
