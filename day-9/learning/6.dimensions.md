# Dimensions: what the size of a vector costs

Every vector has `d` numbers. A larger `d` can hold more detail, and it costs storage, memory and search time in direct proportion. I want to know the price before I pick a model.

## 1. Storage and memory
```
bytes = number of vectors x dimensions x bytes per number
```
For `float32` (4 bytes):
| Vectors | 384 dims | 768 dims | 1,024 dims | 1,536 dims | 3,072 dims |
|---|---|---|---|---|---|
| 1,000 | 1.5 MB | 3.1 MB | 4.1 MB | 6.1 MB | 12.3 MB |
| 100,000 | 154 MB | 307 MB | 410 MB | 614 MB | 1.23 GB |
| 1,000,000 | 1.54 GB | 3.07 GB | 4.10 GB | 6.14 GB | 12.29 GB |

- My Day 9 corpus (a few hundred to a few thousand vectors) is a few megabytes: the size is no problem at all.
- Size starts to matter at **hundreds of thousands to millions** of vectors. The matrix has to sit in RAM for fast search, and a vector database also stores an index on top of the vectors (often as much again or more, depending on the index).
- Also count the copies: the `.npy` file, the database table, the index and any backup.

## 2. Search time
- Brute-force search is one matrix multiply: `n x d` multiply-adds per query. **Time grows in direct proportion to `d`** (and to `n`).
- Going from 3,072 to 768 dimensions makes the multiply about four times cheaper, and four times less data to read from memory.
- For a few thousand vectors this is invisible: both are well under a millisecond or a few milliseconds. The cost is real when `n` is large, which is why Day 10 introduces approximate indexes.
- Memory bandwidth is usually what limits brute force, so smaller vectors (fewer bytes) help even more than the arithmetic count suggests.

## 3. Quality against size
- More dimensions usually means **slightly better** retrieval, with diminishing returns: 3,072 is not three times better than 1,024.
- A model trained at 1,024 dimensions is often better than a weaker model at 3,072. **The model's quality matters more than its vector size.**
- The right question is not "what is the largest" but "what is the smallest size that keeps recall on my queries". I can answer it with the same 20 queries (note 5), by truncating the vectors and re-running recall@5.

## 4. Matryoshka embeddings
- A **Matryoshka** model is trained so that the **first `m` numbers** of the vector already form a good, smaller embedding, like nested dolls. The most important information is packed into the front.
- Then I can **truncate**: keep the first 256 or 512 numbers, throw away the rest, and lose only a little quality.
```python
full = np.load("vectors_1536.npy")            # (n, 1536)
small = full[:, :512]                          # keep the first 512 numbers
small = small / np.linalg.norm(small, axis=1, keepdims=True)   # re-normalise: the length is no longer 1
```
- **Re-normalising after truncation is required.** The first 512 numbers of a unit vector do not have length 1 any more, and a dot product on them is no longer a cosine.
- Which models support it: only models **trained for it**. OpenAI `text-embedding-3-*` (through the `dimensions` parameter), Nomic embed v1.5 and some Gemini embedding models are documented as Matryoshka-style. Truncating a model that was not trained this way throws away information at random and can hurt a lot. I check the model card.
- Some APIs do the truncation and re-normalisation for me (a `dimensions` or `output_dimensionality` parameter). Doing it myself on stored full vectors lets me try several sizes without paying to re-embed.
- It gives a cheap two-stage search: search fast with 256 dimensions, then re-score the best candidates with the full vectors.

## 5. Quantisation (awareness)
Quantisation stores each number with fewer bits.
| Format | Bytes per number | Size against float32 | Quality effect |
|---|---|---|---|
| `float32` | 4 | 1x | the reference |
| `float16` | 2 | 2x smaller | almost none |
| `int8` | 1 | 4x smaller | small loss; needs a scale to map the numbers to -127..127 |
| **binary** (1 bit: the sign) | 1/8 | 32x smaller | larger loss; compared with Hamming distance (count of different bits), very fast |

- Binary vectors are often used **to find candidates fast**, then the top candidates are **re-ranked with the full vectors**: most of the speed and little of the loss.
- Vector databases (Day 10) offer these as options (for example scalar and binary quantisation). I do not build quantisation today: it is awareness.
- The same rule applies as for truncation: measure recall on my own queries before and after.

## 6. A way to decide
1. Start with the model's default size.
2. If the corpus is small (under about 100,000 vectors), **stay at the default**. Saving memory is not worth any loss in recall.
3. If size or speed becomes a problem, try a Matryoshka truncation or `int8`, and compare recall@5 on the same queries.
4. Keep the full-size vectors until the smaller ones are proven good enough.
5. Record the dimensions and the quantisation next to the vectors, as with the model name.

## Mistakes to avoid
| Mistake | What happens |
|---|---|
| Truncating vectors from a model that is not Matryoshka-trained | quality drops by an unknown amount |
| Truncating and not re-normalising | the dot product is not a cosine; scores are wrong |
| Choosing 3,072 dimensions "to be safe" for a small corpus | more storage and time for no measured gain |
| Comparing recall across different dimension sizes with different queries | the comparison means nothing |
| Not recording the dimensions | later a file cannot be matched to its model |
