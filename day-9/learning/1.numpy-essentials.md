# NumPy essentials: only what semantic search needs

An embedded corpus is one big table of numbers, one row per document. Search is arithmetic on that table. I only need a few NumPy tools, and I need to know exactly what each one does to the shape and type of an array.

## 1. Arrays, `shape` and `dtype`
```python
import numpy as np

docs = np.zeros((200, 1024), dtype=np.float32)   # 200 documents, 1,024 numbers each
docs.shape        # (200, 1024): rows are documents, columns are dimensions
docs.dtype        # float32
docs[7]           # the vector of document number 7, shape (1024,)
docs[:, 0]        # the first number of every document, shape (200,)
```
- **`shape`** is a tuple. A matrix of `n` documents with `d` dimensions has shape `(n, d)`. One vector has shape `(d,)`. A query vector that is `(d,)` and one that is `(1, d)` behave differently in a matrix multiply, so I always check the shape.
- **`dtype`** is the number type.

| dtype | Bytes per number | Use |
|---|---|---|
| `float64` | 8 | NumPy's default for Python floats; twice the memory for no gain here |
| `float32` | 4 | the standard for embeddings; most models output it |
| `float16` | 2 | half the memory, less precise; awareness only |
| `int8` | 1 | quantised vectors (note 6) |

- **Memory is `n x d x bytes`.** 200 documents x 1,024 x 4 bytes is 0.8 MB. 1 million vectors x 1,024 x 4 bytes is 4.1 GB. This is why dimension size matters (note 6).
- A list of Python floats becomes `float64` unless I say `np.array(values, dtype=np.float32)`. Mixing the two silently upcasts, and a `float64` copy of a large matrix doubles the memory.

## 2. Vectorised operations
A vectorised operation works on a whole array in compiled code, with no Python loop.
```python
a = np.array([1.0, 2.0, 3.0], dtype=np.float32)
a * 2             # [2. 4. 6.]
a + a             # [2. 4. 6.]
(a * a).sum()     # 14.0
```
- A Python `for` loop over 200 vectors is slow and long. One matrix operation does the same work much faster, because the loop runs in C.
- Rule: if I write a `for` loop over rows of an embedding matrix, I am probably missing a vectorised version.

## 3. Broadcasting
Broadcasting lets arrays of different shapes work together. NumPy compares the shapes from the right, and a dimension of size 1 (or a missing one) is stretched to match.
```python
docs = np.ones((200, 1024), dtype=np.float32)
norms = np.linalg.norm(docs, axis=1, keepdims=True)   # shape (200, 1)
docs / norms                                          # (200, 1024) divided by (200, 1): each row by its own norm
```

| Shapes | Result |
|---|---|
| `(200, 1024)` with `(200, 1)` | works: each row is divided by its own number |
| `(200, 1024)` with `(1024,)` | works: the same vector is applied to every row |
| `(200, 1024)` with `(200,)` | **error** (or the wrong result when the numbers happen to match): `(200,)` lines up with the last axis, 1,024 |

- `keepdims=True` is what keeps the `(200, 1)` shape. Without it the norms have shape `(200,)` and the division fails.
- The mistake to fear is a broadcast that **works but is wrong**, for example a square matrix divided by a `(n,)` array. I check the result shape and a known value after every step.

## 4. Matrix multiply: `@` and `np.dot`
```python
scores = docs @ query        # (200, 1024) @ (1024,) -> (200,)
```
- `@` is matrix multiplication. The last axis of the left array must match the first axis of the right one (`1024` with `1024`).
- For a matrix and a vector it gives one number per row: the dot product of each document with the query. **That one line is the entire scoring step of semantic search.**
- Many queries at once: `(q, d) @ (d, n)` gives `(q, n)`, a score for every query against every document. The documents need to be transposed: `queries @ docs.T`.
- `np.dot` gives the same result for these shapes. I use `@` because it reads like the maths and does not change meaning for higher-dimensional arrays.

## 5. Norms and normalising rows
```python
np.linalg.norm(v)                         # the length of one vector: sqrt(sum of squares)
np.linalg.norm(docs, axis=1)              # the length of every row: shape (200,)
docs / np.linalg.norm(docs, axis=1, keepdims=True)   # every row now has length 1
```
- A vector divided by its own length has length 1 and the same direction. This is **normalising**.
- On normalised vectors, the dot product is the cosine similarity (note 3). So I normalise once when I build the matrix, and the search stays a single `@`.
- A zero vector has norm 0, and dividing by it gives `nan`. An empty text can produce one, so I check for it.
- Some models (OpenAI, many sentence-transformers with a normalise option) return unit vectors already. I verify with `np.linalg.norm(docs, axis=1)` rather than assume.

## 6. Top-k: `argsort` and `argpartition`
After scoring I want the `k` best documents, not the whole ordering.
```python
order = np.argsort(-scores)[:k]                 # full sort, then cut: O(n log n)

part = np.argpartition(-scores, k)[:k]          # the k best, in no particular order: O(n)
order = part[np.argsort(-scores[part])]         # sort only those k
```
- `argsort` returns the **indices** that would sort the array, not the sorted values. Negating the scores gives a descending order.
- `argpartition(-scores, k)` puts the `k` best indices in the first `k` positions without sorting them. It is faster on large arrays, and then I sort only those `k`.
- The plan's task 3 asks for `argpartition`. For 200 documents the difference is invisible; at a million vectors it is real.
- If `k` is larger than `n`, `argpartition` raises an error, so use `min(k, n - 1)` or check first.
- Ties: two documents with the same score can come out in either order. Duplicated documents produce exactly this.

> A worked example of this step, with the exact index arrays, is in `../Notes/topk-argsort-vs-argpartition.md`.

## 7. Saving and loading: `.npy`
```python
np.save("vectors.npy", docs)                  # float32 (200, 1024), a few hundred KB
docs = np.load("vectors.npy")                 # same shape and dtype back
docs = np.load("vectors.npy", mmap_mode="r")  # do not read it all into memory, map the file
```
- `.npy` stores the shape and dtype with the data, so nothing is guessed on load.
- The matrix has no labels. Row `i` means document `i`, so I keep a **metadata JSON in the same order** (id, title, source, text or path) and check that its length equals `docs.shape[0]` on load.
- If the corpus changes, both files are rebuilt together, otherwise row 7 and metadata entry 7 point to different documents. That bug gives wrong answers with no error.

## The whole search in six lines
```python
docs = np.load("vectors.npy")                                  # (n, d), rows already normalised
q = embed(query); q = q / np.linalg.norm(q)                    # (d,), unit length
scores = docs @ q                                              # (n,), cosine similarity
top = np.argpartition(-scores, k)[:k]                          # the k best, unordered
top = top[np.argsort(-scores[top])]                            # ordered best first
results = [(meta[i], float(scores[i])) for i in top]
```

## Mistakes to avoid
| Mistake | What happens |
|---|---|
| Not normalising, then reading the dot product as a cosine | long documents or large-norm vectors win for the wrong reason |
| Normalising the documents but not the query | scores have the wrong scale and a threshold means nothing |
| `float64` everywhere | twice the memory and slower, with no better search |
| Dividing by a `(n,)` array of norms instead of `(n, 1)` | an error, or a wrong result that looks valid |
| Matrix and metadata in a different order | wrong documents returned, no error |
| `argsort(scores)` without the minus sign | the **worst** documents come first |
| Looping over rows in Python | correct but slow, and the sign of missing the matrix form |
