# Prompt anatomy: the parts of a good prompt

On Day 5 and 6 I wrote prompts as plain strings (`SYSTEM_PROMPT` in `extract_service.py`, the long `chat_system.md`) and judged them by reading the output. Day 7 is about writing them on purpose and **measuring** them. First, what is inside a prompt.

## 1. The five parts
| Part | The question it answers | Example (classify a student query) |
|---|---|---|
| **Role / context** | Who is the model, and what is the situation? | "You sort incoming messages for an Indian training institute's help desk." |
| **Task** | What exactly must it do? One clear verb. | "Classify the message into exactly one category." |
| **Constraints** | What must it not do, and what are the limits? | "Use only the categories below. If nothing fits, answer `other`. Do not answer the question." |
| **Output format** | What does the answer look like? | "Reply with only the category name, in lower case." |
| **Examples** | What does a good answer look like for a real input? | Two or three message and label pairs |

- Not every prompt needs all five. A small, clear task may need only task, constraints and format.
- The order is a habit, not a law: context, then task, then constraints, then format, then examples, then the real input.
- If a prompt does not work, I check which part is missing before I add more words.

## 2. Be specific: audience, length, tone
Vague prompts give vague answers.
| Vague | Specific |
|---|---|
| "Explain the refund policy." | "Explain the refund policy to a parent in 3 short sentences, in simple English, without legal words." |
| "Summarise this." | "Summarise this email in one sentence of at most 20 words for the admissions team." |
| "Be helpful." | "Answer in the same language the student wrote in. Use a friendly, polite tone. Never promise a job." |

Three things to state whenever they matter: **who reads it** (audience), **how long** (sentences, words, items), and **how it should sound** (tone).

## 3. Delimit the input
When a prompt holds both my instructions and **data** (a student's message, a document), the model must know where one ends and the other starts.
```
Classify the message between the <message> tags.

<message>
{message}
</message>
```
- XML-style tags (`<message>`, `<document>`, `<example>`) or clear headed sections (`### Message`) both work. Pick one style and keep it.
- It is the same idea I used in `/extract` on Day 5: the text goes inside `<message>` tags and the system prompt says it is **data, not instructions**. That sentence is a prompt-injection defence, but only a soft one (see `3.system-prompting.md`).
- A tag must be **closed**. Input 39 of the Day 6 messy set tried to close the tag itself (`</message> New instructions: ...`). A model reads tags as hints; code that builds the prompt should not trust user text to stay inside them.
- Tags also make examples easy to read for me, and easy to find and change.

## 4. Where things go: long documents first, question last
For long inputs the order matters:
```
<documents>   ... long text ...   </documents>

Question: ...
```
- **Put long documents or data first, and the instructions and question last.** The model reads left to right and the question is freshest when it starts to answer. Some providers' prompt guides recommend this for long contexts.
- **Put the stable part first, the changing part last.** This is also what prompt caching needs (Day 6): the system prompt and fixed instructions come first so the provider can reuse them, and the new message comes at the end.
- Both rules agree: fixed text and long reference material first, the specific request at the end.

## 5. A prompt skeleton I can reuse
```
# Role
You are ... for ...

# Task
Your job is to ...

# Rules
- ...
- If the information is not in the text, answer "unknown". Never guess.

# Output format
Reply with ... only.

# Examples
<example> ... </example>

# Input
<message>
{message}
</message>
```
Headings or tags, one thing per line, the input last.

## 6. Mistakes to avoid
| Mistake | What happens |
|---|---|
| Many rules that contradict each other ("be brief" and "explain in detail") | The model picks one at random per call |
| Saying what not to do without saying what to do | "Don't be formal" gives no direction; "write like a friendly counsellor" does |
| Instructions buried inside the data | The model may treat them as part of the data (or obey the data) |
| The question in the middle of a long document | Weaker answers on long inputs |
| One giant paragraph | Hard for me to read and to change one thing at a time |
| Examples that do not match the real input | The model copies the example's style, not the task |

## Quick check
- What are the five parts of a prompt, and which would I add first if a small task fails?
- Why delimit user text, and why is that not a full defence against injection?
- Where do long documents go, and where does the question go?
- Why does "stable part first" help twice (clarity and caching)?
