# Measuring prompts: a test set, a score and one change at a time

"This prompt looks better" is an opinion. A measured score is evidence. Day 5 already taught me the lesson: the local model gave **valid** JSON for 9 of 10 messages, but only **39%** of the fields were right. Format is not truth, and reading a few outputs is not a measurement.

## 1. The labelled test set
A small set of inputs with the **correct answer written down by me, before I run anything**.
| Rule | Why |
|---|---|
| **20 to 30 cases** per prompt | enough to see big differences, small enough to label by hand |
| **Real, messy inputs** (English, Hinglish, typos, emojis, short, long) | the clean cases are not where prompts fail |
| **Cover every label**, including the escape label (`other`) | a label never tested is never measured |
| **Include hard cases**: two topics in one message, sarcasm, a message with no clear request | easy cases score 100% on every version and tell me nothing |
| **Roughly balanced** labels | 25 of 30 cases being `fees` rewards a prompt that always says `fees` |
| **Fixed**: the same set for every version | otherwise I compare different exams |
| **Separate from the few-shot examples** | an example that is also a test case inflates the score |
| Stored in a file next to the code (`jsonl` or `csv`) | it is part of the project, reviewed like code |

The Day 6 messy-input file is the model for this: each case carries what a correct run looks like.

## 2. Scoring
| Task | Metric |
|---|---|
| A label (classification) | **exact match**: right or wrong. Accuracy = right / total. Also look at a small **confusion table** (which label is mistaken for which) |
| Structured fields (`/extract`) | **field-level accuracy**: each field is right or wrong; average over all fields. Count `null` where `null` is right as correct |
| Free text (a chat answer, a summary) | a **rubric**: a short checklist scored 0 or 1 per item (correct fact, in the right language, under 3 sentences, no invented fee). Scoring by another model ("LLM as judge") is possible, but it must itself be checked against my own labels |

Keep the score simple enough to compute **in code, the same way every time**.

## 3. Change one thing at a time
The plan's four versions are a ladder, and each step changes **one** idea:
| Version | What changes from the one before | Question it answers |
|---|---|---|
| **v1** zero-shot | nothing: the plain instruction | the baseline |
| **v2** clear structure and constraints | role, rules, closed labels, output format, delimiters | does a better-written prompt beat the baseline? |
| **v3** few-shot | v2 plus a few diverse examples | do examples help beyond clear rules? |
| **v4** chain-of-thought or a reasoning model | v3 plus reasoning | does reasoning help, and at what cost? |

If I change the examples **and** the wording **and** the model together and the score rises, I do not know why. Keep the **model, temperature and test set fixed** while the prompt changes; when comparing models, keep the prompt fixed.

## 4. What to record for each version
| Column | Where it comes from |
|---|---|
| **Accuracy** (and the number of right cases, such as 26 of 30) | my scoring code |
| **Input tokens per call**, **output tokens per call** | `usage` (Day 6) |
| **Cost per call**, and per 1,000 calls | the price table (Day 6) |
| **Latency** (median) | the call logs |
| Failures: invalid, refused, cut off | the outcome categories (Day 6 report) |
| The wrong cases themselves | read them: they tell me what to fix |

The Day 6 `llm_calls` table and `compute_cost()` already give the tokens and cost; the prompt version (`5.prompts-as-code.md`) lets me group them by version.

## 5. How big a difference is real?
With a test set of **30 cases, one case is 3.3 points**. A score of 26/30 is 86.7%; 27/30 is 90%.
- The random noise on 30 cases is large: for an accuracy around 85% the standard error is about 6 to 7 points. A difference of one or two cases is **inside the noise**.
- So the plan's rule, "keep the cheapest version within **2 points** of the best", effectively means "the same, or at most one case worse" on 30 cases. I should say that openly in the decision, instead of pretending 2 points is precise.
- To be more sure: run the set **twice** (even at temperature 0, outputs can differ slightly), look at which cases flip, and add more hard cases rather than chasing decimals.
- A big jump (10 points or more) is a real signal. A tiny one is a reason to prefer the **cheaper, simpler** version.

## 6. Why "it looks better" is not evidence
- I remember the outputs I looked at, not the ones I did not.
- I read with the hope that my change helped.
- A prompt can improve three cases and break two others I never checked.
- Small models and big models fail in different places (Day 5: Gemini 98% of fields, local 39%).
- A better-looking answer (more polite, longer) may be **less correct**.

A score on a fixed labelled set does not care what I hoped.

## 7. The decision, written down
After measuring, pick the **cheapest version within the allowed gap of the best** and record it in `decisions.md`:
```
Prompt classify_query: chose v2.
v1 zero-shot 22/30 (73%), 140 tokens, 0.00004 USD per call
v2 structured 27/30 (90%), 210 tokens, 0.00006 USD
v3 few-shot   28/30 (93%), 520 tokens, 0.00014 USD   <- best, but 2.3x the cost of v2 for one more case
v4 reasoning  28/30 (93%), 900 tokens, 0.00041 USD
Within one case of the best at less than half the cost: v2.
```
(The numbers above are an **illustration of the format only**; the real ones come from the measured run.) The record says what was measured, the cost, the gap, and the reason: so the choice can be revisited when a model or a price changes.

## Mistakes to avoid
| Mistake | What happens |
|---|---|
| A test set of 5 cases | every score is noise |
| Only easy cases | all versions score about the same |
| Labels written after seeing the outputs | the "answers" bend toward the model |
| Changing the model and the prompt together | the cause is unknown |
| Few-shot examples taken from the test set | an inflated score |
| Looking only at accuracy | the winner may cost 10 times more |
| Not reading the wrong cases | I miss the pattern to fix next |

## Quick check
- Why must I write the correct labels before running the prompts?
- What does one case mean in points on a 30-case set, and what does that do to the "within 2 points" rule?
- What do I record for each version besides accuracy?
- Why must the few-shot examples be kept out of the test set?
