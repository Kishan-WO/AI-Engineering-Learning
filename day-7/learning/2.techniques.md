# Prompting techniques: zero-shot, few-shot, chain-of-thought and friends

The plan asks me to measure four versions of one prompt on Day 7: **v1 zero-shot, v2 clear structure and constraints, v3 few-shot, v4 chain-of-thought or a reasoning model**. This note is what each of those means, what it costs, and when it helps.

## 1. Zero-shot
Just the instruction, no examples.
```
Classify this student message as one of: admission, fees, schedule, academic, complaint.
Message: "my fees receipt has the wrong amount"
```
- **Cheapest**: fewest input tokens.
- Works well when the task is common and the labels are obvious.
- It is my **baseline**: any fancier version must beat it on the test set to be worth its cost (`6.measuring-prompts.md`).

## 2. Few-shot
Add a few worked examples (input and the correct output) before the real input.
```
Message: "when does the python batch start?"      -> schedule
Message: "I was charged twice, please refund"      -> complaint
Message: "what is the fee for web development?"    -> fees
Message: "{real message}"                          ->
```
What makes examples good:
| Rule | Why |
|---|---|
| **Diverse**: different wording, length, language (English, Hinglish) | The model learns the task, not one phrasing |
| **Representative**: like the real inputs, including messy ones | An example from a clean textbook teaches nothing about WhatsApp text |
| **Cover every label**, and the "none of these" case | Otherwise the unlisted label is under-used |
| **Balanced**: about the same number per label | An example set that is 70% one label pulls the answers toward it |
| **Same format** in every example | The format is copied exactly |
| **Not from my test set** | Testing on the examples is cheating: the score looks better and means nothing |

**Order effects.** Models lean on the **last** examples (and sometimes the first). The same examples in a different order can change the answers. So: do not put all examples of one label at the end, and **test two orders** to see if the result moves.

Cost: examples are **input tokens on every call**. Ten long examples can cost more than the task itself. Prompt caching (Day 6) makes a fixed example block much cheaper, because it is part of the stable prefix.

## 3. Chain-of-thought (CoT)
Ask the model to **reason before it answers**: "think step by step", or "first list the facts, then decide".
```
Think through the message step by step, then give the final label on a new line as: LABEL: <label>
```
- Helps with **multi-step problems** (arithmetic, logic, comparing several facts).
- For a simple label or a field extraction it often adds cost and **no accuracy**.
- **It costs output tokens**, and output is the expensive side (Day 4 and 6: the output price is several times the input price). A 300-token reasoning before a 1-token label can make a call 10 times dearer.
- The answer must now be **parsed** from the end of a longer text, which creates a new way to fail. Use a fixed marker (`LABEL:`), or ask for the reasoning inside a JSON field before the answer field.
- **Reasoning models** (the ones with built-in thinking) already reason internally before they answer. Telling them "think step by step" is usually unnecessary and can even lower quality; they bill their thinking tokens as output tokens. With these, the lever is how much thinking they are allowed, not the phrase.

## 4. ReAct: reasoning plus acting (preview of agents)
The model alternates **Thought, Action, Observation** until it can answer:
```
Thought: I need the fee for web development.
Action: search_fees("web development")
Observation: 42,000 rupees
Thought: I have it.
Answer: The fee is 42,000 rupees.
```
- The "Action" is a **tool call** that my code runs; the result goes back to the model as the Observation.
- This is the pattern behind agents and tool use (Day 8 and later). Today I only need to recognise it.

## 5. Decomposition: several small prompts instead of one big one
Split a hard task into steps, each with its own prompt:
```
1. extract the facts from the message   (structured output)
2. classify the message                 (one label)
3. write the reply using 1 and 2        (free text)
```
- Each step is easier to write, to measure and to fix, and can use a **different model** (a cheap one for classifying, a better one for writing).
- Cost: more calls, more latency, and an error in step 1 flows into steps 2 and 3.
- This is the preview of **chains** (Day 8).

## 6. Self-consistency (awareness)
Ask the same question **several times** at a temperature above 0 and take the **majority answer**.
- Reduces random mistakes on hard questions.
- Costs **N times** the tokens and latency, so it is for rare, hard, high-value questions, not for a classifier on every request.

## 7. Which technique when
| Technique | Use when | Costs | Watch out |
|---|---|---|---|
| Zero-shot | the task is common and clear | least | may miss my labels' meaning |
| Clear structure + constraints (v2) | almost always, before anything else | a few more input tokens | rules that contradict |
| Few-shot | the labels are specific to my domain | input tokens per call | example order, leakage |
| Chain-of-thought | multi-step reasoning | many output tokens | parsing, useless for simple labels |
| Reasoning model | hard reasoning, I do not want to write the steps | thinking tokens + latency | price, not needed for easy tasks |
| ReAct / decomposition | the task needs tools or has clear steps | more calls | errors flow forward |
| Self-consistency | rare, hard questions | N times | not for every request |

**The rule I follow:** start at the top of the table and move down only when the **measured** score says the cheaper version is not good enough.
