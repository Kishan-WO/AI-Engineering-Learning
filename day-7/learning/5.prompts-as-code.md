# Prompts as code: files, versions and a registry

A prompt is part of my program's behaviour. If it lives as an f-string in the middle of a function, I cannot version it, review it, test it or tell which version answered a request. Day 7's build is a **prompt registry**.

## 1. Where my prompts are now (Day 5 and 6)
| Prompt | Where it lives today |
|---|---|
| `/extract` system prompt | the constant `SYSTEM_PROMPT` in `services/extract_service.py` |
| `/extract` input wrapper | an f-string: `f"<message>\n{text}\n</message>"` |
| `/extract` repair message | an f-string in the repair loop: `"That reply was not valid: {problems}. Reply again with corrected JSON only."` |
| `/chat` system prompt (short) | `CHAT_SYSTEM_PROMPT` in `core/config.py` |
| `/chat` system prompt (long) | `prompts/chat_system.md`, chosen by `CHAT_SYSTEM_PROMPT_FILE` |
| classifier (to be built) | not yet |

Task 2 of today is to move **every** one of these into the registry. The long file is already a file; the others are strings in code.

> **Update:** all of them are in the registry now (`extract_system`, `extract_user`, `extract_repair`, `chat_system`, `chat_basic`).

## 2. Why files and not f-strings
| Problem with f-strings in code | What files give me |
|---|---|
| A one-word change is a code change and a deploy | A prompt change is a reviewed file change |
| No history of what the prompt said last month | Git history, and old versions kept side by side |
| Hard to read: quotes, escapes, indentation | A plain Markdown file |
| Cannot tell which version answered | The version is in the log with every request |
| Cannot A/B test two versions | Load `v1` and `v2` by name |

Formats: **Markdown** (simple, readable), **YAML** (metadata next to the text: name, version, model hints), **Jinja2** (templates with loops and conditions). For this project, Markdown with a small YAML header is enough.

## 3. The layout from the plan
```
prompts/
  extract_system/
    v1.md
    v2.md
  chat_system/
    v1.md
  classify_query/
    v1.md
    v2.md
    v3.md
    v4.md
```
- One folder per **prompt name**, one file per **version**.
- **Never edit an old version.** A change is a new file (`v2.md`). Then `v1` can be reproduced and compared forever.
- Loaded **by name and version**: `get_prompt("classify_query", "v2")`.
- A default can point to the current version (a `latest` setting), but a request log must always store the **real** version, not "latest".

## 4. Templates and variables
A prompt has fixed text and **variables** (the message, the course list, today's date).
| Option | Example | Notes |
|---|---|---|
| `str.format` | `"Message: {message}"` | simple; breaks if the text contains `{` or `}` (JSON examples) |
| `string.Template` | `"Message: $message"` | no brace problem, no logic |
| **Jinja2** | `"Message: {{ message }}"` | loops, conditions, filters; the usual choice for larger prompts |

Rules:
- Use a **strict** mode so a missing variable is an error, not an empty string (`StrictUndefined` in Jinja2).
- **Never render user text as the template.** User text is a *value* for a variable, never part of the template source (otherwise a user can inject template code).
- Keep variables to the **end** of the prompt where possible, so the fixed part stays identical between calls (caching).
- Variables with lists (few-shot examples, labels) are better rendered from data, so the label list in the prompt and in the schema come from one place.

## 5. Log the prompt version with every request
If I cannot tell which prompt produced an answer, I cannot debug a drop in quality. Every LLM call should record:
```
prompt_name = "classify_query"
prompt_version = "v3"
```
- In `ai-service` the natural place is the context that already travels with each call (`CallContext`) and the `llm_calls` row (two new nullable columns, or one `prompt` column such as `classify_query@v3`).
- Then the Day 6 accounting question "who spends the money?" gets a sibling: **"which prompt version is cheaper, and which one fails more?"** The same table answers both.
- Also log it in the JSON log line, so a single request can be traced.

## 6. Prompt caching: structure for a stable prefix (from Day 6)
- The registry should make the **stable text first, the variables last** the default shape.
- Keep the stable part **byte-identical** between calls: no timestamp, request id or user name near the top. A rendered template must not change its first 4,000 tokens from call to call.
- When a new version changes the stable part, the cache starts cold again once. That is expected; measure cost after the first calls.

## Mistakes to avoid
| Mistake | What happens |
|---|---|
| Editing `v1.md` in place | Old results can no longer be reproduced |
| Logging "latest" instead of the real version | The log is useless for debugging |
| Rendering untrusted text as a template | Template injection |
| A missing variable becoming an empty string | A silently broken prompt |
| Variables at the top of the prompt | The cache never hits |
| Prompts scattered in several places | One of them is forgotten when I change the rest |
